# 0.6.0 drops the lazy-start build gate; `--lazy` stays an opt-in flag

*Decided 2026-11-18, by the slice (S2 slice 6), following earlier decisions. Nothing new was chosen.*

The question was whether Zigbox 0.6.0 builds lazy start by default or keeps it behind the
`-Dlazy-start` gate (the `lazy_start` build option). Two earlier decisions already settle it:

- [2026-11-16-0.5.2-s2-dormant.md](2026-11-16-0.5.2-s2-dormant.md) made S2 dormant for 0.5.2 only.
  It says S2's 0.6.0 work on `main` undoes the dormancy: `release_writer_version` goes back to
  `constants.layer_writer_version`, and the `lazy_start` option and `lazy_not_yet` in `src/cli.zig`
  are removed.
- The S2 brief's owner's call 5 ([S2-lazy-start.md](../briefs/S2-lazy-start.md), approved
  2026-11-14) keeps `--lazy` opt-in and experimental in S2. Making lazy start what a plain `zbx run`
  does is a later owner decision, once the demo has been green for a release.

So in 0.6.0:

- **Every build has lazy start.** The `lazy_start` build option is gone. The shipped binary, the
  unit tests and every VM demo run the same `zbx`.
- **`zbx push`, `zbx push --dry-run` and `zbx store export` write layer writer 2**, with the lazy
  index and the `org.zigbox.lazy-index` annotation (owner's call 3). The same tree gets new layer
  and manifest digests compared with 0.5.x. Every gzip reader, and every `zbx` since 0.5.2, reads
  writer 2 layers.
- **`zbx run` without `--lazy` is unchanged.** Lazy start happens only when `--lazy` is given, or
  `StartOptions.lazy` for a library caller.
