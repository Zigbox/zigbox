# The 0.4.0 guide bugs (#110-#114): what was fixed and what was cut

*Decided 2026-11-12, by the implementer of the fix PR; the supervisor reviews.*

- **#110** `zbx stop` on a `start_failed` container: a container that never ran has pid 0.
  `Ref.is_gone` now says it is gone, and `report_stop` answers "never started, so there is
  nothing to stop", a no-op with exit 0, with no new code.
- **#111** `push --dry-run name@sha256:...`: `push/source.zig` now resolves an operand with `@` as
  a manifest digest through `reference.parse`, as `zbx sign` does. A digest is never a tag.
- **#113** `/etc/hostname`: a third generated file beside `hosts` and `resolv.conf`, holding the
  container's name and a newline, bound read-only. The plan grows by five steps
  (`child_steps_count` 37 to 42); the step totals in the diag goldens moved by that.
- **#114** `zbx help` lists `push`. E0307's fix text named `--memory` and friends, which a
  build step cannot be given; `diagnose.limit_without_cgroup` takes the asker (`run` or a build
  step), and a build step's text names the missing cgroup access instead of a flag. The
  explanation of E0307 got a sentence for it. No code was added or renumbered.
- **#112** `zbx store ls` overcounting hard-linked files. Supervisor's decision: the meaning of
  `bytes` in `zbx.store.ls/1` does not change (a consumer of a versioned schema must not see a
  silent change); a new member `size_unique` counts each distinct file once, however many names
  it has (objects are compared by id, as in `du`'s `stored_bytes`). The human SIZE column shows
  `size_unique`. It is computed at `ls` time by walking each root's tree (`usage.tree_stored`),
  so no root record changed and old stores need no migration; a tree that cannot be read gives
  `null` in JSON and `?` in text, rather than refusing the whole listing. Cost: `ls` now reads
  every root's trees. The schema's `size_unique` is required and may be null.

## Follow-up: /etc/hostname stays writable (demo-m3)

The first #113 fix bound /etc/hostname read-only like hosts and resolv.conf. SPEC 5 of demo-m3
(commit and diff) runs `/ops.sh`, which writes /etc/hostname, and got "Read-only file system".
Chosen, as in Docker: the hostname is the one generated file bound **writable**; its plan group
has no read-only remount (15 /etc steps, not 16; `child_steps_count` 41). What a program writes is
the container's own copy, in the staged file on the container's /dev, so it is lost with the
container. It is not in the upper layer, so `zbx commit` and `zbx diff` never show it (the mount
point is made in the net layer, as for hosts and resolv.conf). The simulator check and the plan
test assert that the hostname is bound and writable and the other two read-only.
