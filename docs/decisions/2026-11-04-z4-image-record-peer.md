# Z4: the image record of a tree, to and from a peer
*Decided 2026-11-04, by the Z4/Z6 slice.*

`store.export_image(store, memory, tree, out, failure)` gives the text of the newest image record whose tree is `tree`; `store.import_image(store, memory, text, tree, options, failure)` takes such a text from a peer for a tree that is whole here. **`options.expected_manifest` is required and the caller must take it from a trusted source** (for Zigcube, the digest-pinned image reference of the assignment), never from the peer: the peer's text decides neither the tree's image nor its name. Both are in `src/store/image_peer.zig`; its file comment lists the checks and their order.

- **Checks, in order:** size (`image_record_bytes_max`), parse (malformed, newer format), the record names `tree`, the record names `expected_manifest` (`wrong_manifest`; without it a hostile peer could name a well-known digest for its own tree, and `zbx run name@sha256:<digest>` would run it, or import one tree under invented manifests until `images_max` and gc's `blobs_live` fill), under `.keep` every tag reads as a reference, then, under the shared store lock, every tree and object below `tree` is present and sound (`walk.objects`, bounded by `entries_max` and `image_import_stack_max`, which is gc's stack: 32768 subtrees, so nothing a pull or gc accepts is refused for depth; the refusals `too_many_entries` and `stack_full` name the bound hit and its number). A refusal writes nothing. It carries a `Refusal` and raises one coded diagnostic, `ZBX-E0437`, through `diagnose.image_refused` (a busy store and a failing write keep their existing codes).
- **What is kept:** the settings, platform, config, layers and manifest of the record; the time is the local one (a peer's clock is not trusted); **tags are dropped by default** (`TagPolicy.drop`), because a tag a peer names would otherwise move a local reference. A caller that trusts the peer passes `.keep`.
- **Roots:** the image record keeps its tree for gc (`reach_images`); a root record (kind `import`, source `peer`) is written too if none exists, so `zbx store` lists the tree with a reason. The record is written first: a store failure between the two writes leaves a record without a root (the tree is kept; the same import again writes the root), never a root without a record. A root that exists but can not be read is a store failure; a damaged or newer one is left alone.
- **Race (documented, not fixed):** a pull and an import (or two of either) of one manifest at once can each read the old record under the shared lock, and the later write wins, so a tag of the other is lost until it is pulled or imported again. This is the race pull already has with pull. Serialising needs a per-record exclusive lock; the cost is a lock and a re-load for a loss of a tag only, so we left it. The tree stays rooted either way.
- **Idempotent:** the same record again changes nothing. The same manifest with another tree is `conflict` (the record is left as it was); a damaged or newer local record is `local_unusable`, never overwritten.
- **Found while doing it:** `images.parse` accepted a record with an empty platform (which `render` asserts against) and a repeated key standing in for a missing `.tree`. Both are `malformed` now; a text from a peer reaches no assertion.
- **`zbx run`:** `name@sha256:<manifest>` finds the record directly; `name:tag` goes through `zbx.lock`, so a caller that wants `run <tag>` passes `.keep` or writes the lock. Run in the VM, not here.

Fuzzed by `zig build fuzz -- peer` (property 5). Tests: `src/store/image_peer_tests.zig`.
