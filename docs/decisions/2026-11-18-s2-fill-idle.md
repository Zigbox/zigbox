# S2: the background fill waits for 2 s without a read, in ranges of at most 2 MiB

*Decided 2026-11-18, by the supervisor, on S2 slice 6 (the background fill).*

A remote lazy run (foreground or `-d`) fills the rest of its image in the background: the chunks
no read has asked for, in tree order, at most `lazy_fill_fetches_max` (2) requests at once, on
the resolver's two fill slots, which never take a reader's request.

- **`lazy_fill_idle_ms` = 2000** (internal, in `src/constants.zig`, comptime-asserted above 0 and
  below `lazy_read_deadline_ms`). The fill takes a request only once no read has asked a source
  for a chunk for 2 s (`Schedule.demand_ms`, `Schedule.fill_idle_at`). A start-up's reads come in
  bursts, and the fill must not take the registry's bandwidth between them. Each new read moves
  the time on again, so the fill pauses while reads keep coming.
- **`lazy_fill_range_bytes_max` = 2 MiB** (comptime-asserted a whole number of chunks, at least
  one, and at most `lazy_range_bytes_max`). Registry fetches go through one client in turn, so a
  read that arrives while fill requests are in flight waits behind them; the fill cannot be
  cancelled mid-request. Capping each fill request bounds that wait: the worst case is the two
  fill requests in flight, 4 MiB, about 100 ms at 40 MiB/s, well under
  `lazy_attempt_timeout_ms` and `lazy_read_deadline_ms`. The read's own request is the next one
  taken: a fill slot does not take another request until 2 s after that read
  (`resolver_test.zig`, "a read that arrives mid-fill is served before the next fill request",
  on a fake clock).
- **`lazy_progress_interval_ms` = 1000** (internal). While a lazy run is running, the thread that
  waits for the container (`session.wait`'s tick) writes the run record again when what the
  resolver reports changed, so `zbx ps` (which has no store access) shows `local_percent` rising
  to 100. On the same tick, once every object is local, the image's record is rewritten whole
  (version 3): `store ls` no longer shows it partial, `store verify` finds it whole, and a run
  without `--lazy` uses the farm. The check runs again when the container ends and in the
  run's teardown, for a fill that finished after the last tick.

`zbx store gc` during the fill needs no change: the partial image record roots its tree, the
objects present are kept, and the chunks of an object fetched in part stay while a root holds
the object (docs/demos/s2.md, slice 5b).
