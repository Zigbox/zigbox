# Push goes into M8

*Decided 2026-11-08, by the owner. Brief: `docs/briefs/M8-trust.md`, lane U.*

The owner's words: **"Unless there's a reason not to put push in 8, in it goes."**

The motivating user is Botpike (issue #60). Its catalogue images are built with `zbx build`, its
admission signs the **tree digest**, and Zigcube nodes pull by **reference and manifest digest**.
A built result has no manifest and no way into a registry, so no catalogue image can be admitted.
The issue asks for the smallest form, `zbx store export --oci <digest> DIR`, for another tool to
push, and says push itself is not needed. The owner chose to bring push in. Export is the same
packer writing to a directory instead of a registry, so lane U delivers both, and export comes
first (slice 10). Botpike is unblocked when slice 10 merges and does not wait for push.

What Botpike asked to rely on, and what the brief promises:
1. **Deterministic export:** yes, per layer-writer version. The same result gives the same
   manifest digest on any machine running the same writer version (Costs, below).
2. **Round trip:** yes, between stores in the same id mode. `zbx pull` of the manifest gives back
   the exported tree digest when both stores keep owners (the user has a subordinate range) or
   both squash them to 0 (`squash_owner`, no range). Zigcube nodes and the build runner must be
   in the same mode. The demo checks the round trip between two users on one host.
3. **`--output json`** with the manifest digest, config digest and total size: yes
   (`zbx.export/1` and `zbx.push/1`).

## Blockers

**No reason found that keeps push out of M8.** Three dependencies gate parts of lane U. None of
them stops the lane, and each has a cut:

1. **ECR push needs M6c**, which is not built. Its brief (`docs/briefs/M6c-ecr.md`) sits on an
   unmerged branch (`claude/gracious-heisenberg-thdbyp`). Slice 13 starts only after M6c has
   merged, and it is cuttable. If it is cut, push reaches Docker Hub, GHCR and any registry
   that takes a password, but not ECR.
2. **The image config and manifest writer needs a JSON writer.** Slice 2's `json.zig` is blocked
   on the owner naming the project domain, but the writer itself does not use the domain. The
   brief splits the writer out as slice 2's first part, mergeable on its own, and lane U starts
   after it. If the domain stays unnamed, lane U is not held up.
3. **A signature made on the build host does not satisfy `require_provenance` on the pulling
   host.** Signed provenance binds a `zbxResult`, but the pulling host runs a manifest. Slice 14
   (the derived binding) closes this gap and is cuttable. Without it, the pulling host can still
   require a signature (tree-only, or bound to the manifest with `zbx sign <ref>@sha256:…`), but
   not provenance. **This is the owner's call (question 1 below).**

## What moves into M8

- `zbx push <source> <destination>`: a built result, a pulled image or a tree with an image
  record, pushed to an OCI distribution v2 registry. The image is one gzip layer of the stored
  tree, an OCI config made from the result's config, and an OCI image manifest. A single
  platform, no index.
- **Determinism.** The same tree and config give the same layer, config and manifest bytes on
  every host, for a given layer-writer version. Pushing again is a no-op, since every blob
  already exists and the manifest is the same.
- The upload protocol: HEAD on blobs, a cross-repository mount, a chunked or monolithic upload, a
  manifest PUT, and a tag.
- Write-scoped token auth for Docker Hub and GHCR, and Basic-to-Bearer exchange for any registry
  that follows the token spec. ECR push uses M6c's credentials (cuttable).
- **Push credentials** come from the environment or a file, and are never printed, logged,
  written to the store, or sent to a host other than the registry's origin and its token realm.
- `zbx store export --oci <digest> DIR` writes the packed image as an OCI image layout
  (`oci-layout`, `index.json`, `blobs/sha256/`), which is issue #60's request.
- `zbx push --dry-run` packs the image and prints its digests without the network, so a user
  can see the manifest digest before pushing.
- The pushed manifest gets an image record. That lets `zbx sign <ref>@sha256:<manifest>` and
  `zbx run` find it on the host that pushed it.
- A test registry that accepts uploads, used in simulation and in the VM, plus a GHCR part on
  CI using the Actions token.
- `zigbox.push` in the library, for Zigcube's builders.

## What stays out, and why

- **Signatures in registries (cosign, OCI referrers, the 1.1 `subject` field).** M8's
  signatures are in-toto bundles keyed by tree, and `trust export` and `trust import` move them.
  Putting them in a registry adds an artifact format, the referrers API and a fallback tag
  scheme. It would also mean a second way to find a signature, which policy would have to
  reconcile with the first. Cost of leaving it out: a pulling host needs the bundle file next to
  the image reference, a step Botpike's deploy script already has a place for.
- **Multi-platform indexes.** zbx builds for the host's platform only (M7), so it has nothing to
  put in an index. A user who builds on two machines pushes two tags. Cost: no single
  multi-arch tag from zbx.
- **zstd layers.** zbx reads zstd but has no zstd writer, and some registries and older pullers
  still reject zstd. Gzip is the one format every puller reads. Cost: larger layers than zstd
  would give, and std gzip runs at about 48 MB/s at level 6 (measured).
- **Layer-preserving push** (pushing a pulled image's original layers). The store keeps
  flattened trees, not layers, so every push is one layer. A pulled image pushed elsewhere gets a
  new manifest digest. The blob cache's original layers are not reused, because doing so would
  need the original manifest, which the store does not keep. Cost: a re-push of `alpine` is a
  different digest from upstream's.
- **Docker API parity.** No `docker push` flag set, no `docker login` and no `config.json`
  credential store or credential helpers. `config.json` holds credentials in a form zbx would
  have to write back, which breaks "never written". Cost: users of `docker login` give zbx a
  token another way.
- **OCI export as a tar** (`docker save` style) and **OCI import** (`oci-layout` into the store).
  The directory layout is in M8 (slice 10). A tar of it is one `tar` command, and no user has
  asked for import.
- **Private-registry pull with the push credentials.** M6c covers ECR pull only. Pull from a
  password registry is the same credential path, though, so it is a natural follow-up. It stays
  out of M8 to keep the lane bounded. Cost: a user who pushes to a private GHCR repository
  cannot pull it back with zbx until then.
- **Deleting tags or manifests in the registry.** Not needed by the demo or by Botpike.

## Costs of putting it in

- **About four M7 slices** (lane U: L, L, M, S/M, M, plus part of slice 8). M8 is
  already the largest milestone. Lane U runs as a third worktree beside T and P, so the calendar
  cost is smaller than the work cost, but review load grows by the same amount.
- **A new security surface.** zbx will now hold write credentials. A credential leak (a log, a
  diagnostic, a redirect, a mirror) is worse than a leaked pull token. The brief takes the M6c
  rules and adds the realm rule. Slice 12 is reviewed for secrets as slice 1 is.
- **Digest stability is a promise.** Users will pin pushed digests. The layer bytes depend on
  std's gzip, so a Zig upgrade that changes its output changes every pushed digest. Golden
  bytes catch an unnoticed change. A noticed one is a new layer-writer version with a release
  note and `W0550` on the first push that differs from a pinned one (proposed).
- **The round trip is conditional.** A tree pulled back is the same tree only in a store in the
  same id mode (owners kept, or squashed by `squash_owner`). Tree-only signatures cross only between such hosts. The
  brief says so in `docs/demos/m8.md`, and the demo checks the case it can.
- **CI touches a real registry.** The GHCR part needs `packages: write` for the Actions token,
  and it leaves packages behind in the repository's namespace. The harness pushes to one fixed
  name with a run-specific tag. The owner decides whether CI may do this (question 3).

## Questions for the owner

1. Build slice 14 (the derived binding: pull keeps `Labels`, and a result-bound signature counts
   for a manifest whose config derives the same result), or accept that `require_provenance`
   does not hold for pushed images in M8?
2. Must every push name a tag, or may a push be by digest only (proposed: a tag is required)?
3. May CI push to `ghcr.io/zigbox/zigbox-demo` with the Actions token (`packages: write`), or does
   the demo stay on the loopback test registry only?
4. Export is in M8 with push (slice 10), although the words named push only. This is the
   brief's reading of "in it goes" for issue #60, so confirm it.
5. The proposed bounds and defaults in the brief (Lane U, "Proposed bounds"): gzip level 6,
   8 MiB chunks, the credential size bound, the realm rule.
