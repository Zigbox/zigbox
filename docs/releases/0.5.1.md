# Zigbox 0.5.1

0.5.1 is an honest public beta, for **Debian and Fedora only** (the apt and dnf repositories on
zigbox.org, x86_64 and aarch64). It adds the M9 builder additions and M10 devices and GPUs, both
marked **experimental**, and the release automation that builds, signs and publishes it.
Everything is in `v0.5.0..main`.

## Scope: Debian and Fedora

The packages are built, signed and checked for Debian (apt) and Fedora (dnf), and those are the
installs this beta supports. Other Linux distributions may run the static `zbx` from the release
tarballs, but they are not tested or supported in 0.5.1. The Mac build ships through the
Homebrew tap as before, outside this beta's support; M10 is refused there (E0229).

## Experimental: M9 and M10

Both ship as experimental ([decision](../decisions/2026-11-13-0.5.1-ships-m9-m10-experimental.md)):
their commands, flags, file formats and error codes may change in a later release without a
deprecation period.

### M9: the builder additions (slices 1 and 2 of 5)

M9 is **not demonstrated**: no `demo-m9` exists yet, and nothing of it has run in a VM. What is in
0.5.1 is the build file's new features ([brief](../briefs/M9-dockerfile-import.md), what was built
and cut in [docs/demos/m9.md](../demos/m9.md)):

- Input globs and `.exclude`, matched like `.dockerignore` (E0818 past `build_glob_matches_max`).
- Copy steps (`.copy`), which run no container: Docker's replacement rules, globs on trees,
  sources from the project or a `step:` output. Several matches to one `.to` without a trailing
  `/` are refused (E0803), and a project source with an empty or `.` part (`.`, `./a`, `a/`,
  `a//b`) is refused when the file is read (E0801).
- Root steps (`.output = .root`), `.user`, `.workdir` and `HOME`, `config.user` by name (E0817).
- `.caches` (cache mounts outside the step key; W0802; `zbx build --clear-caches`) and `.binds`
  from a `step:` output.
- `image.base = "step:<name>"`.
- A build file may now have up to 256 steps (was 64), 256 KiB long (was 64 KiB). See the known
  issue below.
- A build stopped by SIGINT or SIGTERM drops its store roots and exits with E0808.

Not in 0.5.1: **`zbx import`** (slice 3, the Dockerfile translator), the VM demo and corpus run
(slice 4) and the Mac (slice 5). Still refused with E0802: copy `.chown`/`.chmod`, copies and
binds from a locked image, binds from the project. A non-root `.user` with a writable `/out` is
refused.

### M10: devices and GPUs (4 of 4 slices)

`demo-m10` passed in an Ubuntu 24.04 VM with KVM ([run](https://github.com/Zigbox/zigbox/actions/runs/43468270943))
with a fake vendor device ([brief](../briefs/M10-gpu.md), cuts in [docs/demos/m10.md](../demos/m10.md)):

- `--device /dev/<path>`, with the caller's supplementary groups kept (E0225, W0209).
- `--device vendor/class=name` from CDI JSON specs in the standard directories (E0226, E0227,
  E0230, W0208).
- `--gpu all|dri` (E0228), and a GPU section in `zbx doctor`.

Why experimental: **no real GPU has run it.** The NVIDIA run on rented hardware was not made, and
the AMD run was cut; doctor's NVIDIA lines are covered by fixture goldens only. `--gpu dri` was
not run in CI (the guest has no render node). YAML CDI specs are refused (E0226, with the
`nvidia-ctk cdi generate --format=json` fix), and so are specs over 64 KiB. `zbx inspect` shows
the devices asked for, not what they resolved to.

## Release automation

A release is now one workflow run, draft first and publish last
([automation.md](automation.md), [packaging.md](packaging.md)): CI checks the release commit,
drafts the release, and after the owner's one approval signs the apt and rpm trees, writes the
Linux tarballs, a CycloneDX SBOM and `SHA256SUMS` (signed, `SHA256SUMS.asc`), builds and
notarizes the universal Mac zip on hosted runners, checks the draft against the pinned release
key ([zigbox-release-key.asc](zigbox-release-key.asc)), publishes, and updates the tap and the
site ([#121](https://github.com/Zigbox/zigbox/pull/121),
[#129](https://github.com/Zigbox/zigbox/pull/129),
[#131](https://github.com/Zigbox/zigbox/pull/131),
[#133](https://github.com/Zigbox/zigbox/pull/133)). The apt `Release` now carries `Valid-Until`
(21 days) and is re-signed weekly.

## Other changes

- The 0.4.0 guide bugs ([#117](https://github.com/Zigbox/zigbox/pull/117)): `zbx stop` on a
  container that never started exits 0 (#110); `zbx push --dry-run` takes `name@sha256:` (#111);
  `zbx store ls` adds `size_unique` and shows it as SIZE (#112); `/etc/hostname` is generated and
  writable (#113); `zbx help` lists `push` (#114).
- `zigbox.trust`, the pure trust surface for Zigcube, compiled for `wasm32-freestanding` as a gate
  ([#124](https://github.com/Zigbox/zigbox/pull/124)).
- A file whose filesystem leaves out statx fields is refused, not asserted on.
- CI: per-job timeouts ([#95](https://github.com/Zigbox/zigbox/pull/95)).

## Upgrading

0.5.1 reads every store, record and lock 0.5.0 wrote. Upgrade every `zbx` that shares a store
together; going back to 0.5.0 has the two issues below.

## Known issues

- **A downgrade to 0.5.0 reads the signatures of large builds as damaged.** 0.5.1 lets a build
  have up to 256 steps, so the provenance record of a build with more than 64 steps, and the
  signature record of its result once it is signed, can be larger than 0.5.0's bounds (a
  statement of 256 KiB, a signature record of about 2.7 MiB). The record format is unchanged, so
  0.5.0 does not say the record is newer: it says it is damaged. With 0.5.0 on such a store:
  - `zbx run` of that image under a trust policy, `zbx verify`, `zbx sign` and
    `zbx inspect --provenance` fail with **E0903** ("... is damaged: a line of it is not a signed
    statement"), and the run is refused;
  - `zbx trust prune` keeps the record and warns (W0902); `zbx trust export` reports it unusable,
    and `zbx trust import` refuses a bundle that large (E0909);
  - 0.5.0 cannot build that file at all (E0801, more than 64 steps).

  The records are not damaged, and 0.5.0 never deletes them. **Do not follow E0903's fix
  (`rm <path>`)** for such a record: that deletes a valid signature, and the image must then be
  signed again. Upgrade back to 0.5.1, which reads them. To stay on 0.5.0, keep builds of more
  than 64 steps in a store that only 0.5.1 uses.
- **A downgrade to 0.5.0 drops a container's devices silently.** Run records written with
  `--device` or `--gpu` are read by 0.5.0, which ignores the device list: `zbx restart` from 0.5.0
  starts the container with no devices and no diagnostic
  ([decision](../decisions/2026-11-13-m10-slice3-gpu-keywords.md)). Upgrade zbx everywhere before
  using `--device` or `--gpu`.
- Cache directories (`.caches`) are not locked between two `zbx build` processes on one project:
  run one build at a time per project.
- The guide ([docs/guide/](../guide/index.md)) was written for 0.4.0 and 0.5.0 and does not cover
  M9 or M10. [docs/guide/known-limits.md](../guide/known-limits.md) lists what a user will meet;
  the known issues of [0.5.0](0.5.0.md) and [0.4.0](0.4.0.md) are unchanged unless stated above.
