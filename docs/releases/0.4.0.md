# Zigbox 0.4.0 (M8)

M8 adds trust, Linux packages and push: Zigbox can sign what it builds, refuse to run what it cannot trace, ship as signed deb and rpm packages, and push images to a registry. Everything is in `v0.3.1..main`. The brief is [docs/briefs/M8-trust.md](../briefs/M8-trust.md); the slice-by-slice record is [docs/demos/m8.md](../demos/m8.md).

## Trust

- **Keys.** `zbx key new/list/show` make and describe Ed25519 signing keys in `$XDG_CONFIG_HOME/zbx/keys`. A secret is sealed with argon2id and XChaCha20-Poly1305, or kept in the clear with `--no-passphrase`. A forgotten passphrase is a lost key.
- **Signatures.** `zbx sign` signs a result's tree digest. The signature record survives `store rm`, `store gc` and a re-pull.
- **Provenance.** A build records an SLSA v1 statement (bases, steps, builder). `zbx inspect --provenance` shows it. A derived result is bound to its signer's entrypoint: the same tree with another entrypoint is refused under the first result's signature.
- **Policy.** `~/.config/zbx/policy.zon` can set `.require_signature` and `.require_provenance`. `zbx run` and `zbx build` refuse what fails with E0905 (no signature from a trusted key) or E0906 (no provenance), a tampered object with E0907, and a malformed policy with E0904 giving line and column. `zbx policy check` gives the same answer as `run`.
- **Verify and trust bundles.** `zbx verify` checks six links offline (no network at all). `zbx trust export` writes one in-toto envelope per line; `trust import` takes them on a second user; `trust prune` removes orphaned records (a dry run unless `--apply`).
- **Mac.** `key`, `sign`, `verify`, `trust` and `policy` are forwarded to the Linux VM (`docs/demos/m8.md`, slice 9). `push` is not forwarded: it is Linux-only in 0.4.0, and `store export --oci` is the way out of a Mac's store. Not run on a real Mac: the checks are listed there.

## Packages

- `zig build packages` writes `zigbox` deb and rpm packages and signed apt and dnf repository trees; `packages-check` reads them back. The runbook is `docs/releases/packaging.md`.
- `demo-m8-packages` installs the signed repositories on Ubuntu, Debian, Fedora and Rocky guests and runs the result.
- Not done in this repository: the deploy copy in `Zigbox/zigbox.github.io` that serves the release's `zigbox-repos.tar.gz` at `/apt` and `/rpm` (the session had no access to it).

## Push

- `zbx push` uploads an image to an OCI registry; `zbx push --dry-run` packs the image into the store (a pack record and the layer's blob, which a later push reuses), sends nothing, and prints one line: the manifest digest. `zbx store export --oci <image> <dir>` writes the layout to `<dir>`, which must be absent or empty; a trailing slash on `<dir>` is ignored. Credentials and write-scoped tokens work for Docker Hub and GHCR; ECR push is built on M6c (a real ECR push rides with M6c slice 3).
- The demo pushes to a `registry:2` run by `zbx` itself. A push to GHCR passed once in a `vm.yml` run; it is not in `demo-m8` (no secret in the workflow).

## Demo cuts

Decided 2026-11-11, see [docs/decisions/2026-11-11-m8-demo-cuts.md](../decisions/2026-11-11-m8-demo-cuts.md):

- **No `zbx rm` in M8.** The demo drops ended containers by hand. It belongs to a later milestone.
- **`demo-m8` retries the first push once**, and only after the exact E0503 stall. The cause is the VM's port forwarding through pasta, not the push. A workaround, not a fix: [Zigbox/zigbox#91](https://github.com/Zigbox/zigbox/issues/91) tracks it and the retry goes when it closes. Seeing the stall outside the VM would make #91 block this release.
- Also cut, in `docs/demos/m8.md`: offline `verify` link 5 reads `partial` (W0903) because a build's base trees are not kept in the store, and a passphrase file outside the shared home is not yet refused on the Mac.

## Fixes since 0.3.1

- `zbx run ""` is refused with E0006 instead of tripping an assertion ([PR #92](https://github.com/Zigbox/zigbox/pull/92)).
- `connect_wait` no longer hands a refused address's poll result to the descriptor that takes its slot, and a stall after connect is reported as `Stalled` with its own cause ([PR #90](https://github.com/Zigbox/zigbox/pull/90)).
- `policy check` agrees with `run` for a tree-only signature under `require_provenance` (PR #90).

## Upgrading

A store, lock and run record written by 0.3.1 are read as is; `demo-m8` checks this with the v0.3.1 binary. A policy refuses v0.3.1's images when it requires a signature, as they have none. Nothing is signed or pushed unless asked.

There is no way back. 0.4.0 writes image records at version 3 (0.3.1 writes 2) and run records at version 9 (0.3.1 writes 8); 0.3.1 reads a newer record as `Newer` and refuses it, so a store that 0.4.0 has written to cannot go back to 0.3.1. Keep a copy of the store if you may need to roll back.

Upgrade order matters between peers. A 0.3.1 peer refuses the images and records 0.4.0 exports, so upgrade the importing side (the machine that runs `store import` or pulls) before the exporting side.

## Known issues

- `exec` and build steps do not tamper-check the objects of a tree before they start; only `run` does ([docs/demos/m8.md](../demos/m8.md), the cut on `check_base`).
- A relative upload `Location` that a registry answers from another origin is resolved against the registry's origin, so the push fails at that piece; nothing is sent to the wrong host with credentials.
- A 401 or 403 from such a foreign upload host (an expired signed URL, say) is reported as the registry refusing, with the fix "check the user and the password file", even for an anonymous or ECR push.
- A cached layer whose blob is damaged to the same size is streamed without being hashed again; the registry refuses it as DIGEST_INVALID on every retry. `zbx store export --oci` hashes and drops it.
- The system policy's own owner and mode are checked, but those of `/etc/zbx` are not: a group- or world-writable `/etc/zbx` lets a user remove the policy file.
- For whoever builds the packages: `zig build packages-check` without flags rebuilds an unsigned tree over the signed one, and an owner build does not refuse a tree signed with the test key.
