# Zigbox 0.5.2

0.5.2 adds the four runtime requests Zigcube's C4 milestone (the service mesh) needs, ZB-5 to
ZB-8, and the rest of M9: `zbx import`, which translates a Dockerfile into a build file and never
executes it, with pinned fetches, output pins and the Mac front end. It stays a public beta for
**Debian and Fedora only** (the apt and dnf repositories on zigbox.org, x86_64 and aarch64), as
0.5.1 was. Everything is in `v0.5.1..main`.

`main` also holds the first four slices of S2 (lazy start), which ships as 0.6.0 on its own
([brief](../briefs/S2-lazy-start.md)). In 0.5.2 the S2 code is present but unreachable; see
[S2](#s2-lazy-start-present-but-unreachable) below.

## Scope: Debian and Fedora

Unchanged from [0.5.1](0.5.1.md): the packages are built, signed and checked for Debian (apt) and
Fedora (dnf), and those are the installs this beta supports. Other Linux distributions may run the
static `zbx` from the release tarballs, untested and unsupported. The Mac build ships through the
Homebrew tap, outside this beta's support.

## C4: Zigcube's requests (ZB-5 to ZB-8)

`demo-c4` passed in an Ubuntu 24.04 VM with KVM in `main`'s CI
([#157](https://github.com/Zigbox/zigbox/pull/157), [brief](../briefs/zb-c4.md), the contract
Zigcube codes against in [the decision](../decisions/2026-11-14-zigcube-c4-requests.md), cuts in
[docs/demos/c4.md](../demos/c4.md)):

- **ZB-5** `zigbox.container_socket`: an unconnected IPv4 TCP socket made in a running
  `--net none` container's network namespace by a forked helper and passed back with
  `SCM_RIGHTS`. `--net host` and `--net user` are refused (E0610); a failed step is E0611.
- **ZB-6** `zbx run --hosts-file PATH`: the file is bound read-only at `/etc/hosts`, with
  `--net none` only; a bad path is refused in the parent before the run (E0612).
- **ZB-7**: `zbx exec` into a `--net host` container runs in the host's network instead of
  panicking.
- **ZB-8**: a ZB-5 socket survives the adopting agent's SIGKILL and the supervisor's re-exec.

No IPv6, UDP or Unix sockets. `--hosts-file` is not recorded (see the known issues).

## M9: Dockerfile import (5 of 5 slices)

0.5.1 shipped M9's builder additions (slices 1 and 2) as experimental. 0.5.2 ships the rest
([brief](../briefs/M9-dockerfile-import.md), what was built and cut in
[docs/demos/m9.md](../demos/m9.md)). M9 stays **experimental**, as in 0.5.1
([decision](../decisions/2026-11-13-0.5.1-ships-m9-m10-experimental.md)): its commands, flags,
file formats and codes may change without a deprecation period.

- **`zbx import`** (slice 3, [#145](https://github.com/Zigbox/zigbox/pull/145) via
  [#149](https://github.com/Zigbox/zigbox/pull/149)): a Dockerfile and its `.dockerignore`
  become `zbx.build.zon`; every base is resolved through the lock first. `--target`, `--build-arg`,
  `--hermetic` (a step that needs the network or a cache mount is E0814), `-o`, and
  `--output json` with a schema. What does not carry over (`EXPOSE`, `HEALTHCHECK`, `# syntax`)
  becomes a label or is dropped, with W0811; a `RUN` gets the network only when it matches a
  fetching command (W0810). Refused: an `ARG` with no value (E0812), `FROM scratch` with steps,
  `ADD <url>` without `--checksum`, `ADD <git>`, binds from the context or an image, a
  `--platform` other than the host's (E0811), a blank `ENV` or `LABEL` name
  ([#171](https://github.com/Zigbox/zigbox/pull/171), E0810), and an existing output file
  (E0816).
- **Pinned fetches** (slice 3b): a copy source `.fetch = .{url, sha256}` (`ADD --checksum`),
  downloaded by the parent and stored by content; a hit never downloads (E0820, E0821).
- **Output pins and excludes** (slice 3c, [#163](https://github.com/Zigbox/zigbox/pull/163)):
  `zbx build --pin` records each step's output in `zbx.lock`; `--locked` refuses drift (E0822),
  and without it drift is a warning (W0803); `--pin --locked` is E0005. A lock with pins is
  version 2; a lock with none is written as version 1, byte for byte as before. A duplicate
  `.version` or `.step` in a lock is refused (E0518). `.output_exclude` per step, with the
  defaults `/var/log`, `/var/cache`, `/tmp` and `/var/lib/apt/lists`.
- **`.src = .{"."}`** copies the whole project, as Docker's `COPY .` does; 0.5.1 refused it
  ([decision](../decisions/2026-11-14-m9-copy-dot-is-whole-project.md)).
- **A copy's `.chown` and `.chmod`** run (0.5.1 refused them with E0802).
- **The Mac** (slice 5, [#166](https://github.com/Zigbox/zigbox/pull/166),
  [#168](https://github.com/Zigbox/zigbox/pull/168)): `import`, `build` and `inspect` are
  forwarded to the machine; a path outside the home is refused (E1013); a project whose lock pins
  `linux/amd64` is refused on a Mac without Rosetta (E1016). A step that ran under Rosetta no
  longer leaves `<home>/.cache/rosetta` in its output, and a cached output that holds it is
  rebuilt ([decision](../decisions/2026-11-15-rosetta-cache-not-in-output.md)).
- New bounds: a Dockerfile of 256 KiB, a `.dockerignore` of 64 KiB, 2048 instructions, 64 stages;
  a fetch of 1 GiB with 4 redirects; 32 output excludes and 256 pins.

`demo-m9` imports a Go project's Dockerfile, builds it to a golden digest in two VMs, checks
fetches, pins and drift, and runs 22 of the 33 import fixtures through the binary. Its status in
CI is given under the release gates below.

Still refused: copies and binds from a locked image, a bind from the project, an `.exclude` on a
copy from a step (E0802). `WORKDIR` does not create the directory. The Mac's native arm64 path is
shown only by a trivial build; M7's cross-machine arm64 digest stays open.

## S2: lazy start (present but unreachable)

S2 slices 1 to 4 ([#159](https://github.com/Zigbox/zigbox/pull/159),
[#161](https://github.com/Zigbox/zigbox/pull/161),
[#162](https://github.com/Zigbox/zigbox/pull/162),
[#165](https://github.com/Zigbox/zigbox/pull/165)) merged to `main` before this release was cut.
The owner chose to ship them dormant
([decision](../decisions/2026-11-16-0.5.2-s2-dormant.md)): the code is in the binary, and a user
cannot reach it.

- **`zbx push`, `push --dry-run` and `store export` write layer writer 1**, as 0.5.1 did: no lazy
  index and no `org.zigbox.lazy-index` annotation, so a tree gets the same digests from 0.5.1 and
  0.5.2. 0.5.2 still reads a writer-2 layer.
- **`zbx run --lazy` is refused** before anything runs: E0004, "lazy start arrives in 0.6.0".
  `zbx explain E1207` and `E1208` say so too.
- **The library packs writer 1 unless told otherwise.** `zigbox.push.Input.writer_version` is
  new; it defaults to `zigbox.push.release_writer_version` (1), so a library caller written for
  0.5.1 builds unchanged and gets 0.5.1's digests. `zigbox.push.pack.layer_writer_version` (2) is
  the newest writer the packer knows, not the default.

## Other changes

- The library's start path (the one Zigcube's agent links) goes through the same trust gate as
  `zbx run` ([#147](https://github.com/Zigbox/zigbox/pull/147)).
- `zigbox.exec` holds only the types and the calls on a started command (`Spec`, `Options`,
  `Handle`, `Exit`, `Error`, `Label`, `Phase`, `wait`, `signal`): its ungated `start` was still
  reachable as `zigbox.exec.start`. `zigbox.exec_start` is the gated one, as before. A caller of
  `zigbox.exec.start` moves to `zigbox.exec_start`, which takes a `GateWorkspace`.
- `dnf.write` refuses an rpm that is not one of the release's own; `packages-check` checks only
  the files it owns ([#148](https://github.com/Zigbox/zigbox/pull/148)).
- The diagnostic and text formatting is shared across call sites: the x86_64 `zbx` went from
  4,188,936 to 3,749,352 bytes, with no change to output
  ([#164](https://github.com/Zigbox/zigbox/pull/164),
  [decision](../decisions/2026-11-15-zbx-size-headroom.md)).
- `zig build fuzz-macos`, a gate that compiles the fuzzers for `aarch64-macos`
  ([#167](https://github.com/Zigbox/zigbox/pull/167)).
- New fuzzers: `dockerfile`, `dnf`, `lazy_index`, `chaining`, `lazy_resolver`, `fuse_request`,
  `fuse_serve` (56 in all).

## Upgrading

0.5.2 reads every store, record and lock 0.5.1 wrote. Upgrade every `zbx` that shares a store
together.

## Known issues

- **A lock with pins is version 2.** A `zbx` before 0.5.2 does not read it. Pin with
  `zbx build --pin` only once every `zbx` that builds the project is 0.5.2.
- **`--hosts-file` is not recorded.** The run record stays at version 10, so `zbx ps`, a bundle
  and an adopting agent do not know the path, and a container run again gets the file only when
  it is given `--hosts-file` again.
- Cache directories (`.caches`) are still not locked between two `zbx build` processes on one
  project: run one build at a time per project.
- The guide ([docs/guide/](../guide/index.md)) does not cover M9, M10 or C4.
  [docs/guide/known-limits.md](../guide/known-limits.md) lists what a user will meet; the known
  issues of [0.5.1](0.5.1.md) are unchanged unless stated above.
