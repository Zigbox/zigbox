# Zigbox 0.5.3

0.5.3 adds M2b, the workload knobs (`--ulimit`, `--shm-size`, `--sysctl`, `--require-host`, the
NUMA memory-policy calls, and a cgroup namespace with a read-only cgroup2 view), and M6d, pull from
a private Google Artifact Registry or gcr.io repository with the host's own Google credentials
([scope](../decisions/2026-11-16-0.5.3-scope.md)). **M6d is built, not demonstrated**: its live
demo moves to 0.6.0 ([decision](../decisions/2026-11-17-0.5.3-ships-m6d-undemonstrated.md)).
It stays a public beta for **Debian and Fedora only** (the apt and dnf repositories on zigbox.org,
x86_64 and aarch64), as 0.5.1 and 0.5.2 were. Everything is in `v0.5.2..main`.

`main` also holds S2 (lazy start) slice 5, which ships as 0.6.0. As in 0.5.2, the S2 code is
present but unreachable; see [S2](#s2-lazy-start-still-present-but-unreachable) below.

## Scope: Debian and Fedora

Unchanged from [0.5.1](0.5.1.md): the packages are built, signed and checked for Debian (apt) and
Fedora (dnf), and those are the installs this beta supports. Other Linux distributions may run the
static `zbx` from the release tarballs, untested and unsupported. The Mac build ships through the
Homebrew tap, outside this beta's support.

## M2b: workload knobs (items 1 to 5 and 7)

Three slices ([#178](https://github.com/Zigbox/zigbox/pull/178),
[#180](https://github.com/Zigbox/zigbox/pull/180), [#183](https://github.com/Zigbox/zigbox/pull/183);
[brief](../briefs/M2b-workload-knobs.md), [decision](../decisions/2026-11-16-m2b-workload-knobs.md),
the steps, cuts and failure modes in [docs/demos/m2b.md](../demos/m2b.md)). Every refusal is exit
125, before anything starts unless stated.

- **`--ulimit <name>=<soft>[:<hard>]`** (item 1) for `nofile`, `nproc`, `memlock` and `stack`,
  once per name; one value sets soft and hard, as in Docker. Set in the child before `execve`.
  Without it the container inherits zbx's limits, as before. A value above the invoking user's
  own hard limit is refused, never clamped (E0311, with the `limits.conf` and `LimitNOFILE=`
  fixes); a malformed one is E0310; a failure in the child is E0312.
- **`--shm-size <size>`** (item 2), in `--memory`'s syntax: `/dev/shm`'s size. The default stays
  64 MiB. At least one page, and at most `MemTotal` (E0313); larger than `--memory` is E0314,
  because `/dev/shm`'s pages are charged to the container's memory limit.
- **NUMA memory policy** (item 3): `mbind`, `set_mempolicy` and `set_mempolicy_home_node` join
  `get_mempolicy` in the default seccomp allowlist, without `CAP_SYS_NICE`, so
  `numactl --interleave=all` (MongoDB) and MySQL's `innodb_numa_interleave` work; under 0.5.2 they
  failed with `Operation not permitted`. The kernel still demands `CAP_SYS_NICE` for
  `MPOL_MF_MOVE_ALL`, which the container does not have. `move_pages` and `migrate_pages` stay
  denied.
- **`--sysctl <key>=<value>`** (item 4), namespaced keys only, from the reviewed allowlist
  `src/runtime/policy/sysctls.zon`: 28 keys, among them `kernel.shm*`, `kernel.msg*`,
  `kernel.sem`, `fs.mqueue.*` and 15 per-network-namespace `net.*` keys. At most 16 per run, values at most 256 bytes (E0315). Any other
  key is a host setting (E0316); a `net.*` key with `--net host` is E0317; a value the kernel
  refuses is E0318.
- **`--require-host <setting><op><value>`** (item 5) for `vm.max_map_count`, `fs.aio-max-nr`,
  `vm.overcommit_memory` and `transparent_hugepage`, once per setting. The parent checks before
  the scope, the namespaces or any process, and refuses a host that misses with the
  `sysctl -w` fix (E0319); an unknown setting or a malformed requirement is E0320; a setting the
  host does not expose or zbx cannot read is E0321. zbx never sets a host value. `zbx doctor`
  gains a `host-settings` line, information only; `zbx doctor --require-host …` fails that line
  on a miss, with the same code and fix.
- **The cgroup namespace and a read-only cgroup2 view** (item 7): every scoped run gets its own
  cgroup namespace rooted at its scope, and `/sys/fs/cgroup` is a read-only cgroup2 view of that
  scope alone, in every network mode. `/proc/self/cgroup` reads `0::/`, and Java, .NET and Node
  size their heaps from `--memory` (the before and after table is in the demo document). This is
  a change in what a container sees, with no flag; podman and Docker on cgroup v2 do the same. It
  also closes the exposure of the host's whole cgroup tree under `--net host`. A run with no
  scope (W0301) gets neither, as before. Failures are E0322 (the unshare) and E0323 (the mount).
  `zbx exec` joins the container's cgroup namespace.
- **The library:** `Spec` gains `rlimits`, `sysctls` and `host_requirements`, and `Limits` gains
  `shm_bytes`, all optional with defaults that keep 0.5.2's behaviour; new exports
  `host_settings_read`, `host_requirements_check`, `parse_host_requirement`, `HostSetting`,
  `HostValueSet`, `HostRequirement` and `HostSettings`. The library refuses with the same codes
  as the CLI.
- **New codes:** E0310 to E0323. New fuzzer: `host_settings`.

Recorded cuts and deviations (from [docs/demos/m2b.md](../demos/m2b.md)):

- The demo sets `net.core.somaxconn` to 8192, not the brief's 4096, which is the kernel's default
  ([decision](../decisions/2026-11-16-m2b-sysctl-keys.md)).
- The view sits on a small read-only tmpfs that covers `/sys/fs/cgroup`, not on a partial bind of
  the host's `/sys` ([decision](../decisions/2026-11-17-m2b-cgroup-cover.md)). Under `--net host`
  the host's cgroup2 stays listed in `mountinfo` beneath the cover; a tool that takes the first
  cgroup2 line for `/sys/fs/cgroup` reads the host's entry.
- The upgrade test reads a version-10 run record from a `--device` run, not a `--publish` one
  (0.5.2 writes version 9 for a `--publish` run).
- Not in M2b: adding capabilities (`--cap-add`) is parked, so `--device /dev/net/tun` is accepted
  but unusable (`TUNSETIFF` needs `CAP_NET_ADMIN`); io_uring, cpuset, `io.max`/`io.weight`,
  hugetlb and nested containers are non-goals; `/proc/sys` is readable inside (not masked);
  rlimits other than the four.

`demo-m2b` runs the six steps, the scripted agent, the `/dev/shm` OOM check, the view in every
network mode and the upgrade test from v0.5.2. Its status in CI is given under the release gates
below.

## M6d: private pull from Artifact Registry and gcr.io (built, not demonstrated)

Three slices ([#175](https://github.com/Zigbox/zigbox/pull/175),
[#179](https://github.com/Zigbox/zigbox/pull/179), [#181](https://github.com/Zigbox/zigbox/pull/181);
[brief](../briefs/M6d-gar.md), [decision](../decisions/2026-11-16-m6d-artifact-registry.md), the
demo and the owner's setup in [docs/demos/m6d.md](../demos/m6d.md)).

- **`zbx pull` and `zbx run` of a private image on `<region>-docker.pkg.dev`** and on `gcr.io`,
  `us.gcr.io`, `eu.gcr.io` and `asia.gcr.io`, with the Google credentials the host already has.
  zbx gets the access token itself, with no helper program. With
  `GOOGLE_APPLICATION_CREDENTIALS` naming an `external_account` file, it uses workload identity
  federation (the subject token from a file or a URL, with or without service-account
  impersonation) up front. Without it, the pull goes anonymously, so public images on those hosts
  pull as before, and the GCE metadata server is asked once, only when the registry refuses.
  When the variable names a file zbx does not use (a service-account key, gcloud's
  `authorized_user`, a workforce pool) or cannot read, the pull also goes anonymously first, as in
  0.5.2, and the file is refused (E0561, E0562, E0563 or E0571) only when the registry refuses;
  the metadata server is never asked in its place. The token is looked up for every pull, never
  cached.
- **Where each secret goes:** the subject token only to `sts.googleapis.com`, the federated token
  only to `iamcredentials.googleapis.com`, the access token only to the registry's same-host token
  realm (Basic `oauth2accesstoken:`), the realm's Bearer token only to the registry. None is
  written to output, JSON, `zbx.lock`, the store, a record, a bundle or the logs, and each buffer
  that held one is zeroed after use.
- **Refused, each with one coded line:** no credentials (E0560, naming the registry host), an
  unreadable credentials file (E0561), a service-account key file (E0562: zbx never reads a key,
  and the fix names workload identity federation), another unsupported file (E0563), an
  unreadable subject token (E0564), the exchange refused (E0565), impersonation refused (E0566),
  the access token refused (E0567), the repository not readable (E0568, naming it and
  `artifactregistry.repositories.downloadArtifacts`), a missing repository (E0569), a Google host
  zbx does not authenticate to (E0570), a workforce pool (E0571), and a credential service that
  failed (E0572).
- **The library** takes credentials from its caller, so Zigcube's agent pulls from Artifact
  Registry as it does from ECR: `pull.Request.google`, and the exports `google_credentials`,
  `google_credentials_resolve`, `GoogleEnv`, `GoogleSources`, `GoogleToken`, `GoogleWorkspace` and
  `GoogleTrace`. ECR's credential path is unchanged in behaviour; M6c and M6d share one cloud
  credential layer.
- A pull of a public image, its output and JSON, `zbx.lock` and the store formats do not change.
- New fuzzer: `parse_google`.

**Built, not demonstrated.** `demo-m6d` has never run against Google: it needs the owner's Google
project and the `ZBX_GAR_*` and `ZBX_GCR_REGISTRY` repository variables
([docs/demos/m6d.md](../demos/m6d.md)), which do not exist yet. In CI it prints
`demo-m6d: NOT RUN (...)` as a warning and the job stays green; that is not a passed demo. No pull
with credentials from a real Google registry has been made, and the GCE metadata-server check by
hand has not been run. What shows M6d works today is the simulation in `src/google/`, the unit
tests, the fuzzer and the goldens. The owner chose to ship it so and move the live demo to 0.6.0
([decision](../decisions/2026-11-17-0.5.3-ships-m6d-undemonstrated.md)).

Not in M6d: service-account key files (refused), `authorized_user` and other gcloud user
credentials, executable- and AWS-sourced external accounts, X.509 credential sources, workforce
pools, `~/.docker/config.json`, credential helpers, push to Artifact Registry, and the Mac (the
macOS `zbx` forwards `pull` to its guest, which has no Google credentials, so it is refused with
E0560).

## S2: lazy start (still present but unreachable)

S2 slice 5 ([#169](https://github.com/Zigbox/zigbox/pull/169): `zbx run --lazy` from a registry,
partial image records, a FUSE check in `zbx doctor`) merged to `main` after 0.5.2. S2 stays
dormant in 0.5.3, as the owner chose for 0.5.2
([decision](../decisions/2026-11-16-0.5.2-s2-dormant.md)); it ships as 0.6.0.

- `zbx run --lazy` is still refused before anything runs, with E0004; `zbx explain E1207` and
  `E1208` now say "this zbx (0.5.3)".
- `zbx push`, `push --dry-run`, `store export` and the library still write layer writer 1, with
  no lazy index: the same digests as 0.5.1 and 0.5.2.
- Nothing in 0.5.3 writes a partial image (record version 4), because only `--lazy` makes one.
  0.5.3 reads one.
- **`zbx doctor` shows a `fuse` line**, the one part of slice 5 a user meets: a warning (W1203)
  when FUSE cannot be mounted in a user namespace, saying `zbx run --lazy` cannot start. It never
  fails, and doctor's exit status does not change. See the known issues.

## Other changes

- `zigbox.codes.Code` is `enum(u16)`, not `enum(u8)`: the 255 tags were full. A library caller
  that stored a code's tag in a byte must widen it. Codes on the wire (`ZBX-E…` in text and JSON)
  do not change.
- `zbx doctor --output json` (`zbx.doctor/1`): the `checks` array gains `host-settings` (in the
  middle) and `fuse` (before `net`), and the document gains a top-level `host_settings` object.
- `zbx.run/1` and `zbx.ps/1` gain `ulimits`, `sysctls` and `shm_bytes` for a container that set
  them, without a version bump ([decision](../decisions/2026-11-17-m2b-json-additive.md)).
- New fuzzers: `host_settings` and `parse_google` (58 in all).
- **Fixed:** `zbx exec "" -- <command>` stopped with an internal error (B0001); it is now refused
  with E0402, as `zbx stop ""` is. The cli fuzzer found it.
- **Fixed:** pulling a reference whose tag is longer than 71 bytes (a valid tag may be up to 128),
  such as `zbx pull alpine:<a 72-byte tag>`, stopped with an internal error (B0001) before any
  request: the manifest name's buffer was sized for a digest, not a tag. 0.5.2 has the same bug.
  The tag is now sent whole. The reference fuzzer's extended run found it.

## Upgrading

0.5.3 reads every store, record and lock 0.5.2 wrote. Upgrade every `zbx` that shares a store
together, and Zigcube's agent with them.

- **Run records:** a run that sets `--ulimit`, `--shm-size` or `--sysctl` writes run record
  version 12; any other run writes the version 0.5.2 would have (9 or 10). A 0.5.2 `zbx` skips a
  version-12 record rather than misread it, so `zbx ps` and an adopting agent from 0.5.2 do not
  see that container.
- **JSON:** readers of `zbx.doctor/1` find a check by its `id`, never by its position, and accept
  `id` values they do not know; the new members of `zbx.run/1`, `zbx.ps/1` and `zbx.doctor/1` are
  additive.
- **Containers started by 0.5.2 keep running** and are listed and stopped by 0.5.3 (the
  upgrade test in `demo-m2b`). They have no cgroup namespace of their own, so `zbx exec` into one
  stays in zbx's, and it sees no cgroup view; restart the container to get one.

## Known issues

- **M6d is not demonstrated** (above). Artifact Registry's answer for a missing repository is
  unverified: E0568 or E0569 may name the wrong one of the two
  ([decision](../decisions/2026-11-16-m6d-missing-repo-unverified.md)).
- **`zbx doctor`'s `fuse` line talks about `zbx run --lazy`, which 0.5.3 refuses.** It is a
  warning only on a host without FUSE in a user namespace, and it can be ignored.
- **`zbx exec` does not get the container's `--ulimit`:** an exec runs its own plan and inherits
  the caller's limits.
- **`--ulimit nproc` counts the invoking user's own processes,** outside the container too,
  because the container's root is that user.
- **A sysctl written later inside the container wins:** zbx writes each `--sysctl` once, before
  the program starts, and does not re-check.
- **`pids.max` inside reads `--pids` plus one:** the scope also holds zbx's keeper process.
- **The cgroup view does not help a runtime that ignores it:** Go never reads `memory.max` (set
  `GOMEMLIMIT`), and Node's `availableParallelism()` counts CPUs, not the quota.
- **Smaller review findings left for 0.6.0:**
  - A Google token realm is checked for the registry's host but not its port.
  - E0567's fix ("get a new access token") fits a library caller; on the command line zbx gets the
    token itself.
  - `zbx run --lazy` (refused in 0.5.3) would keep the realm credential for the whole lazy run and
    not re-resolve an expired token; this is tracked for S2.
  - `zbx gc` under-reports the bytes it frees from a partly fetched object with more entries than
    its listing holds; removal is unaffected.
  - The top-level help line for `doctor` does not mention `--require-host`.
  - `--ulimit` refuses a value of more than 18 digits that a u64 holds.
- The known issues of [0.5.2](0.5.2.md) are unchanged: a lock with pins is version 2, which a
  `zbx` before 0.5.2 does not read; `--hosts-file` is not recorded; cache directories are not
  locked between two builds of one project; the guide ([docs/guide/](../guide/index.md)) does not
  cover M9, M10, C4, M2b or M6d.
