# M8 input: Linux packages for `zbx` (deb and rpm)

Owner, 2026-11-04: M8 ships `zbx` as a Debian package and an RPM, from a signed apt and dnf
repository. This is a list to fold into M8's brief when it is written, not a brief. It is one or
two slices. SPEC's M8 section does not list packaging yet; the live design doc should gain it
before the brief is written.

## Scope

- **One package, `zigbox`,** per architecture (`amd64`/`x86_64`, `arm64`/`aarch64`), holding the
  static ReleaseSafe `zbx` from `zig build release` (`/usr/bin/zbx`), its man page if one exists
  by then, and the licence. No maintainer scripts beyond what the formats require: `zbx` is one
  static file and an upgrade is a file swap (SPEC, "Upgrades are a file swap").
- **`zigbox` becomes the dev omnibus in Zigcube's C3** (owner, 2026-11-04): C3 adds `zcube`,
  `zcube-server` and `zcube-agent` to it and ships `zigcube-cli`, `zigcube-server` and
  `zigcube-agent` for one role per host (Zigcube `docs/briefs/c3-linux-packages.md`). So the
  package writer is a module Zigcube can import from the pinned `zigbox` package, not code inside
  `zbx`'s build step only.
- **Dependencies are soft.** `zbx` needs no shared library. The deb says
  `Recommends: uidmap, passt`; the rpm says `Recommends: shadow-utils, passt` (`newuidmap`,
  `newgidmap`, `pasta`). `zbx doctor` already reports what is missing; the package does not
  duplicate that.
- **Built in Zig, not with distro tooling.** A `zig build packages` step writes the `.deb` (an `ar`
  archive of `debian-binary`, `control.tar.gz`, `data.tar.gz`) and the `.rpm` (lead, signature
  header, header, gzip'd cpio `newc` payload) with the standard library, reproducibly (fixed
  mtimes, sorted entries, owner root). `dpkg-deb` and `rpm` are not build dependencies; STYLE.md
  allows no external programs the spec does not name.
- **Repositories:** a static apt repository (`dists/<suite>/Release`, `InRelease`, `Packages`) and
  a dnf repository (`repodata/repomd.xml` and its files), generated by the same step and published
  as static files. The release step writes them; it never runs `apt-ftparchive` or `createrepo`.
- **CI** builds the packages on every release PR and checks them with the distros' own tools in
  the VM (below). CI never signs or publishes.

## Cost and constraints

- **Signing** happens once per release on the owner's machine, as macOS signing does: the archive
  key never reaches CI or a session. apt needs an OpenPGP-signed `InRelease` (and `Release.gpg`);
  dnf needs a signed `repomd.xml` and, for `gpgcheck=1`, signed packages.
- `/etc/subuid` and `/etc/subgid` are left alone: the package does not add ranges for anyone.
  `zbx doctor` says what to add, as today.
- The VM harness boots Ubuntu 24.04, which covers the deb. The rpm needs a second guest image.

## Ask first (owner)

1. **The signing tool.** `gpg` on the owner's machine (an external program STYLE.md does not
   list), or a Zig-native OpenPGP signer (Ed25519, v4 signatures, a few hundred lines in `std`'s
   crypto). Default: a Zig-native signer reading a key file the owner keeps offline, so the
   release step needs nothing STYLE.md does not allow. M8 already brings Ed25519 keys and
   `zbx sign`; the archive signer should share that code, though the archive key stays separate
   from image-signing keys.
2. **Where the repository is hosted.** Default: a static site under the project's GitHub Pages
   (`/apt`, `/rpm`), with the public key beside it.
3. **Which distributions are supported and tested.** Default: deb for Ubuntu 24.04 and Debian 12;
   rpm for Fedora (current) and RHEL 9 compatibles (Rocky or Alma).

## Unknowns to settle first

1. Whether the VM harness can boot a Fedora or Rocky cloud image as easily as Ubuntu's (cloud-init,
   kernel features `zbx` needs). If not, the rpm demo installs and runs `zbx doctor` only.
2. Whether rpm's header signature can be made with the same Ed25519 key that dnf accepts on the
   oldest supported RHEL compatible (RHEL 9's rpm accepts EdDSA; check, do not assume).

## Demo

In the Ubuntu VM: add the repository and its key with the commands the README gives,
`apt install zigbox`, `zbx version` prints the release, `zbx run` of a pulled image works, then
`apt install` of a newer test build upgrades in place and `apt remove zigbox` leaves the store.
In the rpm VM: the same with `dnf install zigbox` and `dnf remove`. Both repositories verify
(`apt update` and `dnf makecache` report no signature warning).
