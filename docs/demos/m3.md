# M3 demo: the store

This document grows slice by slice. Slices 1 (trees and import) and 2 (materialize and run) are
written. The demo itself (`zig build demo-m3`) is slice 5; until then M3 is built in slices, not
demonstrated. `zig build demo-m3` already exists as the VM check of slice 2 (see below) and grows
into the full demo.

## Slice 1: trees and import

`zbx store import <dir>`, `ls`, `du` and `rm`, the canonical tree encoding, file objects and
their chunk lists, the store's layout, and the child that does the store's work. The layout is in
the module doc of `src/store/store.zig`; this section says what was decided where the brief left
room, what was cut, and what was checked.

### What is where

| Piece | File |

| the tree encoding and its decoder | `src/store/tree.zig` |
| attribute sections (canonical, sorted) | `src/store/xattrs.zig` |
| file objects, ids, chunk lists, atomic put | `src/store/object.zig` |

| the commands, their output | `src/store_commands.zig`, `src/schemas.zig` |
| diagnostics | `src/store/diagnose.zig`, codes `E0410`-`E0423`, `W0410`-`W0412` |

### Decisions the brief left open

- **The file-system interface is a second vtable, reached through the host.** The store needs
  about twenty operations the rest of the host does not (lstat with owner and links, xattrs,
  fchown, getdents of long directories, fsync, rename), and its simulator must be a whole file
  tree with faults and crashes, which the container simulator's small model is not. So
  `Host.filesystem()` hands out a `store/fs.zig` `Fs`; `host_real_fs.zig` is the syscalls (and
  is, like `host_real.zig`, a place that may name them) and `fs_sim.zig` is the model. Everything
  above it is written against `Fs` only. A host with no file system (`HostSim` without one) answers
  with a machine that is down: every call fails with `EIO`.
- **A chunk list is stored only for an object longer than one chunk.** The brief says every
  object records its chunk hashes beside it. For a file of at most one chunk the list is
  its content hash (and an empty file has none), so the file is stored without a second file;
  `object.chunk_hashes` returns the list either way. Alpine's rootfs has 87 files and two chunk
  lists. This halves the inodes of a store of small files, and `chunks(object_id)` does not
  change for Zigcube.
- **The imported directory's own mode, owner and attributes are in the digest.** The imported
  directory becomes the container's `/`, so `chmod 700 alpine` gives another digest and
  `chmod 755` gives the first one back. Every directory below the root has its metadata in its
  entry in the parent; the root has no parent entry, so each tree object ends in an `own`
  section (`mode:u16 uid:u32 gid:u32 xattrs`). It holds the root's values in the root tree and
  zeros and no attributes in every other tree, so a subtree is the same object wherever it sits.
  The decoder exposes it as `Decoder.own` once the entries are read, and materialize (slice 2)
  gives `/` that mode, owner and those attributes. The root's metadata is read after its
  contents, at the end of the walk.
- **One root record per tree.** `roots/<digest>` is overwritten by a later import of the same
  tree, so `ls` shows the latest source and time. `files` and `bytes` (logical totals) are in the
  record so `ls` needs no walk.
- **The fixed mtime is 2000-01-01T00:00:00Z** (`constants.store_mtime_seconds`, 946684800), on
  every object and every other file the store writes. Zero was avoided: some tools take the
  epoch to mean "no time".
- **Schemas are named `store-import`, `store-ls`, `store-du`, `store-rm`** (`zbx schema
  store-ls`): `schema` takes one operand.
- **`ls` and `du` and `rm` run in the namespace child too**, but only `import` shows the one-id
  warning (W0201): the other commands do not depend on the map.
- **Extra codes**: `E0421` (no data directory), `E0422` (a tree reached from another is missing
  or damaged), `E0423` (cannot read the store). `E0410` is "no tree with that digest", the code
  for `Spec.image` when the store lacks the digest.

### Ownership, as built

The child maps ids as `zbx run --rootfs` does. With the full map the user is 0 and the subuid
range is 1 to 65536, so a file owned by host uid 100001 is recorded as 2, and `chown` of an
object to 2 inside the child makes the file really owned by 100001. With the one-id map (W0201)
every owner is recorded as 0, whatever the kernel reports (it reports 65534 for ids the map
lacks). A file owned by a host id that is neither the user nor in the range also reads as 65534.
It is recorded as that, and not silently: one warning per import (`W0412`) gives the number of
entries whose owner and whose group showed 65534 and names the first path, and the import JSON
has `"unmapped_owners"` and `"unmapped_groups"` (and the schema). Known limit: 65534 is also a
legal container id and the kernel gives the child no way to tell the two apart, so a file that
really is owned by 65534 is counted too; the digest holds 65534 either way. A one-id import
squashes every owner to 0 by request (W0201) and counts nothing.

`security.capability` is recorded as the child reads it, which in the user's own namespace is
the version 2 form; written back inside the namespace the kernel stores it as a version 3
capability whose root id is the namespace's root, which is what "namespaced v3" means on disk.
Checked for real: a capability set inside `unshare -U -r` was imported, and the object carries
`0100000300000200...` plus the user's uid in the root id field.

### What is cut

- Other xattr namespaces (`trusted.*`, `security.selinux`, ACLs) are skipped with `W0411`, as the
  brief says. So are an attribute with a name over 255 bytes or a value over 4096, and any
  attribute past the sixteenth on a file.
- Devices, FIFOs and sockets are skipped with `W0410`.
- Hardlinks become separate entries; two names for one inode are one object if the bytes and
  metadata agree.
- A file past 4 GiB (4096 chunks), a directory past 16384 entries, nesting past 64 levels, a
  name past 255 bytes, a symlink target past 4095 bytes, and a walk that needs more than 16 MiB
  of working memory are refused with `E0415` and the path. No tree is cut silently.
- `tmp/` files a killed process leaves are not removed until gc (slice 4).

### What was checked, and against what

- Unit tests for every piece, in `zig build test`. The ones that carry the claims:
  - `import_tests.zig`: the digest does not change with the creation order, the listing order
    (the simulator shuffles every listing) or any time; everything that is content changes it;
    modes, owners, attributes and symlinks round-trip through objects and trees; a copy with one
    more file adds one object; devices and attributes are skipped as stated; the depth limit is
    exact; a disk that fills is `E0416` and the same import finishes later.
  - the crash test, this milestone's VOPR: for every write point of an import, once as a failing
    call and once as a crash (files torn, every call failing until a restart), the store holds
    only whole objects, chunk lists, trees and roots (`test_support.check_whole`), and the same
    import then gives the clean run's digest.
  - `store_commands_tests.zig` runs the commands through the command line in the simulator, in
    text and in JSON, and checks the output against the schemas' keys.
  - `diag_golden.zig` has a case for every new code; `site/errors/` has their pages.
- Fuzzers (10,000 iterations, seed 1): `tree` (the decoder never reads outside its input, and
  for any bytes the decoder accepts, encoding what it decoded gives the same bytes: one encoding
  per directory) and `store` (random trees, imported under interrupts and short I/O, an error at
  a random write point, a crash at a random write point, a disk that is too small, sometimes
  into a store that already has objects; always whole afterwards, and the repeat gives the
  digest of an import into a clean file system). Both were checked by mutation: the store fuzzer
  fails when an `fsync` is removed, the tree fuzzer when the order check is.
- In the build container (root, kernel 6.18, no KVM), against the pinned Alpine 3.20.10
  minirootfs, with the release binary: see "Real imports" below.

### Real imports

The pinned minirootfs (`src/testing/vm/alpine.zon`, SHA-256 checked) unpacked as an ordinary user
with a subuid range, as the VM demo does, and imported by that user (full map):

```
b3:14490ed05d0fa4ac3b0ccbba74927c7ebe08bff224c8ee5affb570da601353be
  87 files, 97 directories (the root included), 334 symlinks, 7,802,737 bytes; 80 objects (seven
  files repeat); store du: 7.5 MiB, 53 trees
```

The same tree after `touch -h -d 2031-05-05` on every entry: the same digest, 0 new objects.
After `chmod 700 alpine` (the root directory only): another digest, `b3:a5415b9c...`; after
`chmod 755 alpine`: the first digest again. A file owned by host uid 4242 (no mapping): exit 0,
one W0412 naming `alpine2/x4242`, and `"unmapped_owners":1,"unmapped_groups":1` in the JSON.
With one more 10,000,000-byte file: a new digest, 1 new object, `store du` 17.0 MiB (+10 MB and a
few trees). The mapping does not change a digest when every owner is the importing user: the same
files extracted with `tar -xp` and imported by the user (full map), and a copy of them chowned to
root and imported by root (no subuid range here, so the one-id map and W0201), both give
`b3:5b340463c9e6605c8a4771f525e4a13174bddc504e982112707e9cd785d31306`. A file owned by a subuid
is recorded under the full map as its container id (host 100001 as 2, with its mode and attribute
on the object on disk) and squashed to 0 under the one-id map, so the two maps give different
digests for such a tree, as the brief says they should.

### By hand

```sh
zbx store import ./alpine          # prints b3:...
zbx store import ./alpine-copy     # same digest if the content is the same
zbx store ls                       # roots, newest first
zbx store du                       # the store's bytes, objects and trees
zbx store du b3:14490ed05d0f       # one tree: logical, stored and shared size
zbx store rm b3:14490ed05d0f       # drop the root; the data stays until gc
zbx --output json store import ./alpine
```

### Failure modes (slice 1)

| What | How it shows | Recovery |
| --- | --- | --- |
| the disk fills during an import | `E0416`, says how many objects were kept | free space, run the same command; stored objects are skipped |
| the store directory is read-only or unwritable | `E0417` naming the call | fix permissions or `XDG_DATA_HOME` |
| a file changes while it is imported | `E0418` naming the file | stop the writer or import a copy |
| a limit of the import is passed | `E0415` naming the path | split the tree |
| the source is missing, a file, a symlink or unreadable | `E0414` naming the path | check the path |
| `store.zon` is newer or unreadable | `E0413` | use the zbx that wrote it, or set the store aside |
| no `HOME` or `XDG_DATA_HOME` | `E0421` | set one |
| the namespace cannot be set up | `E0419` with the helper's output | `zbx doctor` |
| a tree below another is missing or damaged | `E0422` naming it (`du`) | import again; `verify` arrives in slice 4 |
| a killed import | files in `tmp/`, nothing under an id | run it again; gc removes `tmp/` (slice 4) |

## Slice 2: materialize and run

`zbx run <digest> -- <command>`, `Spec.image` in the library, the overlay in the setup plan, the
materialized cache, run records version 4. Where the brief left room, what was cut, what was
checked, and what ran where.

### What is where

| Piece | File |
| --- | --- |
| the hardlink farm and its cache | `src/store/materialize.zig` |
| removing a tree (an upper layer, a half-built farm) | `src/store/remove.zig` |
| link, symlink, path attributes in the file-system interface | `src/store/fs.zig`, `host_real_fs.zig`, `fs_sim.zig` |
| resolving the digest, the store's child, the container's directory | `src/runtime/image.zig` |
| the overlay in the plan (`mount_overlay`, `Plan.overlay`) | `src/runtime/plan.zig`, `child.zig`, `host.zig` (`MountKind.overlay`) |
| `Spec.image`, `StartOptions.image_workspace`, pruning a record's layers | `src/runtime/spec.zig`, `run.zig` |
| run record version 4 (`tree`, `upper`) | `src/runtime/records.zig` |
| a diagnostic carried through a pipe | `Diag.encode`, `Diag.decode` in `src/diag/diag.zig` |
| diagnostics | `E0424`, `E0425`, `W0413`; `E0701` can now end a run |

### How a run by digest goes

1. The digest or prefix (12 or more hex digits, with or without `b3:`) is resolved against the
   user's store. No store, no such tree: `E0410`. Ambiguous prefix: `E0411`. Not a digest:
   `E0412`. These end the run before anything is created, exit 125, and are what Zigcube's
   `start_failed` for an unknown digest carries (`ZBX-E0410`).
2. In the store's child (the user's namespace, the id map the container will have) the tree is
   materialized into `<store>/cache/<64 hex>` if it is not there, and the container's directory
   `$XDG_STATE_HOME/zbx/containers/<name>/` is made with `merged` and either `upper` and `work`
   or, for `--read-only`, `empty`. A directory of the same name from an earlier run is removed
   first. The child's failure comes back through a pipe as the child's own diagnostic.
3. The plan mounts the overlay where a plain rootfs would be bound: `mount_overlay` replaces
   `bind_rootfs` (the same number of steps), inside the container's user and mount namespaces,
   with `userxattr,lowerdir=<farm>,upperdir=<upper>,workdir=<work>`. The rest of the setup is the
   same code as for `--rootfs`, on the merged directory.

### The farm

A directory per tree under the store's `cache/`: every directory is real, with the mode, owner
and attributes the tree records; every file is a hard link to its object (no space, and the
object's real owner, mode and attributes); every symlink is made again with its owner. The root
gets the root's own mode, owner and attributes (`Decoder.own`), and every directory the fixed
mtime. Directories get their attributes after their entries, so a directory without write
permission is still filled. It is built in `tmp/` and renamed into `cache/`, so a crash leaves
nothing under a digest (checked at every write point, as a failure and as a crash), and two
builds at once end with one farm. It must be built inside the user's namespace: a hard link to a
file of a subordinate id and `chown` to a container id need it.

### Decisions the brief left open

- **Read-only by mode** is not done by changing modes (the container must see the recorded
  ones). The farm is the overlay's lower layer, which a container cannot write; a write goes to the
  upper layer by copy-up. The plan test says it: the store's path appears in exactly one place in
  a plan, the `lowerdir=` of the overlay, and nothing is bound, remounted or created there.
- **`--read-only` with a digest** is an overlay with no upper layer. The kernel wants two lower
  layers then, so the second is an empty directory (`containers/<name>/empty`). `/tmp` and `/run`
  are the usual tmpfs; a tree without `/proc`, `/dev`, `/tmp` or `/run` fails at the step that
  needs it (`E0205` or `E0209`, naming the tree), because nothing can make them in a read-only
  root.
- **The upper layer's root** has the tree root's mode, owner and attributes, because with an upper
  layer the overlay shows the upper's root, not the lower's. Checked in the VM: a tree imported
  with a root of mode 711 is 711 in the container.
- **The upper of an ended container is kept while its record is.** When `prune` deletes a record
  (the newest 32 are kept) its container's directory is removed, in the store's child, because it
  holds files of subordinate ids. A directory that cannot be removed is `W0413`, never a failed
  run. A new run with the name of an old one removes the old directory first.
- **Paths with a comma, colon or backslash** can not be given to the overlay (the kernel splits
  the mount data at them): `E0425` names the path. Escaping is a cut.
- **Hardlink limit**: ext4 allows about 65,000 names per inode; an object under more names than
  that makes the build fail with `E0424` and the half farm is removed.
- **`E0701`** (no state directory) can end a run now, since the layers live there.
- **`can_end_run`** is true for `E0410` to `E0413`, `E0416` to `E0417`, `E0419`, `E0421` to
  `E0425` and `E0701`, and false for `E0414` (import), `E0418`, `E0420` and the warnings.
- **Record bytes** went from 32 KiB to 40 KiB: the two new fields are at their bounds in the
  comptime proof of the record's size.
- **The run fuzzer** has image scenarios (a fifth of the good roots): the plan is the overlay plan,
  `mount_overlay` is a step like any other that gets a failure injected (`E0425`), the helpers run
  twice (the store's child maps ids too), and a refused helper in the child is `E0419`.

### Cuts

- Copying the tree instead of an overlay when the kernel has no unprivileged overlayfs: a coded
  refusal (`E0425`, naming `zbx doctor`) instead.
- A tree imported under the full id map can not be run under the one-id map (its first `chown`
  fails with `EINVAL`, reported as `E0417`).
- An upper layer nested deeper than 64 directories is not removed (`W0413` says so); the next run
  with the name tries again.
- The library's `commit`, `gc` and `verify` are later slices.

### What was checked, and against what

- Unit tests: `store/materialize.zig` (the farm's shape, the root, built once, a failure or a
  crash at every write point, the hardlink limit, a missing object), `store/remove.zig`,
  `runtime/image_tests.zig` (the whole run against the simulator: the layers, the overlay in the
  child's mount table, the record, the read-only form, E0410, E0412, E0425, a second run with the
  name, removal), `runtime/plan.zig` (the overlay replaces the bind; a read-only plan has no
  upper; **no step ever mounts a path of the store writable, or makes anything in it**),
  `runtime/records.zig` (version 4, and a version 3 record reads), `diag/diag.zig` (a diagnostic
  crosses a pipe), goldens and pages for `E0424`, `E0425` and `W0413`.
- Fuzzers at 10,000 iterations: `run` (with image scenarios), `record`, `cli`, `tree`, `store`.
- In the build container, as an ordinary user with a subuid range (kernel 6.18, which allows
  unprivileged overlayfs): `zbx run <prefix>` of the Alpine rootfs, with a script that writes,
  changes modes, changes owners and deletes across the tree. The store's listing (type, mode,
  owner, size, link count, path) and the sum of every file, taken as root before and after, are
  identical; the container's changes are in `containers/<name>/upper`. Thirty-six runs prune the
  oldest records and remove their layers (files of subordinate ids) down to 32 directories.
- In the VM (Ubuntu 24.04 cloud image, software emulation): `zig build demo-m3 -Daccel=tcg`,
  the slice's five steps (below), and `demo-m1`, `demo-m2` unchanged and passing.

### The VM check (`zig build demo-m3`, slice 2 part)

| Step | Command | Passes if |
| --- | --- | --- |
| 1 | `zbx store import ~/alpine` | the digest alone on stdout, exit 0 |
| 2 | `zbx run <12 hex> --name prime1 -- true`, then the listing and sums of the store; `zbx run <12 hex> --name scribble1 -- sh /scribble.sh`; the listing and sums again | the script prints `scribbled`; the two snapshots are identical (`cmp`); the container's upper holds at least 20 entries; the run record names the tree and an `/upper` path |
| 3 | `--read-only` with the digest: `touch /x`, then `touch /tmp/x` | the first fails with `Read-only file system`; the second prints `tmp-ok` |
| 4 | the rootfs with a root directory of mode 711, imported, run: `stat -c "%a %u %g" /` | `711 0 0` |
| 5 | an unknown digest; the name `scribble1` again | `ZBX-E0410` and exit 125 with nothing on stdout; `/left` from the first run is gone |

The guest has no `b3sum`; the sums are `sha256sum` and the listing carries modes, owners and link
counts, which is the brief's "unchanged" with a tool the image has. `zbx store verify` (slice 4)
will be the BLAKE3 check.

### Failure modes (slice 2)

| What | How it shows | Recovery |
| --- | --- | --- |
| no such tree, an ambiguous prefix, not a digest | `E0410`, `E0411`, `E0412`; exit 125 | `zbx store ls` |

| a container's layers can not be removed | `W0413` naming the path | remove them by hand from the user's namespace |
