# M3 demo: the store

This document grew slice by slice and is finished by slice 5 (the last section, "Slice 5: the
demo"), which says how to run the demo, what it asserts, how to do each spec step by hand, what
was cut, and how the store fails. The earlier sections say how each part was built. Until the
`demo-m3` job is green in CI, M3 is built, not demonstrated. The VM tables of slices 2 to 4 name
the checks of those slices by the numbers they had then; the demo now names them (`CHECK ...`),
and the spec's steps `SPEC 1` to `SPEC 5`.

### The store lock

One file, `<store>/lock`, and `flock` on it (`src/store/lock.zig`; raw `flock(2)`, no library).
An import that finds an object already in the store reuses it; a gc that moves that object to
the trash in the same moment would leave the new tree naming an object that is not there. So:

- **Shared**, for the whole operation, by everything that may reuse what is in the store or put
  in what nothing reaches yet: `import` (with its root record), `commit` (from the walk to the
  recording of its root, held by the command), the build of a materialized directory (`run
  <digest>`), `put_chunk` and its `finish`, and `store rm`.
- **Exclusive** by `gc --confirm` (the whole apply, which makes its plan again under the lock,
  so a confirmed plan is compared with a store that nothing is writing) and by `restore`.
- **Nothing** by a plan (`gc` without `--confirm`), `gc --trash`, `verify`, `ls`, `du`, `diff`.
  A plan made while an import is running may include objects the import is about to reuse; the
  confirm is what takes the lock, and its fresh plan is the one that counts.

The wait is bounded. A command tries without blocking (`LOCK_NB`) every 20 ms for 10 seconds
(`constants.store_lock_wait_ms`; a library caller sets `Store.lock_wait_ms`), then stops with
`E0436` and changes nothing. An exclusive holder writes `<pid> <command>` into the file, so the
message says "'zbx store gc' (process 4242) holds the store lock"; shared holders write nothing,
so a gc kept waiting by importers says that other commands are writing. The kernel frees the
lock when its process ends, whatever the way, so a killed zbx leaves nothing behind.

Holds nest inside one `Store` value (a command that needs the lock across several library calls
takes it first and the calls only count); a shared hold cannot be raised to an exclusive one.
**A library caller that writes chunks and then records the object in a tree must hold the lock
itself (`lock.hold(&store, .shared, ...)`) from the first chunk to the record**; `put_chunk` holds
it for one call only, and a finished object nothing reaches yet is what a gc moves.

Checked: the simulator models `flock` per open descriptor (a crash frees them) and a test makes
the race happen (`lock_tests.zig`: a second program plans and confirms a gc just before an
import writes its root record; with the lock the confirm is refused and verify is clean, and the
test fails when the simulator's lock is made to never conflict); a real kernel with two
processes (a forked child takes the lock exclusively, the parent is refused with the child's
pid and command, then gets it when the child ends); the command line (`gc --confirm` and
`restore` against a writer: `E0436`, exit 1, ten seconds of simulated clock, nothing printed);
`put_chunk` against a gc; and VM step 9 with `flock(1)` as the writer.

Not covered: the *list of live containers* a gc is given is read before the lock is taken (a
container that starts between is not seen; it holds its tree through the shared lock of `run`
only while the directory is built). A bigger lock, over the run itself, would stop gc for as
long as a container lives, which is not what the lock is for.

### Decisions the brief left open

- **The file-system interface is a second vtable, reached through the host.** The store needs
  about twenty operations the rest of the host does not (lstat with owner and links, xattrs,
  fchown, getdents of long directories, fsync, rename), and its simulator must be a whole file
  tree with faults and crashes, which the container simulator's small model is not. So
  `Host.filesystem()` hands out a `store/fs.zig` `Fs`; `host_real_fs.zig` is the syscalls (and
  is, like `host_real.zig`, a place that may name them) and `fs_sim.zig` is the model. Everything
  above it is written against `Fs` only. A host with no file system (`HostSim` without one) answers
  with a machine that is down: every call fails with `EIO`.
- **A chunk list is stored only for an object longer than one chunk.** The brief says every
  object records its chunk hashes beside it. For a file of at most one chunk the list is
  its content hash (and an empty file has none), so the file is stored without a second file;
  `object.chunk_hashes` returns the list either way. Alpine's rootfs has 87 files and two chunk
  lists. This halves the inodes of a store of small files, and `chunks(object_id)` does not
  change for Zigcube.
- **The imported directory's own mode, owner and attributes are in the digest.** The imported
  directory becomes the container's `/`, so `chmod 700 alpine` gives another digest and
  `chmod 755` gives the first one back. Every directory below the root has its metadata in its
  entry in the parent; the root has no parent entry, so each tree object ends in an `own`
  section (`mode:u16 uid:u32 gid:u32 xattrs`). It holds the root's values in the root tree and
  zeros and no attributes in every other tree, so a subtree is the same object wherever it sits.
  The decoder exposes it as `Decoder.own` once the entries are read, and materialize (slice 2)
  gives `/` that mode, owner and those attributes. The root's metadata is read after its
  contents, at the end of the walk.
- **One root record per tree.** `roots/<digest>` is overwritten by a later import of the same
  tree, so `ls` shows the latest source and time. `files` and `bytes` (logical totals) are in the
  record so `ls` needs no walk.
- **The fixed mtime is 2000-01-01T00:00:00Z** (`constants.store_mtime_seconds`, 946684800), on
  every object and every other file the store writes. Zero was avoided: some tools take the
  epoch to mean "no time".
- **Schemas are named `store-import`, `store-ls`, `store-du`, `store-rm`** (`zbx schema
  store-ls`): `schema` takes one operand.
- **`ls` and `du` and `rm` run in the namespace child too**, but only `import` shows the one-id
  warning (W0201): the other commands do not depend on the map.
- **Extra codes**: `E0421` (no data directory), `E0422` (a tree reached from another is missing
  or damaged), `E0423` (cannot read the store). `E0410` is "no tree with that digest", the code
  for `Spec.image` when the store lacks the digest.

### Ownership, as built

The child maps ids as `zbx run --rootfs` does. With the full map the user is 0 and the subuid
range is 1 to 65536, so a file owned by host uid 100001 is recorded as 2, and `chown` of an
object to 2 inside the child makes the file really owned by 100001. With the one-id map (W0201)
every owner is recorded as 0, whatever the kernel reports (it reports 65534 for ids the map
lacks). A file owned by a host id that is neither the user nor in the range also reads as 65534.
It is recorded as that, and not silently: one warning per import (`W0412`) gives the number of
entries whose owner and whose group showed 65534 and names the first path, and the import JSON
has `"unmapped_owners"` and `"unmapped_groups"` (and the schema). Known limit: 65534 is also a
legal container id and the kernel gives the child no way to tell the two apart, so a file that
really is owned by 65534 is counted too; the digest holds 65534 either way. A one-id import
squashes every owner to 0 by request (W0201) and counts nothing.

`security.capability` is recorded as the child reads it, which in the user's own namespace is
the version 2 form; written back inside the namespace the kernel stores it as a version 3
capability whose root id is the namespace's root, which is what "namespaced v3" means on disk.
Checked for real: a capability set inside `unshare -U -r` was imported, and the object carries
`0100000300000200...` plus the user's uid in the root id field.

### What is cut

- Other xattr namespaces (`trusted.*`, `security.selinux`, ACLs) are skipped with `W0411`, as the
  brief says. So are an attribute with a name over 255 bytes or a value over 4096, and any
  attribute past the sixteenth on a file.
- Devices, FIFOs and sockets are skipped with `W0410`.
- Hardlinks become separate entries; two names for one inode are one object if the bytes and
  metadata agree.
- A file past 4 GiB (4096 chunks), a directory past 16384 entries, nesting past 64 levels, a
  name past 255 bytes, a symlink target past 4095 bytes, and a walk that needs more than 16 MiB
  of working memory are refused with `E0415` and the path. No tree is cut silently.
- `tmp/` files a killed process leaves are not removed until gc (slice 4).

### What was checked, and against what

- Unit tests for every piece, in `zig build test`. The ones that carry the claims:
  - `import_tests.zig`: the digest does not change with the creation order, the listing order
    (the simulator shuffles every listing) or any time; everything that is content changes it;
    modes, owners, attributes and symlinks round-trip through objects and trees; a copy with one
    more file adds one object; devices and attributes are skipped as stated; the depth limit is
    exact; a disk that fills is `E0416` and the same import finishes later.
  - the crash test, this milestone's VOPR: for every write point of an import, once as a failing
    call and once as a crash (files torn, every call failing until a restart), the store holds
    only whole objects, chunk lists, trees and roots (`test_support.check_whole`), and the same
    import then gives the clean run's digest.
  - `store_commands_tests.zig` runs the commands through the command line in the simulator, in
    text and in JSON, and checks the output against the schemas' keys.
  - `diag_golden.zig` has a case for every new code; `site/errors/` has their pages.
- Fuzzers (10,000 iterations, seed 1): `tree` (the decoder never reads outside its input, and
  for any bytes the decoder accepts, encoding what it decoded gives the same bytes: one encoding
  per directory) and `store` (random trees, imported under interrupts and short I/O, an error at
  a random write point, a crash at a random write point, a disk that is too small, sometimes
  into a store that already has objects; always whole afterwards, and the repeat gives the
  digest of an import into a clean file system). Both were checked by mutation: the store fuzzer
  fails when an `fsync` is removed, the tree fuzzer when the order check is.
- In the build container (root, kernel 6.18, no KVM), against the pinned Alpine 3.20.10
  minirootfs, with the release binary: see "Real imports" below.

### Real imports

The pinned minirootfs (`src/testing/vm/alpine.zon`, SHA-256 checked) unpacked as an ordinary user
with a subuid range, as the VM demo does, and imported by that user (full map):

```
b3:14490ed05d0fa4ac3b0ccbba74927c7ebe08bff224c8ee5affb570da601353be
  87 files, 97 directories (the root included), 334 symlinks, 7,802,737 bytes; 80 objects (seven
  files repeat); store du: 7.5 MiB, 53 trees
```

The same tree after `touch -h -d 2031-05-05` on every entry: the same digest, 0 new objects.
After `chmod 700 alpine` (the root directory only): another digest, `b3:a5415b9c...`; after
`chmod 755 alpine`: the first digest again. A file owned by host uid 4242 (no mapping): exit 0,
one W0412 naming `alpine2/x4242`, and `"unmapped_owners":1,"unmapped_groups":1` in the JSON.
With one more 10,000,000-byte file: a new digest, 1 new object, `store du` 17.0 MiB (+10 MB and a
few trees). The mapping does not change a digest when every owner is the importing user: the same
files extracted with `tar -xp` and imported by the user (full map), and a copy of them chowned to
root and imported by root (no subuid range here, so the one-id map and W0201), both give
`b3:5b340463c9e6605c8a4771f525e4a13174bddc504e982112707e9cd785d31306`. A file owned by a subuid
is recorded under the full map as its container id (host 100001 as 2, with its mode and attribute
on the object on disk) and squashed to 0 under the one-id map, so the two maps give different
digests for such a tree, as the brief says they should.

### How a run by digest goes

1. The digest or prefix (12 or more hex digits, with or without `b3:`) is resolved against the
   user's store. No store, no such tree: `E0410`. Ambiguous prefix: `E0411`. Not a digest:
   `E0412`. These end the run before anything is created, exit 125, and are what Zigcube's
   `start_failed` for an unknown digest carries (`ZBX-E0410`).
2. In the store's child (the user's namespace, the id map the container will have) the tree is
   materialized into `<store>/cache/<64 hex>` if it is not there, and the container's directory
   `$XDG_STATE_HOME/zbx/containers/<name>/` is made with `merged` and either `upper` and `work`
   or, for `--read-only`, `empty`. A directory of the same name from an earlier run is removed
   first. The child's failure comes back through a pipe as the child's own diagnostic.
3. The plan mounts the overlay where a plain rootfs would be bound: `mount_overlay` replaces
   `bind_rootfs` (the same number of steps), inside the container's user and mount namespaces,
   with `userxattr,lowerdir=<farm>,upperdir=<upper>,workdir=<work>`. The rest of the setup is the
   same code as for `--rootfs`, on the merged directory.

### The farm

A directory per tree under the store's `cache/`: every directory is real, with the mode, owner
and attributes the tree records; every file is a hard link to its object (no space, and the
object's real owner, mode and attributes); every symlink is made again with its owner. The root
gets the root's own mode, owner and attributes (`Decoder.own`), and every directory the fixed
mtime. Directories get their attributes after their entries, so a directory without write
permission is still filled. It is built in `tmp/` and renamed into `cache/`, so a crash leaves
nothing under a digest (checked at every write point, as a failure and as a crash), and two
builds at once end with one farm. It must be built inside the user's namespace: a hard link to a
file of a subordinate id and `chown` to a container id need it.

### Decisions the brief left open

- **Read-only by mode** is not done by changing modes (the container must see the recorded
  ones). The farm is the overlay's lower layer, which a container cannot write; a write goes to the
  upper layer by copy-up. The plan test says it: the store's path appears in exactly one place in
  a plan, the `lowerdir=` of the overlay, and nothing is bound, remounted or created there.
- **`--read-only` with a digest** is an overlay with no upper layer. The kernel wants two lower
  layers then, so the second is an empty directory (`containers/<name>/empty`). `/tmp` and `/run`
  are the usual tmpfs; a tree without `/proc`, `/dev`, `/tmp` or `/run` fails at the step that
  needs it (`E0205` or `E0209`, naming the tree), because nothing can make them in a read-only
  root.
- **The upper layer's root** has the tree root's mode, owner and attributes, because with an upper
  layer the overlay shows the upper's root, not the lower's. Checked in the VM: a tree imported
  with a root of mode 711 is 711 in the container.
- **The upper of an ended container is kept while its record is.** When `prune` deletes a record
  (the newest 32 are kept) its container's directory is removed, in the store's child, because it
  holds files of subordinate ids. A directory that cannot be removed is `W0413`, never a failed
  run. A new run with the name of an old one removes the old directory first.
- **Paths with a comma, colon or backslash** can not be given to the overlay (the kernel splits
  the mount data at them): `E0425` names the path. Escaping is a cut.
- **Hardlink limit**: ext4 allows about 65,000 names per inode; an object under more names than
  that makes the build fail with `E0424` and the half farm is removed.
- **`E0701`** (no state directory) can end a run now, since the layers live there.
- **`can_end_run`** is true for `E0410` to `E0413`, `E0416` to `E0417`, `E0419`, `E0421` to
  `E0425` and `E0701`, and false for `E0414` (import), `E0418`, `E0420` and the warnings.
- **Record bytes** went from 32 KiB to 40 KiB: the two new fields are at their bounds in the
  comptime proof of the record's size.
- **The run fuzzer** has image scenarios (a fifth of the good roots): the plan is the overlay plan,
  `mount_overlay` is a step like any other that gets a failure injected (`E0425`), the helpers run
  twice (the store's child maps ids too), and a refused helper in the child is `E0419`.

### Cuts

- Copying the tree instead of an overlay when the kernel has no unprivileged overlayfs: a coded
  refusal (`E0425`, naming `zbx doctor`) instead.
- A tree imported under the full id map can not be run under the one-id map (its first `chown`
  fails with `EINVAL`, reported as `E0417`).
- An upper layer nested deeper than 64 directories is not removed (`W0413` says so); the next run
  with the name tries again.
- The library's `commit`, `gc` and `verify` are later slices.

## Slice 3: commit and diff

### What is where

| Piece | File |
| --- | --- |
| the commit: the import walk merged with the parent tree | `src/store/import.zig` (`commit`) |
| the diff | `src/store/diff.zig` |
| the commands, their output | `src/store_commands.zig` (`do_commit`, `do_diff`) |
| `device numbers in the file-system interface` | `src/store/fs.zig` (`Stat.rdev_major`, `rdev_minor`), `host_real_fs.zig`, `fs_sim.zig` |
| diagnostics | `E0426`, `E0427`, `E0428` |
| schemas | `zbx schema commit`, `zbx schema store-diff` |
| tests | `src/store/commit_tests.zig`, `store_commands_tests.zig`, `fuzz_commit.zig`, fixtures in `src/store/fixtures/` |

### How a commit goes

1. In the parent, before the namespace: the container's run record is read. A running container
   is `E0427` (nothing is frozen), a record with no tree (a `--rootfs` run) or no upper (a
   `--read-only` run) is `E0426`, an upper layer that is gone is `E0426` too.
2. In the store's child (the user's namespace, so a file of a subordinate id can be read), the
   upper layer is walked with the import's walk. Each directory is the merge of two sorted lists,
   the upper's names and the parent tree's entries:
   - a name only in the parent is copied through unchanged; a directory by its subtree digest, so
     nothing below it is read;
   - a name in the upper wins, except that a directory in the upper which is not opaque is merged
     with the parent's directory of that name (an upper directory made only to hold a copied-up
     child has its mode and owner from the lower directory, so this is right);
   - a whiteout (a character device 0/0, or a file with `user.overlay.whiteout`) removes the
     name outright: no entry is written, so the new tree has no trace of it and its stored size
     drops;
   - a directory with `user.overlay.opaque` = `y` replaces the parent's directory of that name;
   - `user.overlay.*` is never imported (it was not in slice 1 either), but this walk reads it.
3. The new tree is a root recording the container's name and the parent (`store ls --output
   json` has `parent`). A commit that changed nothing prints the parent's digest and writes no
   root.

### Decisions the brief left open

- **A device that is not a whiteout, in the upper layer** is skipped with `W0410` as in an import.
  If the parent has an entry of that name, that entry is gone too: the container's view of the
  name is a device, which the store can not hold.
- **Redirects and metadata-only copy-ups** (`user.overlay.redirect`, `user.overlay.metacopy`) are
  refused with `E0428`, naming the file. The upper layer alone does not say what they changed.
  zbx does not turn either on (the mount is `userxattr` only); `mv` of a directory in the
  container falls back to a copy (overlay answers `EXDEV`), checked for real (below).
- **The diff** lists a directory that appears or goes with its whole contents, one line per path
  (so a diff of a tree against its parent minus a directory names every file lost), and a
  path whose kind changes as `changed ... type`, then the contents of the side that is a
  directory as added or removed. The root directory's own mode, owner or attributes are the path
  `/`. Text: `A`, `D`, `M`, the path (a directory ends in `/`), and for `M` the attributes
  (`content`, `mode`, `owner`, `xattrs`, `target`, `type`). JSON has the same, with `kind`.
- **The commit's JSON** (`zbx schema commit`) has the totals of the whole new tree, what was new
  in the store, and `deleted`, the number of whiteouts in the layer.
- **Exit codes**: `E0426` and `E0427` are the user's (1), `E0428` the environment's (2).

### Cuts

- `--pause` (freezing a running container to commit it) is cut: the freezer needs cgroup
  delegation that M2 only has on a systemd user session, and a commit of a live upper layer
  can not be made consistent without it. `E0427` says the container must have exited and gives
  `zbx stop` as the fix. Not started, not tried.
- A commit does not rewrite the container's own layers: after it, the container still has its
  upper layer and `zbx commit` can be run again (it gives the same digest).
- `apk add` is not in the demo: containers have no network until M6. The demo's changes are file
  operations (add, rewrite, `chmod`, delete); the real overlay behaviour is the same.

## Slice 4: verify, gc, restore and the chunk write

`zbx store verify` says what is damaged and which images it breaks. `zbx store gc` plans, and
applies a plan by its hash into a trash that lasts a week. `zbx store restore` undoes a gc. The
library gets `put_chunk`, a verified write of one object a chunk at a time.

### What is where

| Piece | File |
| --- | --- |
| verify: the passes, the damage table, the reverse walk for paths | `src/store/verify.zig` |
| gc: reachability, plan, apply, trash, expiry, restore | `src/store/gc.zig` |
| the generation counter | `src/store/generation.zig` |
| sorted listing of a shard | `src/store/shards.zig` |
| the chunk write | `src/store/chunks.zig` (`store.put_chunk`; `store.chunks` lists) |
| the commands and their output | `src/store_commands.zig` (`do_verify`, `do_gc`, `do_restore`) |
| diagnostics | `E0429` to `E0436` |
| schemas | `zbx schema store-verify`, `store-gc`, `store-trash`, `store-restore` |
| tests | `gc_tests.zig`, `chunks_tests.zig`, `store_commands_tests.zig`, `fuzz_gc.zig`, goldens |

### Layout additions

```
store/lock                       flock target: shared by writers, exclusive for gc apply and restore
store/generation                 a number; every write to the store raises it first
store/trash/<gc id>/meta.zon     when, until when, counts, and whether the move finished
store/trash/<gc id>/objects/ab/  what gc moved, under the names it had
store/trash/<gc id>/trees/ab/
store/trash/<gc id>/cache/       materialized directories
store/partial/<id>/<n>           chunks of an object being written by put_chunk
```

The gc id is the first 12 hex digits of the plan hash it ran with.

### verify

1. Every file object is read and its id is recomputed from the hash of its bytes and its real
   mode, owner and attributes (an id is the hash of a header, so a changed mode is damage as
   much as a changed byte). Its chunk list is recomputed and compared; a list that is missing,
   extra or different is damage.
2. Every tree object is read, must hash to its name, and must decode.
3. Every root record must read, and the tree below it must be whole: every subtree present,
   every file's object present.
4. If anything is damaged, every root's tree is walked again with paths; for each damaged thing
   the paths (at most 16) of every root that reaches it are recorded, sorted by root and path.

Output: one `E0429` per damaged thing on stderr (the first 256; the rest are counted), then the
summary `E0430`, exit 2 (the store is the environment's). The default text shows the object's
id, why, the first path and how many more; the fix is the `rm` of the damaged file. `--verbose`
shows three paths and the file; `--output json` puts all of it in the stdout object
(`zbx.store.verify/1`), whether or not anything is damaged.

A chunk list with no object beside it is what a killed import or gc leaves. It is counted
(`orphan_lists`) and not damage; the next gc moves it away.

### gc

**What is kept.** Everything below a root record, and everything below the tree of a running
container (read from the run records, `state running`). The plan is what remains:

- file objects no kept tree names, with their chunk lists; chunk lists with no object;
- tree objects no kept tree reaches;
- materialized directories (`cache/<digest>`) of a tree that is neither a root nor live (a
  directory of a root is kept: it is a cache that costs a rebuild);
- leftovers in `tmp/` named `<pid>-<n>` where the process is gone (deleted, not trashed).

**The plan hash** is the BLAKE3 of `zbx-gc-plan 0x01`, the generation counter, and, in id order,
a tag byte and the id of everything the plan would move. `zbx store gc` prints it with the
counts and bytes and changes nothing. `--confirm <hash>` makes the plan again, and acts only if
it hashes the same; otherwise `E0431` (exit 1) names the plan as it is now. Every write to the
store raises the counter first: an import, a commit, a `store rm`, the build of a materialized
directory, a restore, a gc, the assembly of a chunked object. Nothing prompts.

**Apply** writes `meta.zon` (marked unfinished) into a new `trash/<gc id>/`, then `rename`s each
thing into it (an object before its chunk list), then rewrites `meta.zon` as finished with the
counts of what moved. It then empties every trash whose time is past (`store_trash_seconds`, 7
days after it was made) and deletes the dead leftovers in `tmp/`. A directory in `trash/` with
no metadata is removed only if it holds nothing but empty directories.

**Restore** refuses, changing nothing, when the id is not a trash (`E0433`), when a finished
trash holds fewer things than it recorded (`E0434`), or when anything in it is in the store
again (`E0432`, naming the first and counting the rest). Otherwise it marks the trash
unfinished, moves everything back (a chunk list before its object; if the store has no list for
an object that needs one, one is made from the object's bytes first), and removes the trash.
`zbx store gc --trash` lists the trash with its state, `complete` or `incomplete`.

**Crash safety.** The only writes are renames and atomic file writes, and the order is chosen
so that no object ever lacks the chunk list it needs: a killed gc or restore leaves a store that
`verify` calls clean, and the same command (a new plan, or the same restore) finishes the work.
Tested by crashing and failing every write point of an apply and of a restore, in the unit
tests and in the `gc` fuzzer.

### The chunk write

`store.chunks` lists an object's chunk hashes (already in slice 1). `store.put_chunk(store, io,
wanted, index, bytes, failure)` accepts one chunk if its length is the chunk's and its hash is
`wanted.hashes[index]`, keeps it in `partial/<id>/<index>`, and when the last is in assembles
the object: the chunks in order into a file in `tmp/` that must have the size and the content
hash, the attributes applied, the chunk list renamed into place, then the object. `Wanted` is the
object's attributes, size, content hash and chunk hashes: **this is a deviation from the brief's
`put_chunk(object_id, index, bytes)`**, because an object's id is a hash of the content hash and
the attributes and says nothing about the chunks; the caller (Zigcube) has them from the tree
entry and the chunk list it fetched. The id is checked to be the hash of the content and
attributes, a one-chunk file must have its content hash as its one chunk hash, and the chunk
hashes are the caller's claim that the assembly checks against the content hash.
Refusals: `BadWanted`, `IndexOutOfRange`, `WrongLength`, `HashMismatch`, `ContentMismatch`
(and the chunks are discarded), `StoreFailed`. A duplicate chunk is accepted and reported as
such; a held chunk that no longer hashes right is replaced. An empty file has no chunk to put:
`finish` makes it.

### Decisions the brief left open

- **Live containers** are the running ones and the ended ones that can still be committed: a
  record with a tree digest whose upper layer is still on disk. Records keep the newest 32, so
  the tree of an ended container is held until its record is pruned or its layer is deleted;
  then it may be collected, and nothing could have committed onto it anyway. A kept tree keeps
  its materialized directory too (it costs disk until then; the directory is rebuilt on demand
  if it is ever lost).
- **A dead materialized directory** is one whose tree is not a root and not live.
- **The gc id** is 12 hex digits of the plan hash. A second gc with the same hash cannot happen:
  the counter has moved.
- **Orphan chunk lists** are not damage (see verify).
- **Trash expiry** is checked only when a gc is confirmed, not by a timer; `gc --trash` shows
  the time.

### Cuts

- **Limits.** gc keeps what the roots reach in tables of fixed size (about 49,000 distinct
  objects, as many trees, and as many roots-and-live trees as fit 1 MiB); verify holds about
  98,000 distinct objects while it walks. A store past them is refused with a message that says
  what outgrew its memory, never cut. Raising them is a constant (`store_arena_bytes_max`).
- **Restore ordering.** If a gc was killed between moving an object and its chunk list, and a
  second gc then took the list into another trash, restoring the first trash makes the list
  again from the object's bytes. That is the one place restore writes something that was not
  in the trash.
- `put_chunk` has no CLI.

### What was checked, and against what

- Unit tests (`gc_tests.zig`): verify finds a changed byte (naming every path, across roots),
  a changed mode, a damaged or missing tree, a missing object, every chunk-list disagreement,
  an unreadable object (damage with its errno, not a stop), and caps the paths per object at
  16; gc's plan against an oracle (the files of a store that never had the dropped root), the
  plan hash moving with any write, stale refusals, dead directories and leftovers, running

- `chunks_tests.zig`: chunks in any order, corrupted, short, long, out-of-range, duplicate,

- The `gc` fuzzer (10,000 iterations, in the CI matrix): random trees that share a base, some

### The step 7 hang

`demo-m3` timed out once, 480 s after `zbx stop live1`, at the next command (`zbx run --rootfs
... -- true`). It was ours, and old: `Host.wait_event` (`host_real.zig`).

**Reproduction.** `ZBX_DEMO_LOOP_STEP7=<n> zig build demo-m3 -Daccel=tcg` imports the rootfs and
then runs step 7's commands `n` times (a detached run, a refused commit, a stop, a foreground
`run --rootfs -- true`, a commit), with a heartbeat in the guest that prints every ten seconds
what `zbx` and `runuser` are waiting for. Foreground loops hung twice with the cause below: at
round 4 of 25 (a `run` under a guest `timeout`, killed after 150 s) and at round 5 of 80 (with the
heartbeat); the unchanged demo hung once in four runs. About one `run ... -- true` in ten to
twenty. A third loop, with each command in the background of the guest shell and polled, stopped
differently, at round 25 of 60: the harness's next typed line never started (no `ZBXBEGIN`) after
a `stop`. That one I could not explain or repeat (the foreground loops, including the 100 after the
fix, never showed it); the console was quiet, so I cannot say whether the guest or the harness
stopped. It is recorded, not claimed fixed. The heartbeat at the hang:

```
1903 S+ do_wait           runuser -u demo -- env ... /home/demo/zbx run --rootfs ... --name dir5 -- true
1904 S+ do_sigtimedwait   /home/demo/zbx run --rootfs /home/demo/alpine --name dir5 -- true
1911 S  pipe_read         /home/demo/zbx run --rootfs /home/demo/alpine --name dir5 -- true
```

`1904` is the parent, in `Session.wait`, in `rt_sigtimedwait`. `1911` is the scope's keeper
(forked from zbx, so the same command line), reading its pipe until `release_keeper` closes it.
There is no container process: `true` had already ended and was a zombie.

**Cause.** `wait` blocks SIGCHLD and then waits for it with `rt_sigtimedwait`. SIGCHLD's default
action is to ignore it, and a signal that is not blocked is dropped, not queued. A container
whose command ends between its `exec` (which ends `await_report`) and the `sigprocmask` in `wait`
has its SIGCHLD dropped, and the wait then looks at an empty queue for ever, with the child
already waiting to be reaped. `true` on a busy single-CPU guest is the case that does it; `sleep
600` and the long runs of the other steps never do. The keeper fix did not cause it (the keeper
is why `ps` shows a second process, and why the scope stays), and the order of `stop` and `run`
only changes the load.

**Fix.** `wait_event` looks for the child with `wait4(WNOHANG)` first, with the signals already
blocked: a child that ended earlier is found there, and one that ends later raises a SIGCHLD
that waits in the queue. Test: `host_real.zig`, "real wait_event sees a child that ended before
the signals were blocked" (a forked child that exits at once, a pause, the block, the wait; it
returns `.timeout` without the fix and the child's status with it).

**After the fix** the loop ran 100 rounds (500 commands, 826 s under TCG) without a hang, where
the earlier loops hung within 25 rounds.

### By hand

With the `zbx` binary, an Alpine rootfs in `./alpine` (as a user with a subuid range) and a
network. Put an http repository and a resolver in the rootfs first:

```
printf '%s\n' http://dl-cdn.alpinelinux.org/alpine/v3.20/main \
  http://dl-cdn.alpinelinux.org/alpine/v3.20/community > alpine/etc/apk/repositories
echo nameserver 10.0.2.3 > alpine/etc/resolv.conf     # or your resolver
```

1. `zbx store import ./alpine` prints the digest. `zbx store du` prints the total.
2. `cp -a alpine alpine-big && head -c 10000000 /dev/urandom > alpine-big/big.bin`, then
   `zbx store import alpine-big` and `zbx store du`: the total is about 10 MB more, not 7 MB
   more than that.
3. `printf 'apk add --no-cache dtach\nexit\n' | zbx run <digest> --name apk1 -- sh`, then
   `zbx commit apk1` prints a new digest and `zbx store diff <old> <new>` lists `A
   /usr/bin/dtach` and changes to apk's database.
4. Find the object of a file (`cmp` it with the source), change its first byte (`printf X | dd
   of=<object> bs=1 seek=0 conv=notrunc`), then `zbx store verify`: exit 2, the object, its
   file and the paths. Delete the file and import the directory again to repair it.
5. `zbx run <big digest> --name ops1 -- rm /big.bin`, `zbx commit ops1`, and `zbx --output json
   store du <old>` against `... <new>`: `stored_bytes` falls by the file.

### Cuts

- **The same digest** is checked with other mtimes and a new copy in the VM, and with shuffled
  readdir order and changed mtimes in the simulator. The VM cannot choose the order a directory
  is listed in.
- **Extended attributes** are checked on the file the lower directory is made of, from the
  host: Alpine's busybox has no `getfattr`, and the demo does not install one. The simulator
  tests read them back from the store.
- **Owners** are checked the way a container can make them (`chown` as its root, committed).
  The demo cannot give a file in the source tree an owner the demo user is not allowed to give.
- **Chunks.** The demo corrupts an object (the file's bytes), which is what "a chunk on disk"
  is for a file stored whole; the chunk list's own damage is in the unit tests.
- **The size of the demo's package** is one file (`dtach`, 9 KB). A package with more files is
  the same check.
- **aarch64** is built and size-checked, not run.
- **`put_chunk` has no command**, and the store lock is not held across a library caller's own
  steps (see "The store lock").

### Failure modes

| What | How it shows | Recovery |
| --- | --- | --- |
| the disk fills during an import | `E0416`, how many objects were kept; the kept ones are whole | free space, run the same command; stored objects are skipped |
| the disk fills while a farm is built, or the trash filled | `E0416`; the half farm is removed; a half trash is `incomplete` and restorable | free space, run again |
| an object has more names than the file system allows (ext4: 65,000 links to one inode; a big farm of one popular file) | `E0424`; the half farm is removed | fewer copies in use, or a file system with a higher limit |
| the kernel refuses the overlay (no unprivileged overlayfs, a path with `,` `:` `\`) | `E0425`, naming `zbx doctor` or the path; exit 125 | `zbx doctor`; run with `--rootfs`; other `XDG_*` directories |
| an object, tree or root record is damaged | `E0429` for each and `E0430`, exit 2; `verify` names the paths that reach it | delete the file named and import its directory again; `zbx store rm` the roots that reach it |
| a gc plan is stale (anything wrote to the store since it was made) | `E0431`, exit 1, with the hash of the plan now | read the plan again and confirm that |
| the trash expired, or was restored | `E0433`, exit 1 | restore within seven days; `zbx store gc --trash` lists what is left |
| something in the trash is back in the store | `E0432`, nothing moved | drop the roots that brought it back, or let the trash expire |
| the store lock is held (a gc or restore; importers keeping a gc waiting) | `E0436`, exit 1, after 10 s; names the holder when it is a gc or restore | run it again when the other command is done; a lock never outlives its process |
| a killed import, gc or restore | files in `tmp/`, nothing under an id; a trash `incomplete`; `verify` clean | run the command again |
| the namespace, the helper or the data directory is unusable | `E0419`, `E0417`, `E0421`, `E0701` | `zbx doctor`; fix permissions or `XDG_DATA_HOME` |

The older tables (slices 1 to 4) have the rest, with the codes.
