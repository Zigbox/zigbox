# M3 demo: the store

This document grows slice by slice. Slice 1 (trees and import) is written. The demo itself
(`zig build demo-m3`) is slice 5; until then M3 is built in slices, not demonstrated.

## Slice 1: trees and import

`zbx store import <dir>`, `ls`, `du` and `rm`, the canonical tree encoding, file objects and
their chunk lists, the store's layout, and the child that does the store's work. The layout is in
the module doc of `src/store/store.zig`; this section says what was decided where the brief left
room, what was cut, and what was checked.

### Decisions the brief left open

- **The file-system interface is a second vtable, reached through the host.** The store needs
  about twenty operations the rest of the host does not (lstat with owner and links, xattrs,
  fchown, getdents of long directories, fsync, rename), and its simulator must be a whole file
  tree with faults and crashes, which the container simulator's small model is not. So
  `Host.filesystem()` hands out a `store/fs.zig` `Fs`; `host_real_fs.zig` is the syscalls (and
  is, like `host_real.zig`, a place that may name them) and `fs_sim.zig` is the model. Everything
  above it is written against `Fs` only. A host with no file system (`HostSim` without one) answers
  with a machine that is down: every call fails with `EIO`.
- **A chunk list is stored only for an object longer than one chunk.** The brief says every
  object records its chunk hashes beside it. For a file of at most one chunk the list is
  its content hash (and an empty file has none), so the file is stored without a second file;
  `object.chunk_hashes` returns the list either way. Alpine's rootfs has 87 files and two chunk
  lists. This halves the inodes of a store of small files, and `chunks(object_id)` does not
  change for Zigcube.
- **The imported directory's own mode, owner and attributes are not in the digest.** The root of
  a tree is a mount point, not content; a copy made with another umask must give the same digest.
  Every directory below the root has its metadata in its entry in the parent.
- **One root record per tree.** `roots/<digest>` is overwritten by a later import of the same
  tree, so `ls` shows the latest source and time. `files` and `bytes` (logical totals) are in the
  record so `ls` needs no walk.
- **The fixed mtime is 2000-01-01T00:00:00Z** (`constants.store_mtime_seconds`, 946684800), on
  every object and every other file the store writes. Zero was avoided: some tools take the
  epoch to mean "no time".
- **Schemas are named `store-import`, `store-ls`, `store-du`, `store-rm`** (`zbx schema
  store-ls`): `schema` takes one operand.
- **`ls` and `du` and `rm` run in the namespace child too**, but only `import` shows the one-id
  warning (W0201): the other commands do not depend on the map.
- **Extra codes**: `E0421` (no data directory), `E0422` (a tree reached from another is missing
  or damaged), `E0423` (cannot read the store). `E0410` is "no tree with that digest", the code
  for `Spec.image` when the store lacks the digest.

### Ownership, as built

The child maps ids as `zbx run --rootfs` does. With the full map the user is 0 and the subuid
range is 1 to 65536, so a file owned by host uid 100001 is recorded as 2, and `chown` of an
object to 2 inside the child makes the file really owned by 100001. With the one-id map (W0201)
every owner is recorded as 0, whatever the kernel reports (it reports 65534 for ids the map
lacks). Known limit: with the full map, a file owned by a host id that is neither the user nor in
the range also reads as 65534, which is a legal container id, so it is recorded as that. The
kernel gives the child no way to tell the two apart.

`security.capability` is recorded as the child reads it, which in the user's own namespace is
the version 2 form; written back inside the namespace the kernel stores it as a version 3
capability whose root id is the namespace's root, which is what "namespaced v3" means on disk.
Checked for real: a capability set inside `unshare -U -r` was imported, and the object carries
`0100000300000200...` plus the user's uid in the root id field.

### What is cut

- Other xattr namespaces (`trusted.*`, `security.selinux`, ACLs) are skipped with `W0411`, as the
  brief says. So are an attribute with a name over 255 bytes or a value over 4096, and any
  attribute past the sixteenth on a file.
- Devices, FIFOs and sockets are skipped with `W0410`.
- Hardlinks become separate entries; two names for one inode are one object if the bytes and
  metadata agree.
- A file past 4 GiB (4096 chunks), a directory past 16384 entries, nesting past 64 levels, a
  name past 255 bytes, a symlink target past 4095 bytes, and a walk that needs more than 16 MiB
  of working memory are refused with `E0415` and the path. No tree is cut silently.
- `tmp/` files a killed process leaves are not removed until gc (slice 4).

### What was checked, and against what

- Unit tests for every piece, in `zig build test`. The ones that carry the claims:
  - `import_tests.zig`: the digest does not change with the creation order, the listing order
    (the simulator shuffles every listing) or any time; everything that is content changes it;
    modes, owners, attributes and symlinks round-trip through objects and trees; a copy with one
    more file adds one object; devices and attributes are skipped as stated; the depth limit is
    exact; a disk that fills is `E0416` and the same import finishes later.
  - the crash test, this milestone's VOPR: for every write point of an import, once as a failing
    call and once as a crash (files torn, every call failing until a restart), the store holds
    only whole objects, chunk lists, trees and roots (`test_support.check_whole`), and the same
    import then gives the clean run's digest.
  - `store_commands_tests.zig` runs the commands through the command line in the simulator, in
    text and in JSON, and checks the output against the schemas' keys.
  - `diag_golden.zig` has a case for every new code; `site/errors/` has their pages.
- Fuzzers (10,000 iterations, seed 1): `tree` (the decoder never reads outside its input, and
  for any bytes the decoder accepts, encoding what it decoded gives the same bytes: one encoding
  per directory) and `store` (random trees, imported under interrupts and short I/O, an error at
  a random write point, a crash at a random write point, a disk that is too small, sometimes
  into a store that already has objects; always whole afterwards, and the repeat gives the
  digest of an import into a clean file system). Both were checked by mutation: the store fuzzer
  fails when an `fsync` is removed, the tree fuzzer when the order check is.
- In the build container (root, kernel 6.18, no KVM), against the pinned Alpine 3.20.10
  minirootfs, with the release binary: see "Real imports" below.

### Real imports

The pinned minirootfs (`src/testing/vm/alpine.zon`, SHA-256 checked) unpacked as an ordinary user
with a subuid range, as the VM demo does, and imported by that user (full map):

```
b3:c5758cfbe102f8661feb3899eabcb942edcf2f7f6204cf51aa065039bddbc76e
  87 files, 97 directories (the root included), 334 symlinks, 7,802,737 bytes; 80 objects (seven files repeat),
  51 trees, store du 7,814,104 bytes
```

The same tree after `touch -h -d 2031-05-05` on every entry: the same digest, 0 new objects.
With one more 10,000,000-byte file: a new digest, 1 new object, `store du` 17.0 MiB (+10 MB and a
few trees). The mapping does not change a digest when every owner is the importing user: the same
files extracted with `tar -xp` and imported by the user (full map), and a copy of them chowned to
root and imported by root (no subuid range here, so the one-id map and W0201), both give
`b3:017ab5202f8aee2e7c3241460ac1be26c1cfb33c11fac692730fe1c6ed466036`. A file owned by a subuid
is recorded under the full map as its container id (host 100001 as 2, with its mode and attribute
on the object on disk) and squashed to 0 under the one-id map, so the two maps give different
digests for such a tree, as the brief says they should.

### By hand

```sh
zbx store import ./alpine          # prints b3:...
zbx store import ./alpine-copy     # same digest if the content is the same
zbx store ls                       # roots, newest first
zbx store du                       # the store's bytes, objects and trees
zbx store du b3:c5758cfbe102       # one tree: logical, stored and shared size
zbx store rm b3:c5758cfbe102       # drop the root; the data stays until gc
zbx --output json store import ./alpine
```

### Failure modes (slice 1)

| What | How it shows | Recovery |
| --- | --- | --- |
| the disk fills during an import | `E0416`, says how many objects were kept | free space, run the same command; stored objects are skipped |
| the store directory is read-only or unwritable | `E0417` naming the call | fix permissions or `XDG_DATA_HOME` |
| a file changes while it is imported | `E0418` naming the file | stop the writer or import a copy |
| a limit of the import is passed | `E0415` naming the path | split the tree |
| the source is missing, a file, a symlink or unreadable | `E0414` naming the path | check the path |
| `store.zon` is newer or unreadable | `E0413` | use the zbx that wrote it, or set the store aside |
| no `HOME` or `XDG_DATA_HOME` | `E0421` | set one |
| the namespace cannot be set up | `E0419` with the helper's output | `zbx doctor` |
| a tree below another is missing or damaged | `E0422` naming it (`du`) | import again; `verify` arrives in slice 4 |
| a killed import | files in `tmp/`, nothing under an id | run it again; gc removes `tmp/` (slice 4) |
