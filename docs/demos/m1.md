# M1 demo: `zbx run` in an Alpine root filesystem, as an ordinary user

There are two ways to run this demo: by hand on your own Ubuntu 24.04 machine (for presenting),
or automatically in a throwaway VM (`zig build demo-m1`, which is also what CI runs). Both run
the same steps. Prerequisites are the M0 ones ([m0.md](m0.md)): `zbx doctor` is all `ok`.

## By hand, on your own Ubuntu 24.04 machine

You need `zbx` on the PATH (or call it by path), `uidmap` installed, a line for your user in
`/etc/subuid` and `/etc/subgid`, and `kernel.apparmor_restrict_unprivileged_userns=0`. If one is
missing, `zbx doctor` says which and what to type. Nothing below needs root.

```
# The root filesystem: a pinned Alpine 3.20 minirootfs, unpacked by you, owned by you.
$ mkdir alpine
$ curl -fsSLO https://dl-cdn.alpinelinux.org/alpine/v3.20/releases/x86_64/alpine-minirootfs-3.20.10-x86_64.tar.gz
$ echo '0d44a414245f043ae56872a23762e6c9bee585da2cbe4aa81cbd0331eaf53223  alpine-minirootfs-3.20.10-x86_64.tar.gz' | sha256sum -c
$ tar -xzf alpine-minirootfs-3.20.10-x86_64.tar.gz -C alpine
```

**1. A shell in the container.** The container's root is the directory; inside, you are root,
the process list is yours alone, and the hostname is the container's name:

```
$ zbx run --rootfs ./alpine --name demo1 -- /bin/sh
/ # id
uid=0(root) gid=0(root) groups=0(root)
/ # ps
PID   USER     TIME  COMMAND
    1 root      0:00 /bin/sh
    3 root      0:00 ps
/ # hostname
demo1
/ # cat /etc/os-release
NAME="Alpine Linux"
ID=alpine
VERSION_ID=3.20.10
/ # exit
```

(With no terminal on stdin, as in the automated demo, feed the same commands with `printf`.)

**2. The host sees an ordinary process of yours.** In one terminal `zbx run --rootfs ./alpine --
sleep 1000`; in another:

```
$ ps -o uid,user,args -C sleep
  UID USER     COMMAND
 1000 alice    sleep 1000
```

Root inside, your uid outside. Press Ctrl-C in the first terminal: the container stops at once,
and `zbx` exits **130**. (A plain `sleep` as PID 1 ignores every signal it has no handler for;
`zbx` notices that and sends SIGKILL in its place, so Ctrl-C works. A shell keeps its own
handler, and keeps working.)

**3. It is a real root filesystem.** A write lands in the directory, owned by you:

```
$ zbx run --rootfs ./alpine -- sh -c 'touch /etc/hacked'
$ ls -l alpine/etc/hacked
-rw-r--r-- 1 alice alice 0 ... alpine/etc/hacked
$ ls /etc/hacked
ls: cannot access '/etc/hacked': No such file or directory
```

**4. The exit code passes through.**

```
$ zbx run --rootfs ./alpine -- sh -c 'exit 42'; echo $?
42
```

**5. The ids, the host, a missing rootfs, a bundle.**

```
$ zbx run --rootfs ./alpine -- sh -c 'cat /proc/self/uid_map'
         0       1000          1
         1     100000      65536
$ zbx run --rootfs /nowhere -- /bin/sh; echo $?
error[ZBX-E0201]: the rootfs is missing or not a directory
  cause  '/nowhere' does not exist
  fix    unpack a root filesystem into a directory:   mkdir alpine && tar -xzf alpine-minirootfs-*.tar.gz -C alpine
         then name that directory:                    zbx run --rootfs ./alpine -- /bin/sh
  more   zbx explain E0201 · rerun with --verbose for the full cause chain
  docs   https://zigbox.github.io/zigbox/errors/E0201.html
1
$ GITHUB_TOKEN=ghp_0123456789abcdefghij0123 zbx bundle --last
/home/alice/.local/state/zbx/bundles/2026-10-24T21-05-36Z-demo1.tar.gz
$ tar -tzf /home/alice/.local/state/zbx/bundles/2026-10-24T21-05-36Z-demo1.tar.gz
$ tar -xzOf ...tar.gz | grep -c ghp_0123456789abcdefghij0123
0
```

The bundle lists every file and why it is there in `MANIFEST.txt`; read it before you share one.

## Automatically, in a VM

`zig build demo-m1` boots the same pinned Ubuntu 24.04 image as `demo-m0`, with the same
provisioning (user `demo`, `uidmap`, subuid range `demo:100000:65536`, the AppArmor sysctl). The
harness downloads the pinned Alpine minirootfs ([alpine.zon](../../src/testing/vm/alpine.zon),
URL and SHA-256, the hash Alpine publishes next to the file), verifies it, serves it to the
guest, and the guest unpacks it **as `demo`**. Every step is an assertion; stdout and stderr are
kept apart as in M0. The guest's serial console is the only way in.

| Step | What is asserted |
| --- | --- |
| 1 | The shell is fed `id`, `ps`, `hostname`, `cat /etc/os-release` on stdin: `uid=0(root)`; `ps` lists PID 1 (`/bin/sh`) and the `ps` itself and nothing else; the hostname is the name; `ID=alpine`, `VERSION_ID=3.20.`; stderr empty; exit 0 |
| 2 | `sleep 1000` in the background: the host's `ps` shows exactly one such process, with uid 1000; after `zbx` is stopped, none |
| 3 | `touch /etc/hacked`: `/home/demo/alpine/etc/hacked` exists, owned by `demo`; `/etc/hacked` does not |
| 4 | `sh -c 'exit 42'`: zbx exits 42, nothing on either stream |
| 5 | A foreground `zbx run ... sleep 1000` run from the console's shell; the harness sends the byte `0x03` over the serial console, which the tty turns into SIGINT, as for a person; zbx exits 130, with the SIGINT note on stderr, within 2 s (the limit is scaled by 8 under `-Daccel=tcg`) |
| extra | `/proc/self/uid_map` and `gid_map` inside are `0 1000 1` and `1 100000 65536`, with no warning |
| extra | A tmpfs mounted on the host and a host `sleep 4321` exist (checked), and neither is visible from the container |
| extra | A missing rootfs: `error[ZBX-E0201]` on stderr, nothing on stdout, exit 1 |
| extra | A run and then `zbx bundle --last` with `GITHUB_TOKEN`, `DB_PASSWORD` and `--password=...` planted in the environment and the command: `tar -tzf` lists the bundle, `tar -xzOf | grep` finds none of the secrets, and finds at least one `[redacted:...]` marker (a bundle that redacted nothing would pass the first check for the wrong reason) |

### Running it

```
zig build demo-m1                 # needs /dev/kvm (and qemu-system-x86, qemu-img)
zig build demo-m1 -Daccel=tcg     # software emulation: slow (about 8 minutes on a 4-core host, nearly all of it the guest's first boot), no KVM needed
```

`-Dkeep-overlay` and `-Dreuse-overlay` keep and reuse the provisioned VM disk between runs, as in
M0. The base image and the Alpine tarball are cached in `.zig-cache/zbx-vm/`, each verified
against its pinned SHA-256 on every run.

### CI

The `demo-m1` job in `.github/workflows/ci.yml` is a sibling of `demo-m0`: the same KVM setup and
the same image cache entry, plus a cache entry for the Alpine tarball keyed by `alpine.zon`. CI
runs on pull requests and on `main`.

### Developer notes

- The harness is shared with M0 (`src/testing/vm/harness.zig`); `main_m1.zig` holds the M1
  steps and `checks_m1.zig` the assertions as pure functions, each unit-tested with wrong input
  too.
- The Ctrl-C step runs `sh /tmp/ctrlc.sh` at the console's own shell, so the script is the tty's
  foreground job. The script begins with `trap : INT`: bash would otherwise abandon the rest of
  the line when its child dies of SIGINT, and a handler (unlike `trap '' INT`) is not inherited
  as "ignored" by zbx. See "SIGINT inherited as ignored" below.

## Cut from M1

Left out on purpose, so the demo stays small and true:

- **No pty.** `zbx run` does not allocate a terminal for the container. A shell run from a
  terminal works (the terminal is inherited), but there is no `-t`, no window-size handling and
  no job control inside.
- **No `/sys`.** The container has `/proc` and a minimal `/dev`, not `/sys`.
- **No network namespace.** The container shares the host's network. (Network isolation is M5.)
- **No `-e`.** The environment is a fixed minimal one (`PATH`, `HOME=/root`, `HOSTNAME`, and `TERM` if set),
  and there is no way to add variables. Environment passing arrives with the image config.
- **No bundle from the panic handler.** A panic prints the `bug[ZBX-B0001]` block and exits 70;
  it writes no bundle and has no `saved` line, because the handler cannot safely reach the host,
  needs about 700 KiB of working memory, and runs std's compressor, whose own assertions would be
  a second panic. A `bug` diagnostic that the code raises for a recorded run does get a bundle.
- **Huffman-only gzip.** Bundles are gzip files from std's Huffman-only compressor, not its full
  one: the full compressor is 230 KiB of state that std builds as a temporary on the caller's
  stack. Bundles are a little larger than they could be (a few KiB).
- **Foreground only, no `stop`, `list`, re-adoption or events** (M2).

## Open question for the owner: container exit codes 1 and 2

`zbx run` exits with the container's own exit code, and zbx's own failures use the standard's
codes: 1 (the user's mistake), 2 (the environment's), 70 (a bug in zbx). A container that exits 1
or 2 is therefore indistinguishable by exit code from a zbx failure. We did not invent new exit
codes. Today a script tells them apart with `--output json`: a run whose command started ends
with one `{"container_exit":{"code":N}}` line on stderr, and a failure before the command started
is a JSON diagnostic object instead. Should `zbx run` reserve
a range for its own failures, or keep the overlap and rely on `--output json`?

## Failure modes

For each: what can go wrong in production, how it shows up, how to recover.

**No subuid range (or no `newuidmap`).**
- Shows up as: `warning[ZBX-W0201]: mapping only your own id into the container` on stderr, once,
  before the command starts; the exit code is the command's. Inside, only uid 0 exists
  (`/proc/self/uid_map` has one line), and a program that switches users or chowns fails.
  `zbx doctor` reports the same host fact as `ZBX-E0105`.
- Recover: give the user a range (the warning prints the command):
  `sudo usermod --add-subuids 100000-165535 --add-subgids 100000-165535 $USER`, and install
  `uidmap` if the helpers are missing.
- If the helpers exist but refuse the write (a range that is not in `/etc/subuid`, a helper
  that is not setuid root): `error[ZBX-E0204]: writing the id maps failed`, exit 2, naming the
  helper and its exit status and output.

**AppArmor restriction (Ubuntu 24.04 defaults).**
- Shows up as: `error[ZBX-E0203]` (the namespaces could not be created), exit 2, whose cause is
  the doctor's finding for `ZBX-E0101`: `kernel.apparmor_restrict_unprivileged_userns = 1`.
- Recover: `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`, persisted in
  `/etc/sysctl.d/`; `zbx doctor` prints both commands. A site that cannot relax it needs an
  AppArmor profile for zbx (not shipped in M1).

**A rootfs owned by another user.**
- Shows up as: nothing from zbx, which cannot know. Files owned by a user that is not mapped
  appear as `nobody` (uid 65534) inside, and writes the mapped root may not do fail with the
  command's own `Permission denied` and its own exit code. A rootfs that is missing or not a
  directory is `ZBX-E0201` (exit 1); a command that is not in it is `ZBX-E0202` (exit 1).
- Recover: unpack the rootfs yourself, as the user who runs it (`tar -xzf` without `sudo`); do
  not point `--rootfs` at a root-owned tree you want to write to.

**A full disk for run records or bundles.**
- Run records: `warning[ZBX-W0202]: can't save the run record`, once per run; the run goes on and
  exits as the command does, but `zbx bundle` will not find it. A record that cannot be read when
  the old ones are pruned is skipped with `warning[ZBX-W0203]` and counts as the oldest.
- Bundles: `error[ZBX-E0702]: can't write the bundle`, exit 2, with the errno (`no space left on
  the device`); the file is written under a temporary name and renamed, so no half bundle is left.
  With no usable state directory at all (no `HOME`, no `XDG_STATE_HOME`): `ZBX-E0701`.
- Recover: free space, or point `XDG_STATE_HOME` at a directory with room. Records and bundles
  are small (a record is under 32 KiB, a bundle under 200 KiB); at most 32 records are kept, but
  bundles are never deleted by zbx.

**A command killed by a signal.**
- Shows up as: exit code 128 plus the signal (130 for SIGINT, 137 for SIGKILL, 143 for SIGTERM),
  `zbx: the container was killed by signal N (SIGNAME)` on stderr (text mode), `.exit = .{
  .signaled = N }` in the run record, and `{"container_exit":{"signal":N,"code":128+N}}` with
  `--output json`. A container whose PID 1 has no handler for a forwarded signal is killed with
  SIGKILL in its place, and is reported as killed by the original signal. If zbx itself dies, the
  kernel kills the container (`PR_SET_PDEATHSIG`); the record then still says `running`.
- Recover: nothing to recover; this is the normal end of a killed command. The OOM killer shows
  as 137 and is not distinguished from a SIGKILL until M3 (cgroup limits).

**SIGINT inherited as ignored.**
- Shows up as: Ctrl-C and `kill -INT` have no effect on a `zbx run` that was started with SIGINT
  ignored, which is how a non-interactive shell starts a background job (`zbx run ... &` in a
  script) or by a launcher that ignores it. The disposition is inherited through `exec`, an ignored
  signal is discarded by the kernel before zbx's signal wait can see it, and the container
  inherits the ignore too. The run simply goes on until the command ends.
- Recover: stop it with `kill -TERM` or `kill -HUP`; a non-interactive shell ignores only INT
  and QUIT for its background jobs. Or start the run from an interactive shell, or start the
  background job with job control on (`set -m` in the script). `trap - INT` and `setsid`
  do **not** undo an inherited ignore (checked with bash and dash: a background job started in a
  script has `SigIgn: 0000000000000006` in `/proc/<pid>/status`, with either; `set -m` gives
  zeros). zbx does not
  reset signal dispositions in M1.
