# M4 demo: pull

This document grows slice by slice and is finished by slice 5, which says how to run the demo,
what it asserts, how to do each spec step by hand, what was cut and how pulling fails. Until the
`demo-m4` job is green in CI and one top-20 run has passed, M4 is built, not demonstrated.

## Slice 1: references, registry, auth and manifests

`zbx pull --resolve-only <reference>`: the reference parser, the registry client with its
anonymous Bearer flow, OCI and Docker manifest reading with platform selection, digest checks, the
real network behind the host, a test registry in the harness, and the first `05xx` codes. It
resolves; it fetches no layer (slice 2) and writes no lock file or image record (slice 3).

### How a resolve goes

1. The reference is parsed (`E0501` with the reason if not). `alpine:3.20` is
   `docker.io/library/alpine:3.20`, reached at `registry-1.docker.io`; the first part of a name is
   a registry only with a dot, a port, or the name `localhost`.
2. `GET /v2/<repository>/manifests/<tag or digest>` with an `Accept` of the four manifest types.
   A `401` is answered once: its `WWW-Authenticate: Bearer` challenge names the realm, the service
   and the scope; the realm is asked for an anonymous token (no credentials); the request is
   repeated with `Authorization: Bearer`. A second `401` is `E0507`. A `429` is `E0506` with the
   registry's `Retry-After`; nothing retries, and nothing sleeps.
3. The bytes are hashed. If the reference was a digest, or the registry sent a
   `Docker-Content-Digest`, they must match (`E0511`). Nothing from a body is used before that.
4. The type is the body's `mediaType`, checked against the Content-Type when both are there
   (`E0510` if they differ, or if either is a type zbx does not read). An index is searched for
   this machine's platform (`uname -m`: `x86_64` is `linux/amd64`; `aarch64` is `linux/arm64`,
   variant `v8` or none). No match: `E0509` listing what the image offers. A manifest by
   itself is taken as it is.
5. The chosen entry's manifest is fetched by its digest, hashed, compared with the entry's size,
   and read: the config and every layer need a known media type, a sha256 digest and a size.
6. The command prints the digest of that manifest, the one a lock file will record.

The token is kept in the caller's workspace, is sent only to the registry's own origin (a
redirect to another host does not get it), and appears in no message, record or bundle.

### Decisions the brief left open

- **The digest `pull --resolve-only` prints is the platform manifest's**, not the index's. The
  index digest is in the JSON as `index_digest` (null when the reference named one manifest). The
  lock entry the brief describes has a manifest digest and a platform, which is this.
- **No tag and no digest means `latest`**, as Docker does. The brief says the parser refuses what is
  ambiguous; a missing tag is a convention, and the reference then has an explicit tag.
- **`pull` without `--resolve-only` is `E0006`** until slice 2 can fetch layers. The flag is not
  a stand-in for a dry run: it will stay as the "resolve and print" mode.
- **A registry on `localhost` or `127.x.y.z` is spoken to in plain HTTP**, as Docker and Podman do.
  It is also what lets the real network be tested over loopback. Everything else is HTTPS, and a
  redirect from HTTPS to HTTP is refused.
- **One connection per request** (`Connection: close`). A pull of a hundred blobs pays a TLS
  handshake each; it is simple and correct, and a pool can come later behind the same interface.
- **A body is limited to 1 MiB for a manifest, a token response to 32 KiB, a head to 16 KiB**,
  with a message for each (`constants.zig`, "Registry and pull").
- **Memory:** the registry client's workspace (1.6 MiB: the manifest body, the JSON arena, the
  token) is part of the command's static `Storage`; the real network has 2 MiB of static memory
  for the system's CA certificates, parsed once per process, and about 150 KiB of buffers. Nothing
  is allocated after startup.

### The standard library, checked as the spec asks

The pinned std (0.17.0) was read before use. What was adequate and what was not:

- **`std.http.Client` is not adequate and is not used.** It has no timeout on connect, on the TLS
  handshake or on a read. `connectTcpOptions` carries a `timeout` field it never uses, and the
  `Io.Threaded` connect panics with "TODO implement netConnectIpPosix with timeout". A socket
  with `SO_RCVTIMEO` is no way round it: the threaded `recvmsg` treats `EAGAIN` as a bug. A
  registry that stops answering would hang the command for ever.
- So `src/host_real_net.zig` opens its own sockets, waits with `poll` and a deadline on every wait
  (connect, handshake, each read, each write), and gives the TLS client and the HTTP reader a
  `std.Io.Reader` and `Writer` over the socket.
- **Used from std:** `std.crypto.tls.Client` (TLS 1.2 and 1.3, certificate and host verification,
  which worked against Docker Hub and GHCR through the proxy and directly),
  `std.crypto.Certificate.Bundle` (the system CA files; `SSL_CERT_FILE` is honoured, which
  std's `rescan` does not do), `std.Io.net.HostName` for name resolution (through the
  single-threaded `Io`; its timeouts are those of `resolv.conf`, not ours), `std.http.Reader` and
  `Client.Response.Head` for the response head and chunked bodies, and `std.json`.
- **Cost:** the TLS client, the certificate code and the `Io` they need are most of the growth of
  the binary (see "Checked" below).
- Not supported, and said so: IPv6 literal registries (the reference parser refuses them), HTTP
  proxies that need more than basic authentication, a `NO_PROXY` entry for an IPv6 range, and
  `Content-Encoding` on a response (zbx asks for `identity`; anything else is refused).

### What is cut

- Private registries and credentials (M4 is anonymous; the brief defers them).
- A bare manifest's platform is not checked against its config yet: slice 2 reads the config
  blob, and will refuse an image whose `architecture` is not this machine's.
- Connection reuse, `Range` requests (slice 2), and HTTP/2.
- No retry of any kind inside a command. A script retries; a `429` says when.

### What was checked, and against what

- Unit tests for every piece, in `zig build test`. The ones that carry the claims:
  - `client_tests.zig`: all nineteen scenarios of the test registry in the simulator, with the
    exact requests the flow makes (four for a token, three for a rejected token, never a loop),
    where the token goes (and where it does not), and a failure injected at every request index with
    every error the wire can report; 200 seeds of random failures, cut bodies and odd chunking.
  - the tests at the end of `host_real_net.zig`: the same nineteen scenarios over TCP on loopback
    through the real sockets, in normal and chunked framing; a peer that never answers
    (idle and total timeouts, within a second); a refused port; a garbage answer; a head and a
    body over their bounds; a full sink; a `CONNECT` with proxy credentials, a `407`, and a
    tunnel to a peer that does not speak TLS.
  - `pull_tests.zig`: the output in text and JSON against the schema, the usage errors, and the
    registry token in **no output of any mode**, success or failure, for every scenario.
  - `bundle_tests.zig`: a registry token response in a run record is redacted.
  - `diag_golden.zig`: a case for each of `E0501` to `E0513`, and `site/errors/` has their pages.
- Fuzzers (10,000 iterations, seed 1): `reference` (the parser against an oracle written in a
  different style, and the canonical form as a fixed point; it found one bug at once, `:3.20`
  reaching an assertion) and `registry` (the challenge parser, the manifest reader on mutated
  documents, and the whole client against a registry whose answers are cut, failed and changed:
  a resolve that succeeds always returns the digest of the manifest the registry really has).
  The `registry` fuzzer was checked by mutation: it fails when the digest comparison is removed.

  cause  the repository in 'Alpine:3.20' has an uppercase letter, which a repository never has

The first of these is not the error that was asked for: after about twenty resolves from this
container, Docker Hub's anonymous pull limit for its address was used up, and `E0506` is what a
real 429 looks like (Docker Hub sent no `Retry-After`, so the message has no wait). Before that,
`alpine:no-such-tag` gave `E0508` ("docker.io has no 'no-such-tag' in the repository
library/alpine"). The 429 also hit the second request of a resolve (the platform manifest), so a
resolve costs two of the limit's pulls; a pull of an image will cost one more per blob (slice 2).
Behind the proxy, `HTTPS_PROXY=http://127.0.0.1:43707` was used; with `HTTPS_PROXY` and
`https_proxy` emptied, the same command reached Docker Hub directly and gave the same digest.

Not tried here: TLS to a real registry without a proxy that re-terminates it (the direct run above
went through this container's transparent egress, which does the same), IPv6, a registry that
rotates its certificate, and the VM (this slice does not touch the runtime).

- The release binaries, ReleaseSafe and stripped: **x86_64 1,990,104 bytes and aarch64

| --- | --- | --- |

| the answer ends early | `E0513` | run again |

## Registry mirrors

Docker Hub limits anonymous pulls (`E0506` was seen live from the build container), so PR CI
reaches `docker.io` through `mirror.gcr.io`. The setting is the environment variable
**`ZBX_REGISTRY_MIRRORS`**: a comma-separated list of `host` or `host:port`, for example
`ZBX_REGISTRY_MIRRORS=mirror.gcr.io`. There is no config file in M4 (the brief asks for one only
"if one exists by then"; none does), so the variable is the only place, and the choice is
recorded here.

- For a `docker.io` reference a pull asks each mirror in order, then Docker Hub. For any other
  registry the setting is not used (but is still checked, so a typo is found at once: `E0514`
  names the entry).
- Up to four mirrors, 1024 bytes of setting; an entry is a DNS name with an optional port, no
  scheme and no path. A loopback host is spoken to in plain HTTP, any other in HTTPS.
- A mirror's answer is verified like Docker Hub's: the manifest by the digest it was asked for or
  the index lists, the blobs by the digest in the manifest. The client falls through to the next
  candidate only for a refusal another registry could answer differently: the mirror was
  unreachable or timed out (`E0502` to `E0505`), was rate limited (`E0506`), refused a token
  (`E0507`), did not have the image (`E0508`) or cut its answer (`E0513`). A wrong digest
  (`E0511`), an unusable document (`E0510`, `E0512`) or a missing platform (`E0509`) ends the
  pull at once, so a mirror can make a pull fail but never change what is pulled, and Docker
  Hub is not asked as a second opinion.
- The lock file records the reference as written, never the mirror. The token of one candidate
  is dropped before the next is tried.
- Tests (`client_tests.zig`, against the test registry, a mirror and Docker Hub as two hosts of
  one simulated network): a mirror that answers (Docker Hub gets no request); a mirror that is
  down (the first request fails, the second candidate answers, the earlier refusal leaves no
  diagnostic); a mirror that serves a wrong digest (`E0511`, no request to Docker Hub); a bad
  list (`E0514`, no request at all) and a non-Docker-Hub reference that ignores the list.

## Slice 2: blobs and layers to a tree

`zbx pull <reference>` goes on from the resolve: it downloads the config and the layers into the
store's blob cache (a cut download resumes), unpacks the layers in order into a staging directory
inside the store's user-namespace child, imports that directory as one tree, and records the
image. The tree digest is the image's identity; the tag is only how it was asked for. Slice 3 adds
the lock file, the image's configuration and `zbx run <tag>`; this slice stops at the tree.

| a layer blob read through its SHA-256 and gzip or zstd | `src/layer/reader.zig` |

| its diagnostics, `E0515`, `E0516`, `W0501`, `W0502` | `src/layer/diagnose.zig`, `src/diag/codes.zig` |
| the part of a pull that runs in the child | `src/pull_unpack.zig` |
| the part that runs in the parent | `src/pull_commands.zig` |

### How a pull goes

1. Resolve as in slice 1 (mirrors included). The reference is checked, the store is opened (made if
   it is new) and the **shared store lock is held for the whole pull**: the blobs are in the cache
   from the first byte to the record of the image that names them, and a `gc --confirm` in that time
   would take them.
2. For the config and then each layer, in manifest order: a blob that is in `blobs/sha256/<hex>` with
   the right length is `cached` and costs no request. Otherwise `blobs/partial/<hex>` is opened
   (made, or its bytes are hashed again and it is appended to) and the registry is asked for the
   blob, with `Range: bytes=N-` when there are bytes already. The place that answered the resolve
   is asked first, then the others in order, as for manifests.
   - `206` must start where the file ends (`Content-Range`); `200` means the registry ignored the
     range, and the file starts again; `416` removes the partial file and starts again.
   - A redirect (Docker Hub sends blobs to a CDN) is followed without the token. A `401` for a blob,
     because a token lasts minutes and a layer can take longer, gets a fresh token once.
   - The body goes through the hasher into the partial file; at its end the length and the SHA-256
     must be the manifest's, and only then is it renamed into `blobs/sha256/`. A cut body keeps its
     bytes (`E0513`); a wrong digest removes them (`E0511`), and a download that began from old
     bytes is tried once more from nothing before it is refused, since the old bytes may be what
     is wrong.
3. The child (user namespace, the same id map as every store command) makes `tmp/<pid>-<n>`, applies
   the layers to it, runs the existing import on it, writes `images/<manifest hex>`, removes the
   staging directory and prints the result. A pull that is killed leaves the staging directory in
   `tmp/`, where `gc` already removes the leftovers of dead processes.
4. Each layer is read through its SHA-256 once more while it is unpacked, and must still hash to
   its name: a blob that changed on the disk since it arrived is `E0511` with the file to remove.

### The layer applier

The OCI image specification's changeset rules, in `src/layer/apply.zig`:

- A file, directory or symlink replaces what is at its path; a file over a directory removes the
  directory and all it holds. A directory over a directory keeps its contents and takes the new
  mode, owner and attributes.
- `.wh.<name>` removes `<name>`; `.wh..wh..opq` empties its directory of what lower layers put there.
  **The opaque marker is taken to come before the other entries of its directory in the layer**, as
  Docker and BuildKit write it; entries of the same layer written before it are removed too. (A
  per-layer set of the paths written would close this; it was cut, see below.)
- A hard link is made as a link in the staging directory, to a regular file or a symlink that is
  already there; the import then makes separate entries of them, as in M3. A link to a file the
  image lacks is `E0516`.
- Devices, FIFOs and sockets are skipped and counted; one warning (`W0501`) names the first and the
  count. Nothing is created for them, not even a parent directory.
- `SCHILY.xattr.*` pax records are set when the store would keep them (`user.*` and
  `security.capability`, name at most 255 bytes, value at most 4096); the others are counted
  (`W0502`). A file system or namespace that refuses a kept attribute (`EPERM`, `EINVAL`,
  `EOPNOTSUPP`) is counted the same way; any other failure is a failure.
- Owners are applied with `chown` inside the child's namespace, so id 1000 in the tar is container
  id 1000. With the one-id map (`W0201`) every owner is root and nothing is chowned, as `store
  import` records it. An owner the namespace does not map is `E0516`, not a silent 65534.
- Modes are set after the owner, so setuid and setgid survive; times are set to the tar's.

**What is refused (`E0515`, the whole pull):** a path that is absolute; a path with `..`; a path
that goes through a symlink, whether the layer or a lower layer made it; a hard link to an absolute
or `..` path; a whiteout whose name is empty, `.` or `..`. The check is an `lstat` of every
directory on the way to an entry (the last verified directory is remembered, and forgotten when
anything is removed or replaced), so it does not rely on the file system refusing to follow a link.
**What cannot be unpacked (`E0516`):** a cut or corrupt compressed stream, a tar header with a bad
checksum or number, a sparse file or another type zbx does not read, a name over 255 bytes or a
path over 4095, a hard link to nothing, a parent that is a file, an owner that is not mapped, a
layer of more than 64 GiB of file contents, a zstd window over 8 MiB.

A write that fails anywhere in a pull is tested the way gc's are: for every third write point of a
whole pull the simulated disk fails there once (`ENOSPC`); the command ends in a coded diagnostic
or succeeds, the store is whole (`check_whole`), a staging directory is left only when the failure
was its removal, and the same command run again gives the same tree digest.

Checked: unit tests on the simulated file system (every refusal above, each with a check that
nothing outside the root was made); **a test on the real file system** (a layer that makes a
symlink to a directory outside the root and an entry through it, which the kernel would follow:
refused, nothing planted; modes, a hard link with two links, a whiteout and an opaque directory as
a real kernel keeps them); layers made by real tools (`gzip -9` and libzstd level 19, many blocks,
noise, pax records, long names); and the `layer` fuzzer, which builds one or two layers of colliding
names (files, directories, links to `/outside` and `..`, whiteouts, opaque markers, devices, names
that are absolute or climb), wraps them in gzip or zstd, damages some, and applies them. Its
properties: no crash; nothing created outside the staging directory; **nothing written through a
symlink** (the simulated file system panics when asked about a path with a link above its last
part, which a real one would have followed); and a success means the intact archive had no hostile
name or link. Checked by mutation: making the applier skip a `..` fails the fuzzer at once (the
fourth property); making it accept a symlink on the way fails the unit test for that case (the
simulator's panic on a link above a path is a second line of defence in the fuzzer).

### Decisions the brief left open

- **The blob cache is verified twice**: when it arrives (so a wrong blob never enters the cache) and
  when it is unpacked (so a blob that rotted on the disk is found before it becomes a tree). The
  second costs one SHA-256 pass over the compressed bytes.
- **Our own tar reader, not `std.tar`.** `std.tar.Iterator` drops the uid and gid and every pax
  record it does not know, and a layer needs the owners and `SCHILY.xattr.*`. It is 400 lines with
  a checksum, base-256 numbers, GNU long names and pax; `std.tar` was read first and its pax and
  number handling informed this one.
- **The standard library's decoders, checked**: `std.compress.flate` decodes gzip in a 64 KiB
  window and is fine; it reads one gzip member, and bytes after it are ignored (a layer of
  concatenated members would end early, which the digest check cannot see because the blob hash
  covers the file; none has been seen). `std.compress.zstd` decodes with an 8 MiB window plus a
  block; **it does not verify the content checksum** (its option panics if set), which does not
  matter here because the blob's SHA-256 covers every byte. A frame that asks for a larger window
  (`--long`) is refused as damaged with the decoder's word, `WindowOversize`. Both took real
  compressed data in the tests above.
- **The staging directory is `tmp/<pid>-<n>`**, the name `gc` already treats as a leftover when the
  process is gone, so a killed pull needs no new cleanup.
- **An image record is written in this slice** (`images/<manifest hex>`, `store/images.zig`): the
  reference as written, the manifest, the platform, the config blob, the tree, the time and the
  layer blobs. gc needs it to know which blobs are live, and the brief's slice 3 builds on it (it
  adds the image's configuration; a reader skips keys it does not know). Keyed by the manifest, a
  second pull of the same manifest replaces it, and two tags of one image are one record.
- **`zbx pull` prints the manifest digest** (the line `--resolve-only` prints), and with `--output
  json` the object `zbx.pull/1` (`zbx schema pull`): the reference as written, the manifest, the
  platform, the tree digest, how each blob came (`cached`, `downloaded`, `resumed`), and the counts
  of what was unpacked.
- **Blobs of a docker.io image come from the same candidate that answered the resolve first**, then
  the others, so a mirror that has the manifest but not a blob falls back to Docker Hub; a blob
  from any of them is checked by its digest.

### gc: blobs, images and the limit

- `blobs/sha256/<hex>` is a new class of thing in the plan and the trash (`trash/<gc>/blobs/`). A
  blob is live while an image record names it as its config or a layer; an unnamed blob is planned
  with the objects and trees, moved to the trash by an apply, and restored by a restore. A blob
  downloaded again after a gc is the same bytes, so a restore never calls it a conflict. Cut
  downloads in `blobs/partial/` are gc's only when abandoned (review fix, below).
- An image record is a root of its own: it keeps its tree (also when the tree's root record is gone)
  as well as its blobs. A record that cannot be read stops the gc, like a damaged root record.
- **The limit is lifted by sizing the sets to the store, in bounded caller-provided storage.** The
  brief offers growth in bounded storage or paging; this is the first. The ~49,000-object limit came
  from fixed 5.5 MiB sets of 48-byte slots. Now a plan counts what is stored (256 directory reads of
  `objects/` and of `trees/`; a kept object is a stored object, so the count is an upper bound) and
  sizes the sets to it, at three quarters full, in a region the caller provides (`store_gc_tables_bytes`, 64
  MiB, for `zbx` a static zero one: it takes no space in the program's file and none in memory until
  a plan uses it, so a small store touches a few KiB). The slots are 16 bytes (`sets.KeySet`: the first 128
  bits of the digest; two digests that agree there are taken for one, which can only make gc keep
  something that could have gone, at 2^-128 per pair). **About 1.5 million objects and 780,000 trees
  fit**; a store beyond that is refused with a message naming the tables, never cut. Tested on the
  sizing (`plan_tables`: 100,000 and a million objects fit, a hundred million is refused) and on
  the behaviour (blobs, images and the cycle plan, apply, restore); a simulated disk cannot hold
  49,000 files, so the old limit itself is not exercised by a test of that size.
- **The region belongs to the caller** (review fix; the rule is "Storage belongs to the caller" in
  m2.md). `gc.Workspace.tables` is a slice the caller sets, at least `gc.tables_bytes_min` (about
  3.1 MiB: the removal arena, the roots' set and the blobs' set, and room for a small store) and
  `constants.store_gc_tables_bytes` (64 MiB) for a store of about 1.5 million objects. `cli.Storage`
  has `gc_tables` for it. The `zbx` program owns one static zero region in `main.zig` (bss: nothing
  in the file, nothing in memory until a gc sizes the sets). A library user passes its own; the
  tests use 16 MiB. `gc_tests.zig` has a test with two callers, each with a store and a region of
  its own, planned in turn and then on two threads at once: the same plans. The module keeps no
  state for gc. (`cli.shared_storage`, for the tests and fuzzers, carries an 8 MiB region of its own.)

- **Abandoned cut downloads are gc's** (review fix). A `blobs/partial/<hex>` whose last write is
  older than `constants.store_partial_seconds` (24 h) is planned as its own class (`partials` in the
  counts and the JSON, `trash/<gc>/partial/`, restored by `restore`; a restore refuses if a new
  download of the same blob has begun since). The age is the file's modification time (`Stat.mtime`
  is new). No pull is writing a file that old, and an apply takes the store lock exclusive, which a
  running pull holds shared. A pull that finds its partial gone starts that blob again. Test:
  `gc_tests.zig` ("abandoned cut downloads are planned, trashed and restored; recent ones stay").

## Slice 3: images and running

`zbx run alpine:3.20 -- cat /etc/os-release` and `zbx run python:3.12-slim -- python -c
'print(2**100)'` work, the first as the first thing in a project with no lock (it pulls, writes

### What is where

| --- | --- |

| the demo's part | `src/testing/vm/main_m4.zig`, `checks_m4.zig` |

### The image record carries the configuration

`pull` reads the config blob (checked by its digest when it arrived) and keeps five members:
`Entrypoint`, `Cmd`, `Env`, `WorkingDir`, `User`. They are in the record as lines (`.entrypoint`,
`.cmd`, `.env` once for each word, `.workdir`, `.user`; empty ones are left out), so an old
record without them reads as an image that sets nothing. Bounds: 48 words in a list, 64
variables, 1024 bytes a word and 6 KiB in all; an image beyond them is `E0517` and nothing is
recorded. `--output json` of a pull has them in `image`, and `lock` (`{path, created}`, or `null`
for a digest reference).

### `zbx.lock`

ZON, one field a line, sorted by reference, with a version. It is read line by line, so a hand
edit works (the demo does one). Written through a temporary file in the same directory that is
renamed over it, and flushed. **The file keeps the time it was written**: a store file gets the
fixed 2000-01-01 mtime, and the first version of the lock did too (seen with `ls -l` on a real
run); `Fs.write_atomic_stamped` has the choice. The lock is the nearest `zbx.lock` from the
working directory up; with none, the working directory gets one.

- `zbx pull <ref>` adds or updates the entry (a second spelling of the same image, as
  `docker.io/library/alpine:3.20`, is the same entry, and keeps the first text). A pull by a
  digest reference needs no lock and leaves it alone. A damaged lock stops the pull before any
  download (`E0518`, with the line).
- The lock never has a mirror in it: it records the reference as written. Tested with a mirror
  named, and the file searched for it.
- 256 entries at most (`E0518`, "past the entries a lock holds"; the bound is a constant).

### Running by name

The operand of `run` is a tree digest (`b3:` and hex, or 12 hex digits or more, as before) or
else an image name. The shape decides, and it is documented in the help: a name that is also
hex of 12 digits or more would be read as a digest.

| Situation | Result |
| --- | --- |
| `alpine:3.20`, lock has it, the store's record of the locked manifest has the locked tree | runs that tree |
| the lock's tree is not the record's | `E0519`, both trees in the message, exit 125 |
| the lock's manifest has no record | `E0520`, the locked manifest and, if the store has another under the name, that one; the fix is `zbx pull repo@sha256:...` |
| a lock exists and lacks the name | `E0522`, the fix is `zbx pull <name>` |
| no lock anywhere up | pulls (nothing of it on stdout), writes the lock in the working directory, `W0503`, runs |
| `alpine@sha256:...` | the store's record of that manifest, no lock; `E0522` if there is none |
| a lock that cannot be read | `E0518` |

It never pulls once a lock exists. The library's `Spec.image` also takes a name: the store's
newest record pulled as it (`runtime/image.zig`); the cli's way through the lock is `run_image.zig`
(the cli hands the library the tree).

The settings become what the container is started with, as Docker does: `entrypoint` then the
words after `--`, or the image's `cmd` if there are none; the image's environment (`PATH` among
it; the plan looks for a bare command in that `PATH`, up to 16 directories); a working directory
made if the image lacks it (a plan step in the child, after the new root is entered); and the user.
**`User`** is `name`, `uid`, `name:group`, `uid:gid`... resolved against the tree's own files
(`image_user.zig` reads `/etc/passwd` and `/etc/group` from the store, not following a symlink); a
number is never looked up for itself; an unknown name is `E0521`. `HOME` comes from passwd (`/` if it
does not say) unless the image sets one. The step that becomes the user (`setgroups` empty, group,
user) is after the capabilities are restricted and before `no_new_privs` and the filter. Without
the full id map only root exists: `E0523`, before anything is created. Supplementary groups are
not set. `HOME` for root stays `/root`.

### `/sys`

Every container gets the host's `/sys` bound recursively and made read-only (`mount_setattr` with
`AT_RECURSIVE`; the top mount only where the call is missing). Three plan steps, **all tolerant** (a host that
refuses the bind, or a root file system that cannot take the directory, gives a container without
`/sys` and a note). The first version made only the two mounts tolerant, and `demo-m2` under TCG
caught it: its failure mode "--read-only, no /tmp, rootfs not writable" expects `E0209` for the
`/tmp` it cannot make, and got `E0205` for the `/sys` it could not make first. The leak is the brief's:
**the host's network devices (`/sys/class/net`) and its other sysfs are visible** until M5 gives
the container a sysfs of its own. Seen in a real run: `sysfs on /sys type sysfs (ro,relatime)`,
and the cgroup submounts below it read-only too.

### Store commands

- `store ls` lists the roots, then (text: a second table; JSON: `images`) the pulled images by
  reference, manifest, platform, tree and time.
- `store rm <tree>` removes the tree's image records and then its root (a tree that is only an
  image, its root already gone, is accepted). A pulled tree is kept by its image record as well
  as by its root, so removing the root alone would have freed nothing. The lock is not changed:
  the next `zbx run` of the name says `E0520` and gives the pull.
- `store du --by-image` (text and JSON): files, logical bytes, **compressed** bytes (the layers as
  downloaded, from the blob cache), stored bytes and shared bytes (what other roots also use) for
  each image. `--by-image` takes no digest.

### Decisions the brief left open

- **`zbx run <name>` with `--` optional**: the command is only required for a rootfs or a tree
  digest. A tree digest has no image to take it from.
- **`zbx.lock` entries are keyed by canonical reference**, stored as written. Looking one up does
  the parse twice per entry, bounded by 256 entries.
- **The run of a name that is an image with no entrypoint and no cmd** is `E0524`.
- **The warning `W0503`** is a diagnostic block on stderr (the brief says "say so in one line"; the
  rest of the program has no plain note, and the block's cause line is one sentence).
- **The environment bound** went from 32 to 64 variables (`Spec.env`), because real images set
  more than a handful. A variable name over 64 bytes or a value over 4096 is refused by the
  runtime as before (`E0008`).
- **Images with a `USER` in a test**: `memcached:alpine` for the real checks (`USER memcache`).

## Slice 4: the top-20 check

`zig build top20` pulls the twenty most-pulled official images of Docker Hub and runs each one's
default command in the test VM, rootless. It is a separate job (`.github/workflows/top20.yml`):
weekly (Monday 04:17 UTC) and on `workflow_dispatch`, never on a pull request, against the real
Docker Hub (the PR demos use the mirror). Until the workflow is on `main`, a push to a
`vm/top20-<x>` scratch branch also runs it (`vm.yml` ignores those branches). Locally,
`zig build top20 -Daccel=tcg -Dmirror=mirror.gcr.io [-Dca-file=...] [-Donly=redis,nginx]` runs it
under software emulation (about 55 minutes for all twenty); `-Donly` is a development aid.

### What is where

| What | Where |
| --- | --- |
| the twenty images, the date and source, each one's known reason and probe | `src/testing/vm/top20.zon` |
| the run: pull, run, probe, strace, one line per image | `src/testing/vm/main_top20.zig` |
| the judgement as pure functions, unit-tested | `src/testing/vm/checks_top20.zig` |
| the workflow | `.github/workflows/top20.yml` |

### How an image is judged

One result line per image, fields in a fixed order (cut at ` | `):
`ref | pulled | ran | exit | verdict | seccomp | probe | reason`. The run fails if any verdict is
`fail`; it prints `top20: N passed, N known not to run, N failed` last.

- **pull**: `zbx pull <ref>` must exit 0. A failed pull is `fail` always: a known reason never
  excuses a pull (an earlier version did, and a TLS failure showed as "known").
- **run**: `zbx run --timeout 45000 <ref>` with stdin from `/dev/null`. `ran` is "zbx started the
  command" (exit not 125 to 127). Exit 0 passes. A container that is still up when `--timeout`
  stops it (`zbx: stopped: timed out after`) passes whatever code it answers SIGTERM with (redis
  0, mongo 143, registry 2): a server that stays up for 45 s has run.
- **probe** (servers only): while the run is in the background the guest, as root, connects to
  127.0.0.1 (the container shares the host network) every 2 s for up to 44 s, writes a request and
  looks for text in the first line of the reply. A server that is up but does not answer is `fail`
  (reason: what the last try got). Probes: redis `PING` / `PONG`; memcached `version` /
  `VERSION`; registry `GET /v2/` / `200`; mongo and rabbitmq a TCP connection only (their wire
  protocols need a client the guest lacks); nginx, httpd and traefik `GET /` / `HTTP/` (never
  reached today, see below).
- **known**: an entry with a `known` reason that does not pass is `known`, and the line carries
  the reason. The harness still runs it, so an image that starts passing prints a `NOTE` line and
  the note is removed in a reviewed change. Every `known` entry was seen to fail in the
  CI run for the stated reason (the message is in the job log).
- **seccomp**: an image that does not pass is run again under `strace -f -e status=failed`; every
  syscall that returned EPERM and is not on the allowlist by name is listed in `seccomp=`
  (`none` when there is none, `unchecked` without strace). A name with a rule (`socket`, `clone`)
  is not on the plain list, so it shows too; read it with the reason. A seccomp EPERM is therefore
  told from every other failure by that field and by a `top20: SECCOMP:` line.
- **silence**: a failure with nothing on stderr says `failed with nothing on stderr`; nothing
  fails without a line.

The guest's disk is 8 GiB and holds one image at a time: the store and the lock are removed after
each image (the first full run filled the disk at the seventh image: `E0416`).

The seven `known` images, and how each was found to be so:

- nginx, httpd, traefik: `bind() to 0.0.0.0:80 failed (13: Permission denied)` (nginx printed it).
  The container shares the host network and an unprivileged user may bind only ports from 1024
  (`net.ipv4.ip_unprivileged_port_start`). Setting that sysctl is a host change zbx does not make.
  Not a seccomp refusal (`seccomp=none`).
- postgres, mysql, mariadb: the entrypoint exits 1 asking for a password variable; `zbx run` sets
  no environment variable yet. That is a missing feature, not a runtime fault.
- docker: its entrypoint starts `dockerd`, which needs `mount`. The profile refuses it on purpose
  (`seccomp=mount socket`), and a user namespace holds no host capability to mount with.

### Seccomp: what the runs found

The allowlist grew from real failures, each with a reason in `policy/seccomp.zon` and a test in
`src/runtime/seccomp.zig` ("what the top-20 run found is allowed, and its neighbours that change
things are not"): `get_mempolicy` (a NUMA read that mongod and some allocators call at start) and
`fchmodat2` (glibc 2.39's `chmod` on a symlink; a JVM asked). Both were found by an earlier
local run under TCG, before a container restart; that run's log was lost, so what is recorded
here is the earlier commit's finding and the CI run above, in which mongo and openjdk pass with
both allowed. `io_uring_setup` (seen from redis) is refused and stays refused: redis falls back
and passes.

### Bugs the runs found

- nginx: `zbx run` failed with `E0419` and a `B0001` bug report. The store worker hit an
  assertion in `xattrs.section_length`: it asserted that the rest of a tree object was under the
  file-size limit, but that is every later entry of a directory (nginx's `/usr/lib` has thousands),
  megabytes. Fixed (the assertion now bounds what it must: offsets fit in `u32`), with a test of
  a section at the start of a 200 KiB buffer (`src/store/xattrs.zig`). It is not the cause of any
  fuzzer seed. `E0419`'s own text says the namespace "could not be set up" even when the worker
  was killed by a signal; the cause line comes from the generic path.
- the harness: root could not redirect into the demo user's file in `/tmp`
  (`fs.protected_regular`), so every pull failed with an empty reason; an image whose last output
  line has no newline (jshell's prompt) hid the stream marker; a probe built on `head -c` lost its
  buffer when killed. All three are fixed and were found by running it.
