# M2 demo: limits and hardening

This document grows slice by slice. Slices 1 (the D-Bus client and the scope), 2 (exit reasons
and cleanup) and 3 (hardening) are written; the demo script, the by-hand steps, the cuts and the failure modes
arrive with slice 5 (`docs/briefs/M2-limits.md`).

## How a container gets its cgroup (slice 1)

Each container runs in a transient systemd **scope** of the user's systemd manager, named
`zbx-<container name>.scope`. `zbx` asks for it by speaking the D-Bus wire protocol itself
(`src/dbus/`, standard library only; no libsystemd, no libdbus, no `systemd-run`):

1. **Find the bus.** `DBUS_SESSION_BUS_ADDRESS` (only `unix:path=`), else `$XDG_RUNTIME_DIR/bus`.
2. **Probe, before anything is created.** Connect, authenticate with SASL `EXTERNAL` (the uid as
   hex of its decimal text), say `Hello`, read the manager's `Version`.
3. **Decide.** With the manager, the run has a scope. Without it, a run that asks for a limit
   (`--memory`, `--pids`, `--cpus`) is refused (`ZBX-E0307`); a run that asks for none goes on,
   warning once (`ZBX-W0301`), as in M1.
4. **Start the scope, inside the plan.** The plan has a `start_scope` step between the id maps and
   the go-ahead to the child. The parent calls `StartTransientUnit(name, "fail", properties, [])`
   with the child's pid, then waits for `JobRemoved` with result `done`. Only then is the child
   released to run, so nothing it does happens outside the scope or its limits.
5. **The properties.** `PIDs=[child]`, `Delegate=true`, `Slice=app.slice` (systemd 247 and later;
   older managers use their default), `CPUAccounting`, `MemoryAccounting`, `IOAccounting` and
   `TasksAccounting`, `Description=zbx: <name>`, and the limits: `MemoryMax` and `MemorySwapMax=0`
   for `--memory`, `TasksMax` for `--pids`, `CPUQuotaPerSecUSec` for `--cpus`.
6. **Old systemd.** A property the running systemd does not have (`MemoryMax` before 231,
   `MemorySwapMax` before 232, `TasksMax` before 227, `CPUQuotaPerSecUSec` before 213) is left out
   of the request, and the limit is written to the scope's own cgroup file (`memory.max`,
   `memory.swap.max`, `pids.max`, `cpu.max`), found through `/proc/<pid>/cgroup`.
7. **A taken name** is never reused: mode `"fail"` makes systemd answer `UnitExists`, which is
   `ZBX-E0305`.
8. **Job signals are asked for.** Before `StartTransientUnit` zbx adds the `JobRemoved` match rule
   and calls `Manager.Subscribe`, and it calls `Unsubscribe` after the wait (as go-systemd does);
   it does not rely on systemd telling the creator of a job. The wait is bounded (30 s).
9. **An inherited bus address.** `su` and `sudo` leave another user's
   `DBUS_SESSION_BUS_ADDRESS` in the environment. If connecting to the address is refused for
   permission (`EACCES`, `EPERM`), or authentication on it fails, and it is not
   `/run/user/<own uid>/bus`, zbx tries that path once. `--verbose` says which address worked; if
   both fail, the diagnostic tells both stories. A missing socket is not retried (a stale address
   is a different problem from someone else's bus).

The limits are checked before anything starts: `--memory` 4 MiB to 1 TiB in binary units
(`k`, `m`, `g`), `--pids` 1 to 4194304, `--cpus` 0.01 to 1024 with at most three decimals. Anything
else is `ZBX-E0306`.

## How a container ends (slice 2)

When PID 1 of the container has been reaped, and before anything else, zbx reads the scope's
`memory.events` (`oom_kill`) and `pids.events` (`max`) from its cgroup (found through
`/proc/<pid>/cgroup` when the scope started):

| the cgroup says | the reason | zbx exits with | stderr (text) |
| --- | --- | --- | --- |
| `oom_kill` above 0 | `oom` | 137, whatever PID 1 did | `zbx: killed: out of memory (limit 128 MiB)` |
| else `max` above 0 | `pid_limit` | PID 1's own code | `zbx: stopped: process limit reached (limit 64)` |
| neither | `signal` or `exited` | as in M1 | as in M1 |

Decisions (the supervisor's): any OOM kill makes the reason `oom` and the code 137, even if PID 1
exited 0 (a worker was killed and the main process went on); `--verbose` then prints what PID 1
did (`zbx: note: the container's first process exited with code 0`), so nothing is hidden. Any
refused fork makes the reason `pid_limit`, and PID 1 keeps its code. An OOM kill outranks the
process limit. With no `--memory` the line has no limit (an ancestor's limit, or the machine's,
killed it).

`--output json` ends with `{"container_exit":{"reason":"oom","limit_bytes":N|null,"code":137}}`,
`{"reason":"pid_limit","limit":N|null,"code":C}`, `{"reason":"signal","signal":N,"code":128+N}` or
`{"reason":"exited","code":N}`.

The race: systemd removes a scope's cgroup when its last process is gone, so a cgroup that is
already gone cannot be read. Then the run is reported as the plain exit it was (nothing is claimed
without evidence). In the guest the files were readable every time (twelve OOM runs over three boots, the PID 1
that is itself killed included), but there is no guarantee; a library caller that needs one should read
`memory.events` while the container runs.

**Cleanup.** After the exit zbx looks for the scope's cgroup. If it is there, zbx asks the manager
to stop the unit (`StopUnit`, after the same `Subscribe`): `NoSuchUnit` means it went by itself;
otherwise the stop job is waited for. Then it looks again; a cgroup still there, or a manager that
refuses, is the warning `ZBX-W0302` (the exit code is still the container's). `--verbose` says
which of the three it was. A run that fails after its scope was made is cleaned up the same way
(not after a taken name: that scope is someone else's).

**Run record version 2** adds `.reason`, `.detached`, `.scope` and the three `.limit_*` fields. A
version 1 record reads unchanged with no limits, no scope, not detached, and the reason its exit
implies (the upgrade test is `exit_tests.zig`). A version 3 record is skipped as newer.

## Hardening (slice 3)

Between `seal_descriptors` and `exec` the child makes four calls, always, in the order the kernel
needs (plan steps `restrict_capabilities`, `clear_ambient`, `set_no_new_privs`,
`install_seccomp`); the filter is the last thing it does before `execve`. A failure of any is
refused as `ZBX-E0207` (capabilities) or `ZBX-E0208` (`no_new_privs`, seccomp), naming the step;
a container is never started less restricted than asked.

- **Capabilities** (`src/runtime/policy/capabilities.zon`, one reason per entry): `CHOWN`,
  `DAC_OVERRIDE`, `FOWNER`, `FSETID`, `KILL`, `SETGID`, `SETUID`, `SETPCAP`, `NET_BIND_SERVICE`,
  `SYS_CHROOT`, `AUDIT_WRITE`, `SETFCAP`: Docker's default without `NET_RAW` and `MKNOD`, and no
  `SYS_ADMIN`. Every other capability is dropped from the bounding set, and the effective,
  permitted and inheritable sets are set to the list; the ambient set is emptied. In the guest
  `/proc/self/status` shows `CapInh/CapPrm/CapEff/CapBnd: 00000000a00405fb`, `CapAmb: 0`
  (Docker's `a80425fb` less the bits of `NET_RAW` and `MKNOD`).
- **`no_new_privs`** is always set.
- **Seccomp** (`src/runtime/policy/seccomp.zon`): an allowlist of 64-bit syscalls in eleven
  groups with a reason each, plus Docker's argument rules: `clone` may not create namespaces,
  `personality` takes only its usual values, `socket` refuses `AF_VSOCK`; `clone3` answers
  `ENOSYS` (its flags are in a struct a filter cannot read, so libc falls back to `clone`).
  Everything else fails with `EPERM`, not a kill. `src/runtime/seccomp.zig` compiles the file at
  build time into one classic BPF program for x86_64 and aarch64 (599 instructions: 285 syscalls on
  x86_64, 248 on aarch64, checked by a verifier and an interpreter in `bpf.zig`); a foreign architecture, the 32-bit
  entry above all, gets `EPERM`. A name that is on neither architecture's table is a build error.
  Differences from Docker, in the file's header: no 32-bit variants, no `io_uring`.
- **`--read-only`** adds five steps before `pivot_root`: the mount points `/tmp` and `/run` are
  made in the rootfs if missing (while it is still writable), a tmpfs (`tmpfs_bytes_max`, 64 MiB;
  mode 1777 and 0755; nosuid, nodev) is mounted on each, and the rootfs bind mount is remounted
  read-only, keeping the flags it has (the kernel requires that in a user namespace; the host
  reads them with `statfs`). A mount point that cannot be made, a mount or the remount that is
  refused is `ZBX-E0209`. Note: the container's root can write any directory whose owner is
  mapped, whatever its mode, so "not writable" here means owned by an id the container does not
  map (a root-owned rootfs).

What the simulator and the fuzzers check: the BPF programs against an independent reading of the
policy (`zig build fuzz -- seccomp`: random policies, damaged programs, random instructions, the
shipped program), the new steps faulted one by one (`run` fuzzer and the walk in `run_tests.zig`),
and that a started container has the capabilities, `no_new_privs` and a filter that still allows
`execve`, `write`, `close` and `exit_group`.

## Departures from runc's systemd driver

[runc's systemd driver](https://github.com/opencontainers/runc/blob/main/docs/systemd.md) is the
reference (`docs/DECISIONS.md`). What is taken: one transient scope per container; `Delegate`,
`Slice` and the accounting properties; limits as unit properties where the running systemd has
them, and cgroupfs files where it does not; properties chosen by the systemd version.

What is dropped, and why:

- **`cgroupsPath` (`slice:prefix:name`) and the `org.systemd.property.*` annotations.** They exist
  because runc takes an OCI `config.json`. `zbx` has no such input: the unit is always
  `zbx-<name>.scope` and its properties come from `zbx`'s own flags.
- **A system bus.** runc may talk to the system manager as root. `zbx` is rootless and only ever
  talks to the user's manager.
- **`Subscribe` and the unit-state signals.** The only signal `zbx` needs is `JobRemoved`, which
  systemd sends to the client that started the job; `zbx` adds a match rule for it and reads
  nothing else.

## What was checked, and against what (slice 1)

- Unit tests and the golden tests run against the simulator, whose bus speaks the same wire
  format (`src/sim_bus.zig`). It is built with the same marshaller, so it cannot by itself show
  that the marshaller is right.
- `zig build dbus-live` runs the client against a real `dbus-daemon` (CI runs it under
  `dbus-run-session`): Hello, `GetId`, `ListNames`, `AddMatch` with a real signal, the
  `StartTransientUnit` and `Properties.Get` messages (which the daemon validates before routing),
  a `JobRemoved` signal waited for, and a malformed body that the daemon refuses.
- The VM demos (`demo-m0`, `demo-m1`) run `zbx` as a user whose systemd user manager is real, so
  every `zbx run` there makes a real scope.

## What was checked, and against what (slice 2)

- The simulator (`sim_bus.zig`, `sim_world.zig`) models Subscribe-gated `JobRemoved`, `StopUnit`
  (unknown unit, refusal, a job that is not "done", a cgroup that stays), the manager's lateness
  in removing a scope, the kernel's event files, and an inherited socket that is another user's.
  Unit tests (`exit_tests.zig`, `client_tests.zig`) and the `run` fuzzer (OOM, process limit,
  removal timing, stop faults, inherited addresses, record version 2) run against it.
- `zig build dbus-live` (a real `dbus-daemon`, no systemd) routes `Subscribe`, `StartTransientUnit`
  and `StopUnit`.
- `zig build vm-m2-experiment -Daccel=tcg` (not the demo) ran against the guest's real systemd 255
  and kernel 6.8, TCG: `--pids 16` with a loop that starts 40 sleeps; a fork bomb with
  `--pids 64`; `--memory 32m` with a hog that is PID 1 (three times) and one that is a child; the
  limit files of a running container; the scope gone from `/sys/fs/cgroup` and from
  `systemctl --user list-units` after every run; an inherited `DBUS_SESSION_BUS_ADDRESS` naming
  root's bus. Not exercised for real: a stop job that has to end a still-live scope (every run's
  scope had already gone, or answered `NoSuchUnit`), and the cgroupfs fallback for an old systemd.
- **For the demo script (slice 5):** Alpine's busybox `sh` refuses `:(){ :|:& };:` ("bad function
  name"), and a bomb whose PID 1 exits at once ends the container before it forks 64 times (no
  limit hit, exit 0). `sh -c 'b(){ b|b& }; b; sleep 3'` with `--pids 64` reports the limit.

## What was checked, and against what (slice 3)

`zig build vm-m2-experiment -Daccel=tcg` (systemd 255, kernel 6.8, Alpine 3.20 busybox, TCG):

- `/proc/self/status` inside: `NoNewPrivs: 1`, `Seccomp: 2`, `CapEff` and the other sets
  `00000000a00405fb`, `CapAmb: 0`.
- `mount -t tmpfs none /mnt` fails: busybox prints `mount: permission denied (are you root?)`
  for the kernel's `EPERM` (it is busybox's wording; `hostname changed` prints `sethostname:
  Operation not permitted` for the same errno).
- `unshare -U true` fails with `unshare(0x10000000): Operation not permitted`. Creating a user
  namespace needs no capability, so this is the filter, not the capability set.
- `chown` of a file works (`CAP_CHOWN` is kept); a pipeline, `ps` and a subshell work.
- `--read-only`: `touch /x` and `echo hi > /etc/f` fail with `Read-only file system`;
  `touch /tmp/x` and `touch /run/y` work; the mount table shows `/ ro`, `/tmp rw,nosuid,nodev`,
  `/run rw,nosuid,nodev`.
- The slice 1 and 2 checks (limits, OOM, process limit, cleanup, fallback) were repeated under the
  filter with the same results.
