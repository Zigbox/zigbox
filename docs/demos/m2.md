# M2 demo: limits and hardening

This document grows slice by slice. Slices 1 (the D-Bus client and the scope), 2 (exit reasons
and cleanup), 3 (hardening), 4 (the library for Zigcube) and 5 (the demo, `zig build demo-m2`)
are written. The demo is described last, in "The demo (slice 5)".

## How a container gets its cgroup (slice 1)

Each container runs in a transient systemd **scope** of the user's systemd manager, named
`zbx-<container name>.scope`. `zbx` asks for it by speaking the D-Bus wire protocol itself
(`src/dbus/`, standard library only; no libsystemd, no libdbus, no `systemd-run`):

1. **Find the bus.** `DBUS_SESSION_BUS_ADDRESS` (only `unix:path=`), else `$XDG_RUNTIME_DIR/bus`.
2. **Probe, before anything is created.** Connect, authenticate with SASL `EXTERNAL` (the uid as
   hex of its decimal text), say `Hello`, read the manager's `Version`.
3. **Decide.** With the manager, the run has a scope. Without it, a run that asks for a limit
   (`--memory`, `--pids`, `--cpus`) is refused (`ZBX-E0307`); a run that asks for none goes on,
   warning once (`ZBX-W0301`), as in M1.
4. **Start the scope, inside the plan.** The plan has a `start_scope` step between the id maps and
   the go-ahead to the child. The parent calls `StartTransientUnit(name, "fail", properties, [])`
   with the child's pid, then waits for `JobRemoved` with result `done`. Only then is the child
   released to run, so nothing it does happens outside the scope or its limits.
5. **The properties.** `PIDs=[child]`, `Delegate=true`, `Slice=app.slice` (systemd 247 and later;
   older managers use their default), `CPUAccounting`, `MemoryAccounting`, `IOAccounting` and
   `TasksAccounting`, `Description=zbx: <name>`, and the limits: `MemoryMax` and `MemorySwapMax=0`
   for `--memory`, `TasksMax` for `--pids`, `CPUQuotaPerSecUSec` for `--cpus`.
6. **Old systemd.** A property the running systemd does not have (`MemoryMax` before 231,
   `MemorySwapMax` before 232, `TasksMax` before 227, `CPUQuotaPerSecUSec` before 213) is left out
   of the request, and the limit is written to the scope's own cgroup file (`memory.max`,
   `memory.swap.max`, `pids.max`, `cpu.max`), found through `/proc/<pid>/cgroup`.
7. **A taken name** is never reused: mode `"fail"` makes systemd answer `UnitExists`, which is
   `ZBX-E0305`.
8. **Job signals are asked for.** Before `StartTransientUnit` zbx adds the `JobRemoved` match rule
   and calls `Manager.Subscribe`, and it calls `Unsubscribe` after the wait (as go-systemd does);
   it does not rely on systemd telling the creator of a job. The wait is bounded (30 s).
9. **An inherited bus address.** `su` and `sudo` leave another user's
   `DBUS_SESSION_BUS_ADDRESS` in the environment. If connecting to the address is refused for
   permission (`EACCES`, `EPERM`), or authentication on it fails, and it is not
   `/run/user/<own uid>/bus`, zbx tries that path once. `--verbose` says which address worked; if
   both fail, the diagnostic tells both stories. A missing socket is not retried (a stale address
   is a different problem from someone else's bus).

The limits are checked before anything starts: `--memory` 4 MiB to 1 TiB in binary units
(`k`, `m`, `g`), `--pids` 1 to 4194304, `--cpus` 0.01 to 1024 with at most three decimals. Anything
else is `ZBX-E0306`.

## How a container ends (slice 2)

When PID 1 of the container has been reaped, and before anything else, zbx reads the scope's
`memory.events` (`oom_kill`) and `pids.events` (`max`) from its cgroup (found through
`/proc/<pid>/cgroup` when the scope started):

| the cgroup says | the reason | zbx exits with | stderr (text) |
| --- | --- | --- | --- |
| `oom_kill` above 0 | `oom` | 137, whatever PID 1 did | `zbx: killed: out of memory (limit 128 MiB)` |
| else `max` above 0 | `pid_limit` | PID 1's own code | `zbx: stopped: process limit reached (limit 64)` |
| neither | `signal` or `exited` | as in M1 | as in M1 |

Decisions (the supervisor's): any OOM kill makes the reason `oom` and the code 137, even if PID 1
exited 0 (a worker was killed and the main process went on); `--verbose` then prints what PID 1
did (`zbx: note: the container's first process exited with code 0`), so nothing is hidden. Any
refused fork makes the reason `pid_limit`, and PID 1 keeps its code. An OOM kill outranks the
process limit. With no `--memory` the line has no limit (an ancestor's limit, or the machine's,
killed it).

`--output json` ends with `{"container_exit":{"reason":"oom","limit_bytes":N|null,"code":137}}`,
`{"reason":"pid_limit","limit":N|null,"code":C}`, `{"reason":"signal","signal":N,"code":128+N}` or
`{"reason":"exited","code":N}`.

The race: systemd removes a scope's cgroup when its last process is gone, so a cgroup that is
already gone cannot be read. Then the run is reported as the plain exit it was (nothing is claimed
without evidence). In the guest the files were readable every time (twelve OOM runs over three boots, the PID 1
that is itself killed included), but there is no guarantee; a library caller that needs one should read
`memory.events` while the container runs.

**Cleanup.** After the exit zbx looks for the scope's cgroup. If it is there, zbx asks the manager
to stop the unit (`StopUnit`, after the same `Subscribe`): `NoSuchUnit` means it went by itself;
otherwise the stop job is waited for. Then it looks again; a cgroup still there, or a manager that
refuses, is the warning `ZBX-W0302` (the exit code is still the container's). `--verbose` says
which of the three it was. A run that fails after its scope was made is cleaned up the same way
(not after a taken name: that scope is someone else's).

**Run record version 2** adds `.reason`, `.detached`, `.scope` and the three `.limit_*` fields. A
version 1 record reads unchanged with no limits, no scope, not detached, and the reason its exit
implies (the upgrade test is `exit_tests.zig`). A version 3 record is skipped as newer.

## Hardening (slice 3)

Between `seal_descriptors` and `exec` the child makes four calls, always, in the order the kernel
needs (plan steps `restrict_capabilities`, `clear_ambient`, `set_no_new_privs`,
`install_seccomp`); the filter is the last thing it does before `execve`. A failure of any is
refused as `ZBX-E0207` (capabilities) or `ZBX-E0208` (`no_new_privs`, seccomp), naming the step;
a container is never started less restricted than asked.

- **Capabilities** (`src/runtime/policy/capabilities.zon`, one reason per entry): `CHOWN`,
  `DAC_OVERRIDE`, `FOWNER`, `FSETID`, `KILL`, `SETGID`, `SETUID`, `SETPCAP`, `NET_BIND_SERVICE`,
  `SYS_CHROOT`, `AUDIT_WRITE`, `SETFCAP`: Docker's default without `NET_RAW` and `MKNOD`, and no
  `SYS_ADMIN`. Every other capability is dropped from the bounding set, and the effective,
  permitted and inheritable sets are set to the list; the ambient set is emptied. In the guest
  `/proc/self/status` shows `CapInh/CapPrm/CapEff/CapBnd: 00000000a00405fb`, `CapAmb: 0`
  (Docker's `a80425fb` less the bits of `NET_RAW` and `MKNOD`).
- **`no_new_privs`** is always set.
- **Seccomp** (`src/runtime/policy/seccomp.zon`): an allowlist of 64-bit syscalls in eleven
  groups with a reason each, plus Docker's argument rules: `clone` may not create namespaces,
  `personality` takes only its usual values, `socket` refuses `AF_VSOCK`; `clone3` answers
  `ENOSYS` (its flags are in a struct a filter cannot read, so libc falls back to `clone`).
  Everything else fails with `EPERM`, not a kill. `src/runtime/seccomp.zig` compiles the file at
  build time into one classic BPF program for x86_64 and aarch64 (599 instructions: 285 syscalls on
  x86_64, 248 on aarch64, checked by a verifier and an interpreter in `bpf.zig`); a foreign architecture, the 32-bit
  entry above all, gets `EPERM`. A name that is on neither architecture's table is a build error.
  Differences from Docker, in the file's header: no 32-bit variants, no `io_uring`.
- **`--read-only`** adds five steps before `pivot_root`: the mount points `/tmp` and `/run` are
  made in the rootfs if missing (while it is still writable), a tmpfs (`tmpfs_bytes_max`, 64 MiB;
  mode 1777 and 0755; nosuid, nodev) is mounted on each, and the rootfs bind mount is remounted
  read-only, keeping the flags it has (the kernel requires that in a user namespace; the host
  reads them with `statfs`). A mount point that cannot be made, a mount or the remount that is
  refused is `ZBX-E0209`. Note: the container's root can write any directory whose owner is
  mapped, whatever its mode, so "not writable" here means owned by an id the container does not
  map (a root-owned rootfs).

What the simulator and the fuzzers check: the BPF programs against an independent reading of the
policy (`zig build fuzz -- seccomp`: random policies, damaged programs, random instructions, the
shipped program), the new steps faulted one by one (`run` fuzzer and the walk in `run_tests.zig`),
and that a started container has the capabilities, `no_new_privs` and a filter that still allows
`execve`, `write`, `close` and `exit_group`.

## The library for Zigcube (slice 4)

The contract is Zigcube's `HANDOFF.md`, section 2. What is met, how, and what is not as written.

### Storage belongs to the caller

Slice 3 had module-level variables: the bundle workspace, the doctor's facts, the run handle. They
are gone. A `Handle` (`constants.handle_bytes_max`, 480 KiB) holds the plan and the doctor's
`Facts`; a `bundle.Workspace` (1 MiB) is the bundle's; `cli.Storage` holds a handle, a workspace
and the room `ps` lists into, and `main.zig` owns the one the `zbx` program uses (static, so in
BSS, not on the stack). The library keeps no module-level state: the real host's errno is
`threadlocal`, and the panic handler's settings belong to the `zbx` program. Nothing large is a
local, so the stack stays small: a thread that starts and waits for a container ran in a 256 KiB
stack in the test, and 96 KiB crashed it in a debug build, so about 128 KiB is the need in debug
and less in release. The test (`lifecycle_tests.zig`, two `std.Thread`s, each with its own handle
and simulator) starts and waits for two containers at once; a mutation check (a shared handle)
made it fail.

One finding on the way: adding a two-byte `threadlocal` (the real host's errno) made every
release binary panic before `main`. The binary's TLS segment is already 256 KiB: std's default
`signal_stack_size` is a `threadlocal` alternate signal stack that
`std.Thread.maybeAttachSignalStack` installs per thread. A static binary without libc sets up its
own thread area at startup (`std.os.linux.tls.initStatic`), and with the new variable it put the
thread control block at a misaligned offset (`incorrectAlignment`). That is a defect in std's
`tls`: minimal programs with a `u16` threadlocal do not reproduce it, so it depends on the layout
of the whole segment. Test binaries and Debug builds were fine, so only the VM showed it (`zbx`
printed `B0001` for every command). The variable is `align(16)`, and the guard is that
`zig build release` now runs the host's binary with `--version`, which fails without it (a later
change to the thread-locals, or a new Zig, is caught only by that run).

For Zigcube's thread pool: each thread costs that 256 KiB of TLS (the alternate signal stack) on
top of its own stack, so a pool of N threads takes N x (256 KiB + stack). Setting
`std_options.signal_stack_size = null` in the agent's root would drop the signal stack (and the
stack traces it makes possible on a stack overflow); that is the agent's choice.

### The contract, operation by operation

| HANDOFF | In `zigbox` |
| --- | --- |
| `start(Spec) -> Handle` | `start(host, &spec, options, &handle, &diag)`; the handle is the caller's. `StartOptions.detached`, `timeout_ms`, `grace_ms`. |
| `stop(Handle, grace_ms)` | `lifecycle.stop(ref, grace_ms, kill_wait_ms)`: SIGTERM by the forwarding rule, SIGKILL after the grace, then a wait of `kill_wait_ms`. A PID 1 with no SIGTERM handler gets SIGKILL at once (the kernel would ignore SIGTERM), reported as `killed`. |
| `inspect(Handle) -> Status` | `inspect(&handle)` returns `Status = union(enum) { starting, running, stopped: ExitReason }` as in the contract: the reason is the one `wait` returned (or the start failure). For a container of another process, `Entry.status()` gives the same union: `running`, `stopped` with `exit_reason_of(&record)`, or `stopped = .lost`. (`Entry` stores a compact `State` and builds the union on demand: an `ExitReason` can hold a 5.6 KiB `Diag`, and `ps` lists dozens.) |
| `list()` | `lifecycle.list(host, &entries)`: the records plus the zbx scopes that are running with no record (state `running`, no command). Each `Entry` carries the labels, command, pids and limits. |
| re-adoption | `lifecycle.adopt(host, name, &ref, &state)` from the record's pids, the pid's `NSpid` (innermost 1), `/proc/<pid>/cgroup` naming the scope and `cgroup.events` saying `populated 1`. No memory of the earlier process is used. |
| event stream | `lifecycle.Watcher.poll`; see below. |
| `Spec.limits` | `Spec.limits` with `cpu_millis`, `memory_bytes`, `pids`, as in the contract (slices 1 and 2). |
| `Spec.env` | `Spec.env`: added to PATH, HOME, HOSTNAME and TERM, replacing a default of the same name. At most 32 variables, name 64 bytes, value 4096, and the command and environment together within `exec_strings_bytes_max`; `ZBX-E0008` otherwise. Not kept in the record (a value may be a secret). |

### Detached runs

`zbx run -d` forks a supervisor (`setsid`, its streams on `/dev/null`) before anything else. The
supervisor starts the container, sends frames down a pipe (a tag byte, a 16-bit length and the
bytes): warnings, `started` (name, pid, scope) or `failed` (the exit code and the rendered
diagnostic). The caller relays the warnings, prints the name (or `zbx.run/1` JSON) on `started`,
or the diagnostic and the code on `failed`, and exits. A supervisor that ends without a report, or
sends nonsense, is `ZBX-E0405` (the caller never hangs and never prints a success it did not see).
After the `started` frame the supervisor closes the pipe and waits for the container, then
finishes the record. The record (version 3) has the pid of the container's PID 1, the supervisor's
pid, the command and the labels. SIGPIPE is ignored in the supervisor before every frame: starting
a scope puts it back, and a caller that went away must not kill the supervisor.

### Time

`--timeout <ms>` on `run` stops the container when it has run that long (SIGTERM, then SIGKILL
after `--grace`, default 10 s); the report says `timed out after N ms` and, in JSON,
`"timed_out":true` inside `container_exit`. On `stop`, `--timeout` bounds the whole stop: the
grace is cut to it, and the wait after SIGKILL is what is left of it (at least 500 ms); a
container still there then is `ZBX-E0404`. The clocks are the host's monotonic clock; the
simulator has a virtual one, so the tests do not sleep.

### Events and the poll bound

The event stream is a poll, not a push: `Watcher.poll(host, &watcher, scratch, out)` lists, compares
with what it saw last time and writes `started`, `stopped` and `lost` events. It does not wait. A
change is seen by the first poll after it, so a caller that polls every
`constants.events_poll_ms_max` (1000 ms) sees every change within that time; a container that
ends is seen as `stopped` when its record shows the end, which the supervisor writes a moment after
the cgroup empties (until then the pid alone says it is gone). At most `out.len` events come per
poll; the rest come next time. A container whose record was pruned is forgotten without an event.

### Where the contract cannot be met as written

These are for the owner to decide; none is papered over.

- **`Spec.image` is `rootfs`.** The contract holds an image digest; M2 has no image store. The
  field is the directory to use as the root. Mapping a digest to a rootfs is the agent's job until
  the store exists.
- **Labels and environment are `Label { key, value }`, not `[2][]const u8`.** Same data, a struct
  with names; an adapter is one line.
- **`list()` returns `Entry` values, not `Handle`s.** A `Handle` is 480 KiB and belongs to the
  process that started the container; a container of an earlier process has none. An `Entry` has
  what a handle was for (name, labels, pids, state); `adopt` makes a small `Ref` for `stop`,
  `signal` and `wait`.
- **The event stream is polled**, with the bound above, not pushed.
- **`ExitReason` has no `timed_out` variant.** A run stopped for its time reports the signal that
  ended it (`signaled`, code 143 or 137) and `timed_out(handle)` is true. The record keeps the
  flag (`.timed_out`, version 3), so `ps --all` shows the state `timed_out`, `ps --output json`
  has `"timed_out":true` (and `reason` `signal`), and `exit_reason_of(&record)` is still the
  `signaled` that did it. That the variant is missing is the only gap left.
- **`start_failed` from a record is a minimal `Diag`** (the code and one cause saying where the
  rest is): a record keeps the code, not the whole diagnostic.
- **`stop` of a container this process waits for** must run on another thread than `wait` (the
  wait is what reaps it); the doc of `stop` says so.
- **Poll costs.** `stop` and `wait` on a `Ref` of another process poll every 20 ms; there is no
  pidfd wait. A pidfd would remove the polling for a container of this user, at the cost of a
  syscall the simulator does not model yet.

### Cut

`zbx logs` is cut, as the brief says it may be: a detached container's streams are `/dev/null`.

### Commands and schemas

`zbx ps [--all]` (text, or `--output json`; a run stopped for its time shows `timed_out`), `zbx stop <name> [--grace ms] [--timeout ms]`,
`zbx schema <command>` and `run -d`, `run --timeout`. Nothing prompts. `zbx schema` prints the
JSON Schema (draft 2020-12, `$id` `https://zigbox.github.io/zigbox/schema/<command>/1`) for `run`,
`bundle`, `ps`, `stop` and `doctor`; a unit test checks each is valid JSON and has its `$id`, and
the `ps` and `stop` tests parse the real output and check the required fields. New diagnostics:
`ZBX-E0401` (a time that is not a number), `E0402` (no container with that name; with no
state directory it is the existing `E0701`), `E0403` (cannot signal PID 1), `E0404` (still there after SIGKILL), `E0405` (the
supervisor of a detached run failed or never reported), `E0406` (no schema for that command).

## Departures from runc's systemd driver

[runc's systemd driver](https://github.com/opencontainers/runc/blob/main/docs/systemd.md) is the
reference (`docs/DECISIONS.md`). What is taken: one transient scope per container; `Delegate`,
`Slice` and the accounting properties; limits as unit properties where the running systemd has
them, and cgroupfs files where it does not; properties chosen by the systemd version.

What is dropped, and why:

- **`cgroupsPath` (`slice:prefix:name`) and the `org.systemd.property.*` annotations.** They exist
  because runc takes an OCI `config.json`. `zbx` has no such input: the unit is always
  `zbx-<name>.scope` and its properties come from `zbx`'s own flags.
- **A system bus.** runc may talk to the system manager as root. `zbx` is rootless and only ever
  talks to the user's manager.
- **`Subscribe` and the unit-state signals.** The only signal `zbx` needs is `JobRemoved`, which
  systemd sends to the client that started the job; `zbx` adds a match rule for it and reads
  nothing else.

## The demo (slice 5)

`zig build demo-m2 -Daccel=kvm` (what CI runs) or `-Daccel=tcg` (software emulation, about six
minutes on a laptop-class host once the images are cached). It is the M0 and M1 harness: the same
Ubuntu 24.04 cloud image and provisioning, the pinned Alpine minirootfs unpacked as user `demo`,
and every `zbx` command run as `demo` with the user's session variables, so the scope and its
limits are real (the user manager is systemd 255, cgroup v2). `-Dkeep-overlay` and
`-Dreuse-overlay` keep and reuse the provisioned disk between runs, as in the other demos. Each
check is a pure function in `src/testing/vm/checks_m2.zig` with unit tests that include wrong
input (they run in `zig build test`).

### What it does, in order

Provisioning: the rootfs is unpacked; four small scripts are written (a memory hog, a loop that
starts 40 sleeps, a status printer, and the host side of step 1); a copy of the rootfs gets
`stress-ng` by `apk add --no-cache stress-ng` run inside a `zbx run` (the container shares the VM's
network in M2; the copy's `/etc/resolv.conf` names the emulated resolver 10.0.2.3 and its
`/etc/apk/repositories` use `http://` because the minirootfs has no CA certificates; apk checks
signatures with the keys in the rootfs).

The four steps of the spec, with what each asserts:

| Step | Command (as `demo`) | Asserted |
| --- | --- | --- |
| 1 | `zbx run --rootfs ./alpine --pids 64 --name bomb1 -- sh -c 'b(){ b\|b& }; b; wait; sleep 3'`, in the background under `timeout 150`, while the host answers a probe each second | five probes answered; zbx not cut off by `timeout` (124) and not 125; the last line of stderr is `zbx: stopped: process limit reached (limit 64)`; the scope is gone afterwards |
| 2 | `zbx run --rootfs ./alpine-stress --memory 128m -- stress-ng --vm 1 --vm-bytes 512m --oomable` | exit 137; the last line of stderr is `zbx: killed: out of memory (limit 128 MiB)`; the scope is gone |
| 3 | `zbx run --rootfs ./alpine -- mount -t tmpfs none /mnt` | a non-zero exit that is not zbx's own (not 125 or 70); stderr says `permission denied` or `Operation not permitted` (case-insensitive: busybox says `mount: permission denied (are you root?)`, glibc says `Operation not permitted`; both are the kernel's EPERM) |
| 4 | `zbx run --rootfs ./alpine --read-only -- touch /x`, then `--read-only -- sh -c 'touch /tmp/x && echo tmp-ok'` | the first exits non-zero with `touch: /x: Read-only file system`; the second prints `tmp-ok` and exits 0 |

The acceptance criteria:

- **Hardening in force:** in a container, `/proc/self/status` shows `CapInh`, `CapPrm`, `CapEff`
  and `CapBnd` all `00000000a00405fb` (the allowlist in `policy/capabilities.zon`), `CapAmb` 0,
  `NoNewPrivs: 1`, `Seccomp: 2`.
- **Limits visible, then gone:** `zbx run -d --memory 64m --pids 20 --cpus 0.5 --name lim1 -- sleep 1000`;
  while it runs, `zbx-lim1.scope` is in `/sys/fs/cgroup/user.slice/user-1000.slice/user@1000.service/app.slice`
  with `memory.max=67108864`, `memory.swap.max=0`, `pids.max=20`, `cpu.max=50000 100000`; after
  `zbx stop lim1` the scope is in neither the cgroup tree nor `systemctl --user list-units`.
- **Exit reasons told apart** (`--output json`, the `container_exit` line): `oom` with code 137
  (a hog under `--memory 32m`), `pid_limit` with code 2 (PID 1's own code; 40 sleeps under
  `--pids 16`), `signal` with code 143 (`--timeout 2000` on a `sleep`), `exited` with code 42.

The lifecycle (slice 4), every `zbx` here a new process:

- `run -d --name det1 -- sleep 1000` prints `det1` and returns with nothing on stderr; `ps` lists it
  `running`; `ps --output json` has it with `detached` true and its command; its supervisor (the
  pid in its record) is alive; `stop det1 --output json` says `killed`, `exit_code` 137 (a `sleep`
  PID 1 has no SIGTERM handler, so SIGKILL at once); the scope is gone; a second `stop` says
  `det1 was not running, exit code 137`; `ps --all` lists it `signal:9`, and plain `ps` does not.
- `stop det3 --grace 3000` on `sh -c 'trap "exit 7" TERM; sleep 1000 & wait'` says `graceful`,
  `exit_code` 7.
- `run -d --timeout 3000` ends by itself: 8 s later `ps --all --output json` has it `stopped` with
  `timed_out` true; a foreground `run --timeout 3000` exits 143 and prints
  `zbx: stopped: timed out after 3000 ms`.
- One-line refusals: `stop nobody` is `ZBX-E0402`, `stop det4 --grace soon` is `ZBX-E0401`,
  `schema logs` is `ZBX-E0406` (each exit 1, nothing on stdout); `schema run|bundle|ps|stop|doctor`
  each print a schema with its `$id`.

Two failure modes are exercised too: `--read-only` on a rootfs with no `/tmp` that the user cannot
write is `ZBX-E0209`, exit 125; and an inherited `DBUS_SESSION_BUS_ADDRESS` naming root's bus is
turned away and the run goes on, on the user's own bus, with a note saying so.

### Two spec commands changed (spec rev 51)

Both were found by running the spec's commands in the VM. The owner decided to change the spec
to what the demo runs, and the live doc says so from rev 51 (2026-10-26):

1. **The fork bomb needs `sleep 3` after `wait`.** The spec's line is
   `sh -c 'b(){ b|b& }; b; wait'`. Run in the VM (measured under TCG, three variants, same
   container): it exits 0 at once, writes nothing, and never reaches the limit. `wait` only waits
   for PID 1's own jobs; the background pipeline forks and exits, and its children are not PID 1's
   jobs, so `wait` returns and PID 1 ends the container before the tree has grown to 64. With
   `b; sleep 3` and with `b; wait; sleep 3` the limit is hit and zbx reports
   `stopped: process limit reached (limit 64)`. The demo runs `b; wait; sleep 3`, and so does the
   spec from rev 51. (Rev 48 said `wait` keeps PID 1 alive; it does not.) Under KVM in CI the
   same line hits the limit too (run 38).
2. **stress-ng needs `--oomable`.** Without it stress-ng starts a new worker every time the kernel
   kills one, for a day by default. Measured under TCG: after seven minutes it was still going
   (each restart touches 128 MiB), with the kernel's OOM report repeating on the console. With
   `--oomable` the run takes about a second and zbx prints `killed: out of memory (limit 128 MiB)`
   as the last line, exit 137, although stress-ng itself reports success. The report is zbx's, from
   the scope's `memory.events`, so it does not depend on stress-ng's view.

Also: the console is where the harness reads output, so the demo runs `dmesg -n 1` first (the
kernel prints a report for every OOM kill, and the output of one command is bounded at 64 KiB).

### By hand

In an Ubuntu 24.04 session of a user with a systemd user manager and `uidmap` (see
`docs/demos/m1.md` for the setup):

```sh
mkdir alpine && tar -xzf alpine-minirootfs-3.20.10-x86_64.tar.gz -C alpine
zbx run --rootfs ./alpine --pids 64 -- sh -c 'b(){ b|b& }; b; wait; sleep 3'
# ... can't fork ... then: zbx: stopped: process limit reached (limit 64)
cp -a alpine alpine-stress   # then apk add stress-ng inside: zbx run --rootfs ./alpine-stress -- apk add stress-ng
zbx run --rootfs ./alpine-stress --memory 128m -- stress-ng --vm 1 --vm-bytes 512m --oomable
# zbx: killed: out of memory (limit 128 MiB)   (exit 137)
zbx run --rootfs ./alpine -- mount -t tmpfs none /mnt          # mount: permission denied (are you root?)
zbx run --rootfs ./alpine --read-only -- touch /x             # touch: /x: Read-only file system
zbx run --rootfs ./alpine --read-only -- sh -c 'touch /tmp/x && echo tmp-ok'
zbx run -d --rootfs ./alpine --name w -- sleep 1000; zbx ps; zbx stop w
```

### Failure modes

Each is a coded, one-line-per-part diagnostic; `zbx explain <code>` and the error page have the
rest.

- **No user bus** (no lingering, no login session): a run with limit flags is refused (`E03xx`,
  exit 125) naming the cause and pointing at `zbx doctor`; a run with no limit flags runs without a
  scope and prints `W0301` once.
- **Delegation missing a controller** (`memory` or `pids` not delegated to the user's manager):
  the limit's flag is refused with a cgroup diagnostic; `zbx doctor` shows the controllers.
- **An OOM that hits zbx itself**: zbx runs in the user's own cgroup, outside the scope, so the
  scope's limit does not touch it; a host-wide OOM can kill any process, zbx included, and the
  record then reads `lost` (`ps` shows it) with no reason.
- **A seccomp denial that looks like a bug**: a syscall not on the allowlist returns `EPERM`, so an
  application sees `Operation not permitted` and may report something unrelated. The profile
  follows Docker's and has only been run with Alpine's busybox and stress-ng; a glibc rootfs
  (Debian-based `python`, `postgres`) must be tried before M4 and the allowlist grown from what
  fails. `Seccomp: 2` in `/proc/self/status` says the filter is on; `strace` from the host
  (`-f` on the container's PID 1) shows the denied call.
- **`--read-only` without `/tmp` or `/run`**: if the rootfs lacks them and is not writable by the
  user, `ZBX-E0209` (exit 125) says so before the command starts; make the directories as the
  rootfs's owner.
- **A container that outlives its supervisor, or a supervisor that dies**: the record says `lost`;
  `ps` lists it; `stop` of a `lost` container reports it was not running.

### Cuts

- `zbx logs` is cut; a detached container's streams are `/dev/null`.
- The demo does not run a glibc image (M4), network limits (M5) or a seccomp denial of a real
  application.
- `vm-m2-experiment` is removed. It was the look-around for slices 2 to 4; its useful checks are in
  the demo (the fork bomb and the OOM, the limit files and their cleanup, the capability and
  seccomp status, `--read-only` with and without `/tmp`, the inherited bus, the lifecycle). What
  it also printed (pids limit with a loop, the other two OOM repeats, and the per-run record
  fields) is covered by the unit and simulator tests.
