# M5 demo: network

This document grows slice by slice and is finished by slice 4, which adds `zig build demo-m5`,
the by-hand steps of the spec's demo and the failure modes. Until the `demo-m5` job is green in
CI, M5 is built, not demonstrated.

## Slice 3: `--net user` and `--publish` through pasta

`--net user` gives a container its own network namespace connected to the host's network by
pasta, run as the user: no privilege, and no change to the host's firewall, routes or
interfaces. `--publish HOST:CONTAINER` (TCP, repeatable, at most 16) forwards a host port into
the container and implies `--net user`; with an explicit `--net none` or `--net host` it is a
usage error (`ZBX-E0003`).

### pasta's interface, settled

The VM installs Ubuntu 24.04's `passt` package, `0.0~git20240220.1e6f92b-1` (Launchpad's
publishing history for noble: the release pocket, no update). Every fact below comes from that
commit's manual (`passt.1`) and source at https://passt.top/passt/ (`?id=1e6f92b`), and was then
confirmed in the guest by hand (run 40728860678, below).

| Question | Answer | Where it is settled |
| --- | --- | --- |
| How pasta attaches to an existing namespace | `pasta [options] PID`: it joins `/proc/PID/ns/user` and `/proc/PID/ns/net` (`--netns PATH` is the other way, with `--userns`). zbx passes the container's PID 1, which waits on its sync pipe meanwhile. | `passt.1`, SYNOPSIS and `--userns`; `conf.c`, `conf_pasta_ns` |
| How it signals that it is ready | `--pid FILE` writes its PID "once initialisation is done": after `tap_sock_init` (the tap device, then `pasta_ns_conf`: `lo` up, with `--config-net` the host's addresses and routes) and after `tcp_init` (the `-t` ports bound). With `--foreground` the PID is its own. zbx gives `--pid /proc/self/fd/1`, its stdout being a pipe zbx reads; a pasta that fails first writes nothing there and exits 1, its reason the last line of its stderr. The descriptor is one of 0 to 2 because later releases close every inherited descriptor above 2 (`isolation.c`, `close_range` in `isolate_initial`, current tree). | `passt.c`, `main` (the order of `tap_sock_init`, `tcp_init`, `write_pidfile`); `util.c`, `write_pidfile` |
| What it does when the namespace goes away | It exits. For a namespace named by a procfs path (a PID) inotify sees nothing, so it checks `/proc/PID/ns/net` once a second (`pasta_netns_quit_timer`) and exits when the open fails other than with `EACCES`. The fallback appeared on 2024-02-16; before it, pasta attached by PID never noticed. In the guest it exited 935 ms after the namespace's process was killed, and its port was free. | `pasta.c`, `pasta_netns_quit_init`, `pasta_netns_quit_timer_handler`; `passt.1`, `--no-netns-quit` |
| `--dns-forward ADDR` | DNS (UDP to port 53) sent from the namespace to ADDR goes to the host's first resolver (`dns_host`, the first `nameserver` of the host's `/etc/resolv.conf`), asked from the host's side, and answers come back from ADDR. On Ubuntu that resolver is systemd-resolved's stub, 127.0.0.53, which the container cannot reach itself. zbx uses 169.254.1.1 (link-local, as Podman does) and writes it into the container's `/etc/resolv.conf`. With `--no-map-gw` pasta warns "Couldn't get any nameserver address" (a loopback resolver is not passed on by DHCP), and forwarding still works: a raw DNS query for example.com through it got two answers in the guest. | `passt.1`, `--dns-forward`; `conf.c`, `add_dns4`, option 9; `udp.c`, the `dns_match` and `dns_host` mapping |
| `-t` for TCP port forwards | `-t HOST:CONTAINER` (also `--tcp-ports`), repeatable; it binds HOST on every address of the host (0.0.0.0, and :: when the host has IPv6). In pasta mode `-t`, `-u`, `-T` and `-U` default to `auto` (forward every port the container listens on, both ways), so zbx passes `none` for all it does not use. A failed bind is fatal: "Failed to bind port 8080 (Address already in use) for option '-t 8080:80', exiting", and "(Permission denied)" below `net.ipv4.ip_unprivileged_port_start` (1024 on Ubuntu). | `passt.1`, `-t` (pasta-only options); `conf.c`, `conf_ports` |
| The minimum version zbx relies on | `2024_02_16` (the release `2024_02_16.08344da`, the first with the timer fallback; `2023_12_30.f091893` lacks `pasta_netns_quit_timer`). Older is `ZBX-E0602`. Ubuntu's build prints `pasta unknown version` (its `debian/rules` exports `VERSION` in a recipe line of its own, so the build falls back to "unknown version"), and a version with no date cannot be judged: zbx accepts it. Debian snapshot versions (`0.0~git20240220...`) and upstream tags (`2024_02_20.1e6f92b`) are read. | the passt tags list; `pasta.c` at `2023_12_30.f091893` and `08344da`; the probe below |

The command line zbx runs, from `src/runtime/pasta.zig`:

```
pasta --config-net --quiet --foreground --pid /proc/self/fd/1
      --udp-ports none --tcp-ns none --udp-ns none --no-map-gw
      --dns-forward 169.254.1.1 [--tcp-ports HOST:CONTAINER]... | --tcp-ports none
      <the container's PID 1>
```

`--no-map-gw`: the gateway address does not lead to the host's loopback, so a container cannot
reach services that listen only there.

### pasta's lifecycle in zbx

- After the id maps are written (so pasta is root in the container's user namespace when it
  joins it) and before the scope, the parent runs two plan steps: `start_pasta` and
  `await_pasta`. The child is blocked on its sync pipe until `release_child`, which comes after
  them: it runs nothing until pasta reports the interface configured.
- `start_pasta` (`Host.start_program`) forks pasta as zbx's own child: a session of its own (a
  terminal's ^C is not for it), `PR_SET_PDEATHSIG` SIGKILL (a SIGKILL of zbx kills it), stdin
  `/dev/null`, stdout the ready pipe, stderr the run's pasta log.
- `await_pasta` waits for the ready line within `pasta_ready_timeout_ms` (10 s). An end of file
  (pasta exited), something that is not its PID, or no line in time is a coded error; pasta is
  killed and reaped, and the container never runs its command.
- When the container ends, `wait` kills and reaps pasta first, so the ports go at once. A failed
  start (`abandon`) does the same. A SIGKILL of zbx: the kernel kills the container (its
  `die_with_parent`) and pasta (its death signal), and pasta would exit by itself within a
  second anyway.
- On amd64 the process that runs is `pasta.avx2`: pasta executes its AVX2 build at once when
  the CPU has it (`arch_avx2_exec`), so `ss -tlnp` and `ps` name it `pasta.avx2`.
- pasta's output goes to `$XDG_STATE_HOME/zbx/logs/<name>.pasta.log` (or under
  `~/.local/state`), emptied when pasta starts, never to the container's stdout. A run whose
  record is pruned loses its log too. Ubuntu's AppArmor profile for pasta lets it write only under
  `/tmp` and `$HOME`; pasta opens neither file itself (it inherits both descriptors), and the
  ready pipe through `/proc/self/fd/1` worked under that profile in the guest.

### Diagnostics

| Code | When |
| --- | --- |
| `ZBX-E0600` | a `--publish` that does not parse: not `HOST:CONTAINER`, a port not a number, outside 1 to 65535, more than 16, a host port twice. (It was slice 2's temporary "not available yet"; M5 is unreleased, so the code is reused.) |
| `ZBX-E0601` | `--net user` or `--publish`, and no `pasta` on `PATH` |
| `ZBX-E0602` | a pasta whose version names a date before 2024-02-16, with the version found and the one needed |
| `ZBX-E0603` | pasta failed to start: it exited, or said something else, or was not ready in 10 s; pasta's last line is the cause |
| `ZBX-E0604` | a host port another program listens on (from pasta's bind failure) |
| `ZBX-E0605` | a host port below `net.ipv4.ip_unprivileged_port_start`: refused before pasta starts when the sysctl can be read, and from pasta's bind failure when it cannot |

`zbx doctor`'s `net` line warns about a pasta older than the minimum as well.

### Cuts and deviations

- The log of a run's pasta is a file of its own, `logs/<name>.pasta.log` beside `runs/`: the
  brief names "the run's log", and zbx had none. A log that cannot be made (no state directory, a
  full disk) is not kept and does not refuse the run; a failure's diagnostic then says so.
- A failed pasta's last line is read from the start of its log, at most 4 KiB
  (`pasta_log_tail_bytes_max`): a pasta that fails while starting has written a line or two.
- The top-20 harness publishes every probed server (not only nginx, httpd and traefik) on its port
  plus 20000; images without a probe keep `--net host`, as slice 2 gave them.
  The top-20 run on slice 3's code (60fcce3) passed: 16 run, and 4 have a documented reason
  (postgres, mysql and mariadb want a password variable; docker wants `mount`). nginx, httpd and
  traefik now run, through `--publish`:
  https://github.com/Zigbox/zigbox/actions/runs/40740657844
- The simulator cannot show the kernel's part of a SIGKILL of zbx (the death signals); it models
  it (`World.kill_supervisor`), and the VM shows the real one.

### By hand, on Ubuntu 24.04

You need a user who is not root, with a range of subordinate ids (`zbx doctor` says if not), and
`zbx` on the `PATH`.

```
sudo apt install passt iptables      # pasta, and the firewall tool step 4 reads
zbx doctor                           # the last line, "ok   net", names pasta
zbx pull alpine && zbx pull nginx    # a name needs an entry in zbx.lock; pulls alpine:latest, nginx:latest

# 1. No network unless granted.
zbx run alpine -- wget -qO- https://example.com
#    wget fails ("bad address"); the last line is:  zbx: network: none (grant with --net)

# 2. User-mode networking.
zbx run --net user alpine -- wget -qO- https://example.com
#    prints the page: "Example Domain"

# 3. A published port.
sudo iptables -S > /tmp/rules.before
zbx run -d --name web --publish 8080:80 nginx
curl localhost:8080                  # "Welcome to nginx!"

# 4. Whose listener, and no firewall change.
ss -tlnp                             # 0.0.0.0:8080 ... users:(("pasta.avx2",pid=...,fd=6)): yours
sudo iptables -S | diff /tmp/rules.before -     # no output
zbx stop web                         # the port is free again within a second or two
```

`zbx run --publish 8080:80 nginx` also works in the foreground in one terminal, with `curl` in
another. The demo uses `-d` because it has one terminal. Bare `alpine` and `nginx` are the spec's
names; they resolve to `latest`, which is what the demo pulls and runs. That is not a problem for
the demo: `nginx:latest` is the image the top-20 table runs through `--publish` too.

On Debian-family hosts only `passt` has to be installed. `ss` is in `iproute2`. If `iptables` is not
installed, step 4's comparison has nothing to compare: the demo installs it in the VM and refuses an
`iptables -S` that printed no built-in chains (`check_rules_read`).

### The agent test

`agent_m5.zig` repeats the steps by JSON: it reads `zbx schema run` before relying on `network`
and `published`, takes the refusal from the exit line's `network:"none"` with the program's
failure, grants `--net user` and checks `network:"user"`, reads `published` from a run with
`--publish`, starts a server with `run -d` and reads its name from the document, stops it with
`stop --output json`, and for a missing pasta reads `code`, `blame` and `fixes` of the diagnostic
(ZBX-E0601, `environment`, an install command and a `zbx run --net host ...` line), applies the
host-network alternative to its own command, and checks `explain --output json` agrees.

Findings, things the agent could not read from JSON (each is a line the demo prints):

1. **The reason for a failure is not in the exit line.** `network:"none"` with a non-zero code is
   all it says; an explicit `--net none` looks the same, and the agent infers that the network may
   be the cause. The hint is text-only by design, and is absent in JSON mode.
2. **`run -d --output json` has no `network` or `published`.** The agent must remember the port it
   asked for.
3. **`ps --output json` has neither for a running container.** A container's ports are not
   readable after the run command that published them has returned.
4. **The fixes of ZBX-E0601 are free text.** The install command needs root (only the word `sudo`
   says so), and the second fix is a template (`zbx run --net host alpine -- sh`) the agent must
   not run; it takes the `--net host` flag out of it.
5. **`doctor --output json` has no `net` form.** The check only warns, so it has no code and no
   diagnostic; the text report is on stdout. An agent can learn that pasta is missing only by
   trying `run --net user`.
6. **The agent's schema checker cannot validate a run document**: `zbx schema run` is a `oneOf` of
   `$ref`s, which the checker (the subset of JSON Schema zbx's other schemas use) does not follow.
   The agent reads the network members' place in the schema by path instead
   (`schema_describes_network`); the run documents themselves are checked by their members.

None was worked around in zbx. Findings 2 to 5 are candidates for a later milestone.

#### Closed in M6 (slice 1)

The owner took all six into M6 (`docs/briefs/M6-state.md`, "Closing M5's carried-over notes").
`agent_m5.zig` no longer prints findings: each is now a check that fails the demo if it regresses.

1. **The hint is in the exit line.** `container_exit` carries `"hint":"network_none"` when the
   text mode would print `zbx: network: none (grant with --net)`: the default network, no
   `--net`, and the program exited non-zero. A single member, not a `notes` array: the text has
   one note, the member is an enum that can grow (`network_none` today), and an agent tests one
   string. An explicit `--net none` carries none, in JSON as in text.
2. **`run -d --output json`** says `network`, `published` and `env` in its `container` object.
3. **`ps --output json`** says the same for every container, read from the run record (version 5
   of the record; a container of an older zbx has `"network":null`, no forwards and no names).
4. **A fix says what it needs.** `"needs_root":true` is set on a fix whose command runs `sudo`
   (decided where the fix is made, so it cannot disagree with the text) and `"template":true` on
   a fix whose command is an example to adapt (`zbx run --net host alpine -- sh`). Both are
   written only when true; the schema and the goldens follow.
5. **`doctor --output json`** prints the `zbx.doctor/1` document on stdout: every check with
   its status and detail, and for a warning or a failure its `code` and its `diagnostic`. The
   `net` warning is `ZBX-W0102` (the userns warning is `ZBX-W0101`). Failures are still one
   diagnostic per line on stderr.
6. **`zbx schema run` is one object schema with no `$ref`.** The members of the three documents
   a run can print are all listed under `properties`, and `oneOf` names the members that tell
   them apart (the idiom of `schema store-du`, which the agent's checker already followed). A
   second, resolver-free form beside the old one was the alternative; one text is simpler to
   keep true. `$defs` stays, inlined, so a reader of the old path still finds it. `schema
   doctor` has the same shape.

### Deviations and cuts

- **Step 4's `ss -tlnp` as the user does not name pasta.** The spec says the listener is owned by
  the demo user. The first run showed that `ss -tlnp` as the demo user lists the listener but leaves
  the process column empty: pasta drops its privileges and becomes undumpable once ready, so the
  user cannot read its `/proc/PID/fd`. The owner is still shown by `ss -tlnpe` as the demo user
  (`uid:1000`), and root's `ss -tlnpe` names `pasta.avx2`. The demo runs all three. By hand, use
  `ss -tlnpe`; the spec's step 4 should say so.
