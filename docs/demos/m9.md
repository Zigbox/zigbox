# M9 demo: Dockerfile import and the builder additions

Until the `demo-m9` job is green in CI, M9 is built, not demonstrated. Slice 2 (this file's
first version) has run no VM demo: `demo-m9` is slice 4's, and no harness for it exists yet.

Brief: `docs/briefs/M9-dockerfile-import.md`. Slice 2 builds what the brief's "builder additions"
describe: input globs and `.exclude`, copy steps, `image.base = "step:"` and named
`config.user`. Unit and simulated-store tests cover them (`copy_tests.zig`,
`compose_tests.zig`); nothing here ran in a guest.

## What slice 2 built

- **Input globs and `.exclude`** (`glob.zig`, `input_tree.zig`): E0818 when a build's globs match
  more than `build_glob_matches_max` paths.
- **Copy steps** (`copy.zig`, `compose.zig`): a step with `.copy` runs no container. For each
  entry the parent selects the source's matching paths into a tree laid under `.to`, puts the
  selection's digest in the step's key, and lays every selection over the base with
  replace-merge (a later file replaces an earlier one; two directories merge). A file the
  patterns do not take never changes the key. The output is rooted like a root step's.
- **`image.base = "step:<name>"`**: the result's tree is that step's output; config is inherited
  from the image the chain of `step:` bases began with; provenance names that image.
- **`config.user` as a name**: looked up in the result's tree (E0817 if absent); the record
  holds `uid:gid`.

## Cuts and deviations (recorded)

- **Still E0802 (read, not built):** a bind from the project's files or from a locked image (cut
  for good) and a `.binds` on a copy step; a copy from a locked image; an `.exclude` on a copy
  from a `step:`.
- **A copy's `.chown` and `.chmod`** run (`2026-11-14-m9-copy-chown.md`). The selection is made
  in the parent; an owner or mode is part of a file object's id, so the new objects are written
  in a single-threaded child inside the store's user namespace, before any exec. A name is
  looked up in `/etc/passwd` and `/etc/group` of the step's base (a user alone takes its primary
  group, as `.user` does); numbers are taken as written; a name the base lacks, or the id
  4294967295, is E0817. Both fields are in the step's key. Every file, directory and symlink
  the patterns take gets the owner; the mode goes on files and directories, not symlinks.
  Directories made on the way to `.to` get the owner (Docker's "new files and directories") and
  keep 0755; a directory that already exists in the base keeps the base's attributes. On a host
  that maps one id (W0201) every owner is 0:0, as an import's is; the mode still applies.
- **Excluded directories.** With no `!` line in the exclude lists an excluded directory is
  skipped wholesale. With any `!` line an excluded directory is still entered, so a file a `!`
  line brings back is found, and empty directories can result.
- **Multiple matches to a `.to` with no trailing `/`:** the matches land on the same path and
  the later one wins (Docker refuses it). A `.to` ending in `/` puts each match inside.
- **`.src = .{"."}`** is refused as an input (a project path is a plain relative path); from a
  `step:` source `.` or `/` copies the whole tree.
- **Owners of copied files** without `.chown` are the source's: a project file is 0:0 as every
  input is. Docker gives `--chown`-less copies root, which is the same here.
- **A source is a tree, not a stream:** a `step:` source's globs are matched against its output
  tree at build time, so a glob that matches nothing is E0803 naming the step.
- **Rooting:** every tree a step reads after the import that wrote it is rooted `build:<step>`
  until it is used, so a concurrent `store gc` cannot remove it in between: a copy's source tree
  and its selection trees (dropped once the output is recorded) and a command step's input tree and its binds' selection trees
  (dropped on a hit, on an error, and when its worker settles or is aborted). Roots are
  counted per tree within a build, so the first of two steps that share a tree (the same
  inputs, the same bind selection, a copy's source) to finish keeps the root for the other. A
  build stopped by SIGINT or SIGTERM, at any point up to the image's record, aborts its workers
  and drops its roots (E0808, one line naming the signal; never exit 0). A build killed
  with SIGKILL, or two `zbx build` processes on one project that share a tree, can still leave
  or drop a root early: `zbx store gc` lists a leftover and the user may remove it.
- **`.caches`** run (`cache` mount kind): `build/caches/<group>/<name>`, outside the step key,
  steps sharing an id run one after another. The report marks such a step `cache` (text, and
  `"caches":true` in JSON); `W0802` is printed once on stderr naming them; cache
  directories are not locked between two `zbx build` processes on one project, so run one build
  at a time per project (a known limit); `zbx build
  --clear-caches` empties the cache directories first, under the exclusive store lock (E0436
  when busy). `--graph` with `--clear-caches` clears nothing.
- **`.binds` from a `step:` output** run: the selection of the bind's `.source` in that step's
  output is part of the key (a file outside it changes nothing) and is mounted read-only at
  `.to`. A single-file source mounts a directory holding that file. A source that matches
  nothing is E0803. A bind from the project's files or a locked image stays E0802 for good.
- **A non-root `.user` with a writable `/out`** is refused by `needs_root` in this slice: the
  output would belong to ids the parent cannot write (`2026-11-13-m9-nonroot-out-refused.md`).
- **`zig build check` and the VM:** see the slice's handoff in `docs/decisions/`.
