# M9 demo: Dockerfile import and the builder additions

Until the `demo-m9` job is green in CI, M9 is built, not demonstrated. Slice 2 (this file's
first version) ran no VM demo; slice 4's `demo-m9` passed on a `vm/` branch (see the demo's
status below).

Brief: `docs/briefs/M9-dockerfile-import.md`. Slice 2 builds what the brief's "builder additions"
describe: input globs and `.exclude`, copy steps, `image.base = "step:"` and named
`config.user`. Unit and simulated-store tests cover them (`copy_tests.zig`,
`compose_tests.zig`); nothing here ran in a guest.

## What slice 2 built

- **Input globs and `.exclude`** (`glob.zig`, `input_tree.zig`): E0818 when a build's globs match
  more than `build_glob_matches_max` paths.
- **Copy steps** (`copy.zig`, `compose.zig`): a step with `.copy` runs no container. For each
  entry the parent selects the source's matching paths into a tree laid under `.to`, puts the
  selection's digest in the step's key, and lays every selection over the base with
  replace-merge (a later file replaces an earlier one; two directories merge). A file the
  patterns do not take never changes the key. The output is rooted like a root step's.
- **`image.base = "step:<name>"`**: the result's tree is that step's output; config is inherited
  from the image the chain of `step:` bases began with; provenance names that image.
- **`config.user` as a name**: looked up in the result's tree (E0817 if absent); the record
  holds `uid:gid`.

## Cuts and deviations (recorded)

- **Still E0802 (read, not built):** a bind from the project's files or from a locked image (cut
  for good) and a `.binds` on a copy step; a copy from a locked image; an `.exclude` on a copy
  from a `step:`.
- **A copy's `.chown` and `.chmod`** run (`2026-11-14-m9-copy-chown.md`). The selection is made
  in the parent; an owner or mode is part of a file object's id, so the new objects are written
  in a single-threaded child inside the store's user namespace, before any exec. A name is
  looked up in `/etc/passwd` and `/etc/group` of the step's base (a user alone takes its primary
  group, as `.user` does); a uid alone as a number gets the group of the same number, as
  BuildKit gives `--chown=1000` the owner 1000:1000; a name the base lacks, the id 4294967295, or
  an id above 65536 that the store's user namespace cannot map, is E0817, one line naming the id
  and the mapped range. A passwd larger than 128 KiB (group 256 KiB) is named as too large, not
  as a missing name. Both fields are in the step's key, each on its own: a changed `.chmod` alone
  misses. The restamp walks at most `store_walk_entries_max` entries, as `store verify` does;
  past that the step is refused, never a crash. Every file, directory and symlink
  the patterns take gets the owner; the mode goes on files and directories, not symlinks.
  Directories made on the way to `.to` get the owner (Docker's "new files and directories") and
  keep 0755; a directory that already exists in the base keeps the base's attributes. On a host
  that maps one id (W0201) every owner is 0:0, as an import's is; the mode still applies.
  The cache keys the `.chown` text, not the ids written, so a step built under W0201 keeps its
  0:0 output as a hit after `newuidmap` is installed. zbx has no flag to skip the cache yet;
  a changed `.chown` text (such as `app` written as `1000:1001`) builds it again with the real
  owner. Keying the map's kind as well is left to a later milestone.
- **Excluded directories.** With no `!` line in the exclude lists an excluded directory is
  skipped wholesale. With any `!` line an excluded directory is still entered, so a file a `!`
  line brings back is found, and empty directories can result.
- **Multiple matches to a `.to` with no trailing `/`** are refused (E0803, naming the count),
  as Docker refuses them; before 0.5.1 the later one silently won. A `.to` ending in `/` puts
  each match inside.
- **`.src = .{"."}`** from the project copies the whole project: every top-level entry, found
  and excluded as the glob `*` finds them, each laid whole under `.to`, so `src/a.txt` lands at
  `<to>/src/a.txt` as Docker's `COPY .` puts it. `./a.txt`, `a/`, `a//b` and `a/./b` are
  refused when the file is read (E0801, "has an empty or . part"): a project source is `.`, a
  plain relative path or a glob of one. 0.5.1 refused `.` too and suggested `.src = .{"*"}`,
  which flattens each top-level directory into `.to`; 0.5.2 takes `.` again
  (docs/decisions/2026-11-14-m9-copy-dot-is-whole-project.md). From a `step:` source `.` or `/`
  copies the whole tree.
- **Owners of copied files** without `.chown` are the source's: a project file is 0:0 as every
  input is. Docker gives `--chown`-less copies root, which is the same here.
- **A source is a tree, not a stream:** a `step:` source's globs are matched against its output
  tree at build time, so a glob that matches nothing is E0803 naming the step.
- **Rooting:** every tree a step reads after the import that wrote it is rooted `build:<step>`
  until it is used, so a concurrent `store gc` cannot remove it in between: a copy's source tree
  and its selection trees (dropped once the output is recorded) and a command step's input tree and its binds' selection trees
  (dropped on a hit, on an error, and when its worker settles or is aborted). Roots are
  counted per tree within a build, so the first of two steps that share a tree (the same
  inputs, the same bind selection, a copy's source) to finish keeps the root for the other. A
  build stopped by SIGINT or SIGTERM, at any point up to the image's record, aborts its workers
  and drops its roots (E0808, one line naming the signal; never exit 0). A build killed
  with SIGKILL, or two `zbx build` processes on one project that share a tree, can still leave
  or drop a root early: `zbx store gc` lists a leftover and the user may remove it.
- **`.caches`** run (`cache` mount kind): `build/caches/<group>/<name>`, outside the step key,
  steps sharing an id run one after another. The report marks such a step `cache` (text, and
  `"caches":true` in JSON); `W0802` is printed once on stderr naming them; cache
  directories are not locked between two `zbx build` processes on one project, so run one build
  at a time per project (a known limit); `zbx build
  --clear-caches` empties the cache directories first, under the exclusive store lock (E0436
  when busy). `--graph` with `--clear-caches` clears nothing.
- **`.binds` from a `step:` output** run: the selection of the bind's `.source` in that step's
  output is part of the key (a file outside it changes nothing) and is mounted read-only at
  `.to`. A single-file source mounts a directory holding that file. A source that matches
  nothing is E0803. A bind from the project's files or a locked image stays E0802 for good.
- **A non-root `.user` with a writable `/out`** is refused by `needs_root` in this slice: the
  output would belong to ids the parent cannot write (`2026-11-13-m9-nonroot-out-refused.md`).
- **`zig build check` and the VM:** see the slice's handoff in `docs/decisions/`.

### Differences from Docker (what the demo shows)

- An `ARG` with no default and no `--build-arg` is refused (E0812); Docker substitutes the empty
  string.
- `EXPOSE`, `HEALTHCHECK`, `# syntax` and the like become labels or are dropped, with W0811.
- `RUN` steps get the network only when the translator matches a fetching command (W0810), and
  `--hermetic` refuses them (E0814).
- `FROM scratch` with steps, `ADD <url>`, `ADD <git>`, binds from the context and `--platform`
  other than the host are refused (E0811).

## Slice 3: the Dockerfile translator and `zbx import`

What ran: unit tests (the fixtures through a table resolver, 24 then and 29 Dockerfiles with
33 goldens since the slice's fixes, the library test with two
callers on two threads), the `dockerfile` fuzzer, and smoke runs of the real binary on the cloud
container, which is not the test VM (`zbx import` of a small Dockerfile against Docker Hub
through `ZBX_REGISTRY_MIRRORS`). No VM demo ran: `demo-m9` is slice 4's.

The fuzzer found two translator bugs before the first commit of it: `COPY --from=` with no name
reached the resolver, and a `<<` that names no heredoc (`<<{OF`) was read as a heredoc and
tripped an assertion. Both are fixed and the second has a unit test.

### Cuts and deviations (recorded)

- **`FROM scratch` with steps is E0811.** The builder has no scratch base (`compose.zig` resolves
  every base through the lock). A scratch target with config only becomes an image with no base.
- **`RUN --mount=type=bind` from the context or an image is E0811**, because the builder refuses
  those binds for good (`graph.zig`). A bind from another stage is translated.
- **Copies from an image and `--exclude` on a copy from a stage are still E0802 at build time**
  (the slice 2 cut), so a translated file can be refused by `zbx build`. The translator keeps
  them in the build file and the import report notes each one (W0811: "kept, but zbx build
  refuses it (E0802) for now"). `--chown` and `--chmod` are built and get no note.
- **`WORKDIR` does not create the directory.** Docker creates a `WORKDIR` that does not exist; the
  build file only sets `.workdir`, so a step whose directory no base or earlier step made fails
  at run time.
- **`--hermetic` refuses only the network and a cache mount** (review of PR #145). A bind from a
  step's output is part of the build's inputs, so it is hermetic and passes.
- **A variable `--from` or mount `from=` is expanded with the ARGs before the first FROM only**,
  as BuildKit does. One that names nothing that way is E0812.
- **`COPY` and `ADD` in exec form (JSON) are not substituted**: the words are taken as written.
- **The lock is found from the working directory, not from `--context`.** `zbx import` reads and
  writes `zbx.lock` beside where it runs, as `zbx pull` does; the build file it writes is where
  `-o` says.
- **E0816 covers both "the output exists" and "the write failed"** (supervisor ruling, no new
  code).
- **The help text lost some words.** `zbx help` must stay under `output_bytes_max` with a
  512-byte margin, and the import section needed about 1.5 KB, so a number of existing help lines
  were shortened (log, state and policy paths, exec, `--net`, and similar). No limit was raised.

## Slice 3b: pinned fetches

`.fetch` copy sources (parser, printer, validation), the download in the parent through the
pull's client, the tagged key without the URL, Docker's remote-`ADD` defaults (`0600`, `0:0`, the
name from the URL when `.to` ends in `/`), gc keeping fetched blobs, `E0820`, `E0821`, and
`ADD --checksum=sha256:<hex> <url> <dest>` in the translator.

Demo step 7 is the part FETCH9 of the first VM (`src/testing/vm/fetch_m9.zig`, every assertion in
`checks_fetch_m9.zig` with a unit test). The project is `src/testing/vm/m9_fetch/`; the file
server is `src/testing/vm/fixture_http.zig`, built for the guest (x86_64, static, no libc) with
the harness and served to the guest beside `zbx`. It listens on `127.0.0.1:8080`, a fixed port,
so that the Dockerfile and its pin are files of the repository rather than text the harness
writes.

### Cuts and deviations (recorded)

- **`drift.build.zon` is not in `m9_fetch/` yet.** It belongs to step 8, which is slice 3c's.
- **The fetch is downloaded when its step misses, under the store's shared lock**, in the
  step's copy, and only when the blob is not in the store whole (its SHA-256 is checked again
  before it is trusted). A hit never downloads, so a warm store makes no request, which is what
  the demo checks. Each download writes its own partial file and checks the hash before the
  rename, so two builds fetching one pin at once do not share bytes.
- **The provenance input of a step whose first source is a fetch is the pin**, not a tree: it
  is the same whether the blob was downloaded in this build or was already there.
- **`ADD --checksum` substitutes `ARG`s in the URL**, as Docker does; the build file holds the
  URL the hash pins.
- **`.src = "."` keeps a link at the top of the project as a link**, as `COPY .` does; a link
  the file names (`.src = "link"`) is still followed.
- **A build whose first act is a download now makes the store**, as a pull does. Before the fix,
  a build of a fetch in a store not made yet refused with `E0417` ("making the blob directory
  failed"); the VM caught it and `compose_tests.zig` keeps it. As for every command, the store is
  made below `XDG_DATA_HOME`, which must exist, so the demo makes the fresh one first.

### Cuts and deviations (recorded)

- **A uuid stands in for a changed download.** Step 8's network step writes
  `/proc/sys/kernel/random/uuid`, so a fresh store in the second VM gives another output without
  the demo depending on a mirror changing under it. The step still has `.network = true`, which is

- **A pin's `.file` is the build file's path relative to the project directory**, as the build

- **A stale pin's fix is `zbx build --pin`.** There is no `--repin`: under `--pin` a step whose

- **A pin is keyed by the build file and the step's name.** Renaming a pinned step leaves its old

  since that would be a new code; `zbx build --pin` writes the pin under the new name.
- **AGENT's `zbx build --output json --locked` on the drift case is not run in the VM.** The JSON
  form of E0822 is covered by its snapshot (`src/testdata/diag/E0822.json.txt`).

## Slice 5: the Mac

**Status: built, not run on a Mac.** No Mac or self-hosted runner was reachable from the session
that built it: the Linux gates pass, the macOS `zbx` and the test roots cross-compile for
`aarch64-macos`, and `demo-mac`'s new steps have not run. They run with `zig build demo-mac` on the
owner's Mac or on the `mac` workflow's self-hosted runner.

- **`import`, `build` and `inspect` are forwarded** (`src/forward_commands.zig`) to the Linux
  `zbx` in the machine, like `run` and `pull`: the project is under the shared home, at the same
  path, so the Dockerfile, the lock and `zbx.build.zon` are where the Linux `zbx` looks for them.
  None asks for a passphrase, so all keep the terminal (`forward_commands_tests.zig` reads their
  sources). `zbx inspect [--provenance] <digest>` works on the Mac as `build`'s help says. The
  Mac's `help` lists them.
- **Paths outside the home are refused on the Mac.** The machine shares the home and nothing
  else, so a `-o`, `-f` or `--context` of `build` or `import` that is absolute or climbs with
  `..` out of the home is `ZBX-E1013` ("… is not shared with the virtual machine; only <home>
  is"), before the machine is asked, as a working directory outside the home already was. Paths
  inside the home work unchanged. The positional Dockerfile of `import` is not checked on the Mac
  (a cut: an outside one is refused by the Linux `zbx`, which cannot read it).
- **`--platform` is refused for `build`, `import` and `inspect`** as on Linux (`E0004`, an
  unknown option): the Mac takes it out of the command line only for the other commands (`run`,
  `pull`), and passes it through to these three for the Linux `zbx` to refuse.
- **Rosetta.** A forwarded `build` or `import` whose project lock (the nearest `zbx.lock` from
  the working directory up, as the Linux `zbx` finds it) pins any `linux/amd64` entry is refused
  with `ZBX-E1016` on a Mac without Rosetta, as `run --platform linux/amd64` is, with
  `softwareupdate --install-rosetta --agree-to-license` and then `zbx vm stop`. A lock the Mac
  cannot read is left to the Linux `zbx`. Cut: a `RUN` step that fails inside the machine with
  ENOEXEC (an amd64 binary with no Rosetta, from a base the lock does not name) is not mapped to
  `E1016`; it fails as that step's own error.
- **`build` was not forwarded before.** The brief says "`import` forwarded like `build`", but M7's
  Mac slice was cut (M7 brief, open question 6), so `build` was not in the table either. Importing
  without building is half a demo, so this slice forwards both. That also lets M8's provenance
  reach Mac builds (the M8 brief's slice 9 note).
- **`demo-mac` steps m9.1 to m9.5** (`src/testing/mac_demo.zig`): the project of `demo-m9`
  (`m9_project/`; a unit test checks that its list names the same files as `hello_m9.zig`'s) is
  written afresh to `~/zbx-demo-mac/m9-project`.
  - m9.1: `zbx import` writes `demo-m9`'s golden build file byte for byte, owned by the Mac user,
    with W0811, and leaves `zbx.lock` byte for byte as written.
  - m9.2: `zbx build` (its exit code checked) prints a digest and keeps the lock; the image prints
    `hello from zigbox`, and its `--whoami` prints exactly `10001`.
  - m9.3: `demo-m9`'s pair: an `extra.go` made on the Mac (`sed 's/func main/func init/'
    main.go`) gives at least one miss and a digest other than m9.2's; with it removed, `0 misses`
    and m9.2's digest again.
  - m9.4: that digest is `demo-m9`'s golden (`m9_expected.zon`).
  - m9.5: a second project, `~/zbx-demo-mac/m9-native` (`FROM alpine:3.20`, `RUN uname -m >
    /arch`, an empty lock of its own), is locked by `zbx pull` to the machine's own platform
    (`linux/arm64`, checked in the lock), imported and built natively, with no Rosetta; its image
    prints `aarch64`. No golden digest is compared for it.
- **The M9 steps m9.1 to m9.4 need Rosetta.** The lock pins `linux/amd64`, as `demo-m9`'s does,
  so that the Mac's digest can be compared with the golden recorded in a Linux VM. `demo-mac`
  asks `zbx doctor` first; without Rosetta those four steps fail, each with one line naming
  `ZBX-E1016` and `softwareupdate --install-rosetta`, and m9.5 still runs. If m9.4 fails on a Mac
  while m9.1 to m9.3 pass, the difference is between the two machines (Rosetta or virtiofs); the
  failure prints the Mac's digest, the lines of a listing of its image tree (path, mode, owner,
  type, a file's SHA-256 prefix) that differ from the golden tree's (`m9_expected.tree.txt`,
  recorded from a Linux build that printed the golden digest), and what `zbx inspect` says.
  PR #168's first Mac run (run 43742279700) failed m9.4 with
  `b3:7681469b90a9416931ee5561bf4257ca8ab1c9a5bfaa0b623957326a2775ac53`, m9.1 to m9.3 and m9.5
  passing; the listing was added to find out which files differ. On the next run (43747691774)
  it showed the only difference: `/root/.cache` and `/root/.cache/rosetta`, empty directories
  Rosetta made while the final stage's `RUN` ran. Every file, the Go binary compiled under
  Rosetta included, matched.
- **Rosetta's cache is not in a step's output.** A root step whose platform is not the
  machine's (on a Mac, linux/amd64 under Rosetta) leaves `<home>/.cache/rosetta` out of its
  output, and `<home>/.cache` too when its base lacks it and it holds nothing else; a `.cache`
  the base has, and the step's own files in it, stay
  (docs/decisions/2026-11-15-rosetta-cache-not-in-output.md). The first run with that rule (job
  132951593134) still failed m9.4 with the same digest: m9.2 was all hits on the entry the
  run before had written, because the rule did not change the step's key. A hit is now checked
  against the same rule, and an entry that breaks it is removed and the step runs again.
- **m9.3's `extra.go` is new each run.** The Mac's store outlives a run, so a second run of the
  same `extra.go` was all hits and m9.3 failed (run 43747691774). The file now ends in a comment
  with the time and the shell's pid.
- **Time on the runner.** `mac.yml` gives the whole job 60 minutes. The first M9 build on a fresh
  machine pulls the amd64 golang base and compiles Go under Rosetta, which is the slowest step of
  `demo-mac`; if the job meets the timeout there, a second run (warm store and cache) is the
  measure, and the timeout is raised only with that evidence.
- **The native arm64 path is shown only by m9.5**, a trivial build with no golden digest. M7's
  cross-machine arm64 criterion (the same arm64 digest on two machines) stays open: it needs an
  arm64 golden recorded on a second arm64 machine, which needs the owner's sign-off to record.
