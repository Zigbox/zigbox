# M9 demo: Dockerfile import and the builder additions

Until the `demo-m9` job is green in CI, M9 is built, not demonstrated. Slice 2 (this file's
first version) ran no VM demo; slice 4's `demo-m9` passed on a `vm/` branch (see the demo's
status below).

Brief: `docs/briefs/M9-dockerfile-import.md`. Slice 2 builds what the brief's "builder additions"
describe: input globs and `.exclude`, copy steps, `image.base = "step:"` and named
`config.user`. Unit and simulated-store tests cover them (`copy_tests.zig`,
`compose_tests.zig`); nothing here ran in a guest.

## What slice 2 built

- **Input globs and `.exclude`** (`glob.zig`, `input_tree.zig`): E0818 when a build's globs match
  more than `build_glob_matches_max` paths.
- **Copy steps** (`copy.zig`, `compose.zig`): a step with `.copy` runs no container. For each
  entry the parent selects the source's matching paths into a tree laid under `.to`, puts the
  selection's digest in the step's key, and lays every selection over the base with
  replace-merge (a later file replaces an earlier one; two directories merge). A file the
  patterns do not take never changes the key. The output is rooted like a root step's.
- **`image.base = "step:<name>"`**: the result's tree is that step's output; config is inherited
  from the image the chain of `step:` bases began with; provenance names that image.
- **`config.user` as a name**: looked up in the result's tree (E0817 if absent); the record
  holds `uid:gid`.

## Cuts and deviations (recorded)

- **Still E0802 (read, not built):** a bind from the project's files or from a locked image (cut
  for good) and a `.binds` on a copy step; a copy from a locked image; an `.exclude` on a copy
  from a `step:`.
- **A copy's `.chown` and `.chmod`** run (`2026-11-14-m9-copy-chown.md`). The selection is made
  in the parent; an owner or mode is part of a file object's id, so the new objects are written
  in a single-threaded child inside the store's user namespace, before any exec. A name is
  looked up in `/etc/passwd` and `/etc/group` of the step's base (a user alone takes its primary
  group, as `.user` does); numbers are taken as written; a name the base lacks, or the id
  4294967295, is E0817. Both fields are in the step's key. Every file, directory and symlink
  the patterns take gets the owner; the mode goes on files and directories, not symlinks.
  Directories made on the way to `.to` get the owner (Docker's "new files and directories") and
  keep 0755; a directory that already exists in the base keeps the base's attributes. On a host
  that maps one id (W0201) every owner is 0:0, as an import's is; the mode still applies.
- **Excluded directories.** With no `!` line in the exclude lists an excluded directory is
  skipped wholesale. With any `!` line an excluded directory is still entered, so a file a `!`
  line brings back is found, and empty directories can result.
- **Multiple matches to a `.to` with no trailing `/`:** the matches land on the same path and
  the later one wins (Docker refuses it). A `.to` ending in `/` puts each match inside.
- **`.src = .{"."}`** is refused as an input (a project path is a plain relative path); from a
  `step:` source `.` or `/` copies the whole tree.
- **Owners of copied files** without `.chown` are the source's: a project file is 0:0 as every
  input is. Docker gives `--chown`-less copies root, which is the same here.
- **A source is a tree, not a stream:** a `step:` source's globs are matched against its output
  tree at build time, so a glob that matches nothing is E0803 naming the step.
- **Rooting:** every tree a step reads after the import that wrote it is rooted `build:<step>`
  until it is used, so a concurrent `store gc` cannot remove it in between: a copy's source tree
  and its selection trees (dropped once the output is recorded) and a command step's input tree and its binds' selection trees
  (dropped on a hit, on an error, and when its worker settles or is aborted). Roots are
  counted per tree within a build, so the first of two steps that share a tree (the same
  inputs, the same bind selection, a copy's source) to finish keeps the root for the other. A
  build stopped by SIGINT or SIGTERM, at any point up to the image's record, aborts its workers
  and drops its roots (E0808, one line naming the signal; never exit 0). A build killed
  with SIGKILL, or two `zbx build` processes on one project that share a tree, can still leave
  or drop a root early: `zbx store gc` lists a leftover and the user may remove it.
- **`.caches`** run (`cache` mount kind): `build/caches/<group>/<name>`, outside the step key,
  steps sharing an id run one after another. The report marks such a step `cache` (text, and
  `"caches":true` in JSON); `W0802` is printed once on stderr naming them; cache
  directories are not locked between two `zbx build` processes on one project, so run one build
  at a time per project (a known limit); `zbx build
  --clear-caches` empties the cache directories first, under the exclusive store lock (E0436
  when busy). `--graph` with `--clear-caches` clears nothing.
- **`.binds` from a `step:` output** run: the selection of the bind's `.source` in that step's
  output is part of the key (a file outside it changes nothing) and is mounted read-only at
  `.to`. A single-file source mounts a directory holding that file. A source that matches
  nothing is E0803. A bind from the project's files or a locked image stays E0802 for good.
- **A non-root `.user` with a writable `/out`** is refused by `needs_root` in this slice: the
  output would belong to ids the parent cannot write (`2026-11-13-m9-nonroot-out-refused.md`).
- **`zig build check` and the VM:** see the slice's handoff in `docs/decisions/`.

### By hand

In a guest with `zbx` on the `PATH`, as an ordinary user, with `ZBX_REGISTRY_MIRRORS=mirror.gcr.io`:

```sh
cp -a src/testing/vm/m9_project ~/hello && cd ~/hello   # (the harness writes these files)
zbx import                         # exit 0; zbx.build.zon is m9_expected.build.zon; W0811 on stderr
zbx build                          # ends `built b3:<64 hex>`
zbx run <digest>                   # hello from zigbox
zbx run <digest> -- /usr/local/bin/hello --whoami     # 10001
zbx inspect <digest> --output json # user 10001:10001, workdir /home/app, the two labels
zbx build --output json            # every step hit, the same digest
echo more >> README.md && zbx build                   # all hits, the same digest
sed 's/func main/func init/' main.go > extra.go && zbx build   # build stage misses, new digest
rm extra.go && zbx build           # the first digest, every step a hit
zbx import --target tools -o tools.build.zon          # tools-1 flagged net and cache, W0810
zbx import --target tools --hermetic -o t2.build.zon  # exit 1, E0814 at Dockerfile:11, no file
zbx build -f tools.build.zon       # W0801, W0802
zbx run <it> -- curl --version     # exit 0
```

### Cuts and deviations (recorded)

- **The second Go file** is `main.go` with `func main` renamed `func init` (`sed`), not a second
  renamed function: the brief only needs a file that the glob takes and that compiles.
- **`main.go` reads `--whoami` from its last argument**, so the brief's literal
  `zbx run <d> -- /usr/local/bin/hello --whoami` works: the entrypoint is kept and the path is
  hello's first argument, as Docker does it.
- **Owner and mode of `/etc/hello/VERSION`** are read with `stat` in a run of the image, not
  from the store's tree, which the harness cannot walk without the store's code.
- **`W0810` is not the last line of the tools report**, as the brief has it ("ends with
  `W0810`"): the report's `W0811` follows it. The demo asserts both, W0810 then W0811
  (supervisor ruling).
- **EXPOSE and HEALTHCHECK are read from the report's "not carried over" list**, not from
  W0811's cause, which is cut after a few entries. `zbx import` writes the text report and then
  its warnings to stderr and nothing to stdout, so the checks split stderr at the first warning.
- **ACCEPT runs 11 of the fixtures through the binary**, those whose bases are in the demo lock
  (`src/build/dockerfile_fixtures/vm_cases.zig`). The rest name node, python, debian, nginx,
  other golang tags, quay.io or mcr.microsoft.com: gigabytes of pulls or registries zbx does not
  pull from. All of them are checked against their goldens by `zig build test` through the
  library.
- **No upgrade test.** `demo-m9` is generated from `demo-m7` without its old-binary part.
- **`m9_expected.build.zon` is excluded from `zig fmt`**: zbx writes a one-element tuple as
  `.{ "go.mod" }`, which zig fmt would rewrite. The golden is what zbx writes.

### Differences from Docker (what the demo shows)

- An `ARG` with no default and no `--build-arg` is refused (E0812); Docker substitutes the empty
  string.
- `EXPOSE`, `HEALTHCHECK`, `# syntax` and the like become labels or are dropped, with W0811.
- `RUN` steps get the network only when the translator matches a fetching command (W0810), and
  `--hermetic` refuses them (E0814).
- `FROM scratch` with steps, `ADD <url>`, `ADD <git>`, binds from the context and `--platform`
  other than the host are refused (E0811).

### The corpus run

The survey's 61 Dockerfiles (`docs/research/2026-11-11-dockerfile-survey.md`), fetched on
2026-11-14 in the session and not checked in, each through the library (`translate.translate`)
with the fixtures' table resolver (every base resolves, with Docker's default `PATH` and no image
env), `linux/amd64`. No crash, no assertion, and every refusal a registered code.

| Pass | Translated | Refused |
|------|-----------:|--------:|
| No `--build-arg` | 37 | 24: E0812 ×12, E0811 ×11, E0810 ×1 |
| Each E0812's ARG given a value | 45 | 16: E0811 ×15, E0810 ×1 |

The 16 refused with values: a bind from the context (gitea, InvokeAI, vllm), a bind from an image
(open-webui), `--mount=type=tmpfs` (docker/cli), `ADD <url>` (keycloak, mastodon, ultralytics),
steps on `FROM scratch` (monero, lazydocker), a scratch stage with no steps used by a copy
(grafana), `--platform=linux/arm64` (ollama), `${X#...}` (moby), `COPY --parents`
(home-assistant), `USER ${NB_UID}` (jupyter, E0810): `NB_UID` is an image variable, set by
the base image's `ENV`, not an `ARG`, and the table resolver gives no image env (a real pull
does). The refusal's fix said "give the ARG a value"; it now says to give the variable a value
(`--build-arg` for an ARG, or the base image's ENV once pulled). And authelia, whose dummy value
`x` made a digest reference the build file cannot hold (an artifact of the run, not a finding).

## Slice 3: the Dockerfile translator and `zbx import`

What ran: unit tests (the 24 fixtures through a table resolver, the library test with two
callers on two threads), the `dockerfile` fuzzer, and smoke runs of the real binary on the cloud
container, which is not the test VM (`zbx import` of a small Dockerfile against Docker Hub
through `ZBX_REGISTRY_MIRRORS`). No VM demo ran: `demo-m9` is slice 4's.

The fuzzer found two translator bugs before the first commit of it: `COPY --from=` with no name
reached the resolver, and a `<<` that names no heredoc (`<<{OF`) was read as a heredoc and
tripped an assertion. Both are fixed and the second has a unit test.

### Cuts and deviations (recorded)

- **`FROM scratch` with steps is E0811.** The builder has no scratch base (`compose.zig` resolves
  every base through the lock). A scratch target with config only becomes an image with no base.
- **`RUN --mount=type=bind` from the context or an image is E0811**, because the builder refuses
  those binds for good (`graph.zig`). A bind from another stage is translated.
- **Copies from an image and `--exclude` on a copy from a stage are still E0802 at build time**
  (the slice 2 cut), so a translated file can be refused by `zbx build`. The translator keeps
  them in the build file and the import report notes each one (W0811: "kept, but zbx build
  refuses it (E0802) for now"). `--chown` and `--chmod` are built and get no note.
- **`WORKDIR` does not create the directory.** Docker creates a `WORKDIR` that does not exist; the
  build file only sets `.workdir`, so a step whose directory no base or earlier step made fails
  at run time.
- **`--hermetic` refuses only the network and a cache mount** (review of PR #145). A bind from a
  step's output is part of the build's inputs, so it is hermetic and passes.
- **A variable `--from` or mount `from=` is expanded with the ARGs before the first FROM only**,
  as BuildKit does. One that names nothing that way is E0812.
- **`COPY` and `ADD` in exec form (JSON) are not substituted**: the words are taken as written.
- **The lock is found from the working directory, not from `--context`.** `zbx import` reads and
  writes `zbx.lock` beside where it runs, as `zbx pull` does; the build file it writes is where
  `-o` says.
- **E0816 covers both "the output exists" and "the write failed"** (supervisor ruling, no new
  code).
- **The help text lost some words.** `zbx help` must stay under `output_bytes_max` with a
  512-byte margin, and the import section needed about 1.5 KB, so a number of existing help lines
  were shortened (log, state and policy paths, exec, `--net`, and similar). No limit was raised.
