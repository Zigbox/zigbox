### Layout

```
$XDG_DATA_HOME/zbx/state/            (or ~/.local/share/zbx/state)
  <name>/data/                       the volume's files, bound into the container
  <name>/state.zon                   created, last used, last container, last path, :ro
  <name>/lock                        flock target
  .trash/<name>@<seconds>/           a volume `state rm` moved, whole
```

`<name>/`, the record and the lock are the user's own; `data/` is made by the container's root
inside the container's user namespace (the plan step `make_state_data`, after the id maps are
written and before the user is changed), so it is owned by root in the container and by the user
on the host, and what the container `chown`s inside it is owned through the map (postgres's 999 is
100998 on a host whose range starts at 100000).

### How a run mounts a volume

1. `--state` is parsed as it is read: a bad name is `E0705`, a bad path or list `E0005`. A target
   is absolute, every part a name (no empty, `.` or `..` part, no `:`), at most 256 bytes, not `/`,
   not under `/proc`, `/sys` or `/dev`, not one of the generated `/etc` files, and holds no `:`, space or control byte. One run names a
   volume once, and no target is at or below another's.
2. In `start`, after everything that can fail without the volumes (the name, the checks, the
   scope, the image), each volume's directory is made if new, its lock taken, and its record
   read (a damaged or newer one is `E0712`) and written with this container, its path and the
   time. The volumes are taken last so that every later way out of `start` lets them go.
3. In the child, before the new root is entered: `data/` made, a hidden directory
   `/dev/.zbx-state-<n>` made on the container's fresh `/dev`, the volume bound there, and made
   read-only for `:ro`. After the new root is entered: the target is made with its parents and
   the volume moved onto it (`MS_MOVE`), and the hidden directory removed. The target is so read
   as the container reads it: a symlink in the image resolves inside the container, never on the
   host. A failed step is `E0713`.
4. The run record (version 6) lists the volumes as one string of `--state` values separated by
   spaces (a target holds no space), the way slice 1 keeps the `-e` names: two strings in a row
   would read to the bundle's redactor as a secret's name and value.
5. `wait` lets the locks go once the container is reaped.

### The lock: what holds it, and why

- **The holder is the process that calls `start` and `wait`**: `zbx run` in the foreground, the
  supervisor of a detached run (`run -d` forks the supervisor before `start`, so the caller of
  `run -d` never holds it), or Zigcube's agent's supervisor. The lock lives in the library's
  `Handle`, so a library caller gets the same rule.
- **flock on an `O_CLOEXEC` descriptor.** The container's child inherits it through `clone3` and
  closes it at `execve`; the keeper closes every descriptor it does not need; pasta's `execve`
  closes it. Only the holder keeps the open file description, so its death frees the lock.
- **Every exit path:** a clean exit, an exit code, `zbx stop` (the supervisor's `wait` returns),
  `--timeout`, a killed container: `wait` releases after the reap. A start that fails releases
  before it returns (an `errdefer` from the moment the volumes are taken). SIGKILL of `zbx` or of
  a supervisor: the kernel closes its descriptors, and the container's PID 1 dies with its parent
  (`PR_SET_PDEATHSIG`), so a volume never has a writer its lock does not know of.
- **A lock file left by a crash** is only a file: flock is not persistent. Nothing cleans it up
  and nothing needs to. The text an exclusive holder writes (`<pid> <container>`, cut to 64 bytes)
  is read only when the lock is found held exclusive, and a refusal names the holder by the
  running run record whose supervisor is that pid, else by the text.
- **A run waits half a second** (`state_lock_wait_ms`) for a busy lock before it refuses, so a
  `zbx state rm` holding it for a moment is not mistaken for a writer; `state rm` itself does not
  wait. A second writer is `E0706`, exit 125, naming the container; a reader beside a writer, and
  a writer beside readers, the same.

### The state commands

- `zbx state ls [--output json]` (`zbx.state.ls/1`): each volume's name, size (`disk_bytes`, the
  blocks on the disk, and `bytes`, the files' sizes, each inode once), `files`, created, last
  used (the last time a run took it), last container and path, whether a running container uses
  it and which (from the run records), and the trash with each entry's expiry. The size is
  counted in the store's namespace child; a count that stops (an unreadable file, a tree past 64
  levels, past the entry or hard-link bounds) is `W0702` and the size is `null`, never a guess.
- `zbx state rm NAME` (`zbx.state.rm/1`) takes the lock exclusive without waiting (busy: `E0706`),
  and in the namespace child renames the volume to `.trash/<name>@<seconds>`, then empties every
  trash entry past `store_trash_seconds` (7 days), as gc does with its own trash.
- `zbx state restore NAME` (`zbx.state.restore/1`) takes the newest trash entry of the name:
  none is `E0709`, an expired one `E0710` (it is not brought back; the next `rm` empties it), a
  volume made again under the name `E0708` naming both. The rename runs in the namespace child.
- `zbx store gc` works inside the store's directory only; a test plans and confirms a gc past every
  expiry beside a state directory and checks every path under `state/` is unchanged.

### Decisions the brief left open

- **The size is the disk's.** `ls` shows `disk_bytes` in text; JSON has both.
- **"Last used" is when a run last took the volume**, written at the start: a run killed with
  SIGKILL cannot write at its end, and the start is the one time every run passes.
- **The trash holds the whole volume directory**, record and lock included, under
  `<name>@<seconds>`; two removals of one name are two entries, and `restore` takes the newest.
- **A `:ro` first use makes the volume**, empty, as a read-write one does.
- **The mount targets' rules** are slice 3's in the brief ("Other mounts"); slice 2 needed them
  for `--state` and implements them in `volume.target_problem`, which slice 3 can share.

### Cuts and known limits

- The run fuzzer does not generate `--state` runs; the exit paths are covered by
  `volume_tests.zig` one by one, and the VM part.
- `restore` renames over the name after checking it is free; a run making the name in the same
  instant loses to `rename(2)`'s rules (it fails on a non-empty directory). Not seen, not tested.
- Expired trash that cannot be removed stays for the next `rm`, silently.
- When `zbx` itself is killed, the kernel frees the volume's lock at once, but the container's
  processes die a moment later (PID 1 by `PDEATHSIG`, the rest with its PID namespace). A second
  run that takes the lock in that window can start while the old container is still exiting.
  Postgres's own `postmaster.pid` refuses a second postmaster on the same data directory, so the
  demo's case is covered by the database itself; a program without such a lock is not. Holding
  the lock until the old container's cgroup is empty would close it: a later change.
- In the simulator the container model and the file tree are separate; a test that checks both
  puts the volume's directory in each.

### Failure modes

| What | How it shows | Recovery |
| --- | --- | --- |
| a volume in use by another run | `E0706` naming it, exit 125 (1 for `state rm`) | `zbx stop <name>`, or `:ro` |
| a bad name, a bad path | `E0705`, `E0005` | fix the flag |
| no `HOME`/`XDG_DATA_HOME`, or a state directory that cannot be made | `E0711` naming the path | set one, free space |
| a damaged or newer `state.zon` | `E0712` | move it aside; the data is not in it |
| a mount step refused, or a missing path in a `--read-only` root | `E0713` | `zbx doctor`; a path the image has |
| `rm` of a name that is not there | `E0707` | `zbx state ls` |
| `restore` with nothing in the trash, after the expiry, over a new volume | `E0709`, `E0710`, `E0708` | `zbx state ls` |
| a size that cannot be counted | `W0702`, size `null` | count it by hand in the user's namespace |
| zbx or its supervisor killed | the lock is free; the container died with it | run again |

## Slice 3: other mounts and `state export`

`--tmpfs PATH[:SIZE]`, `--bind HOST:PATH`, `--secret HOST_FILE:PATH`, the target rules they share
with `--state`, and `zbx state export NAME [-o FILE]`. Codes `E0012`, `E0013`, `E0210`, `E0211`,
`E0714` to `E0716` and `W0703`, each with a golden (`src/diag_golden.zig`) and an error page
(`site/errors/`). The run record is version 7 (it keeps the mounts); a record of version 4 to 6 is
still read.

### What is where

| What | Where |
| --- | --- |
| flag parsing, the shared target rules (absolute, no `..`, no duplicates, nothing at, in or over another, nothing over `/proc`, `/sys`, `/dev` or `/etc/hosts`, `/etc/hostname`, `/etc/resolv.conf`) | `src/runtime/mounts.zig` (rules also used by `state/volume.zig`) |
| the plan steps and the child's work (stage under `/dev/.zbx-mount-N`, move onto the target after the new root is entered) | `src/runtime/plan.zig`, `src/runtime/child.zig` |
| the refusals | `src/runtime/mounts_diagnose.zig`, `src/state/diagnose.zig` |
| the record's `mounts` | `src/runtime/records.zig` (never the secret's bytes: only the host path and the target) |
| the commit leaves every mount point as the parent has it | `src/runtime/` commit path, tested in `mount_tests.zig` |
| `state export` | `src/state/export.zig` (gzip tar with std's writers), `src/state_commands.zig` |
| bounds | `constants.zig`: `mounts_max` 8, `mount_path_bytes_max`, `tmpfs_mount_bytes_default` 64 MiB, `_min`, `_max`, `secret_bytes_max` 64 KiB, `state_export_notes_max` |
| fuzzers | `fuzz_cli`, `fuzz_run`, `fuzz_record`, `fuzz_state` |

A `--secret` is copied into the container's own memory (a tmpfs file, mode 0400, owned by the
container's root, mounted read-only). A `--bind` is always read-only. A `--tmpfs` is `nosuid,nodev,
noexec`, mode 1777, and its pages are charged to the container's cgroup, so `--memory` holds for
them.

### Cuts and known limits

- A `--secret` is a file of at most 64 KiB; there is no directory form.
- `--bind` has no read-write form (the brief says always read-only).
- A tmpfs is never `exec`; there is no flag for it.
- `state export` writes owners as the container sees them (999 stays 999), keeps symlinks, hard
  links, modes and times, and leaves out devices, sockets and fifos with one `W0703` note each (up
  to 16 notes, then a count). It refuses a volume a container is writing (`E0706`) and a terminal
  (`E0714`). Extended attributes are not archived.

### Failure modes

A mount that does not parse (`E0012`), two that collide (`E0013`), a source that is missing or not
a file or directory of the right kind (`E0210`), a mount that fails in the child (`E0211`), an
export to a terminal (`E0714`), a file that cannot be written (`E0715`), a volume that cannot be
read (`E0716`), a file left out (`W0703`). Each is one line with the cause and the fix; the export
is written to a temporary name and renamed, so a stopped export leaves no half archive.

## Slice 4 (second part): the agent test, the top-20 run, the by-hand steps, failure modes

### The agent test (demo-m6's AGENT part)

`agent_m6.zig` and `agent_json_m6.zig`: a scripted agent drives the spec's five steps, and the
state commands around them, with `--output json`, `zbx schema <command>` and `zbx explain
--output json` only. It runs in its own project (`za`), on its own volumes (`agentdb`,
`agentold`, `agentlk`) and its own port (5433). Every decision is made on a member of a JSON
document, and every document is checked against the schema `zbx schema` printed, none of which

#### Findings

What the agent could not learn from JSON. Each is printed as a `FINDING` line by the run and
none is worked around:

1. **No document says when a container is ready.** `run -d` returns when the container has
   started; the agent polls the published port (`pg_isready` and `psql`, guest tools) before it
   writes. A health or ready state in `ps` would close it; it is not in M6's brief.
2. **`ps` and `run -d` do not say which volumes a container mounts.** The only place that
   connects a container to a volume is `state ls` (`used_by`), from the volume's side. The agent
   asks the volume, not the container. A `state` member (names, targets, read-only) in `ps` would
   be additive.
3. **`ZBX-E0710`'s only fix is a sentence** ("copy its files out by hand first"), `command` null:
   an agent can report an expired trash and cannot act on it.

Not findings, found on the way: `ZBX-E0706`'s context carries the holder (`holder`) and the fix
is the command that stops it; a refusal's exit status differs between `run` (125) and the state
commands (1), which the agent reads from the process status as for every other command;
`state export` without `-o` writes the archive to stdout, so there is no JSON result then (the
schema says so); the harness waits for `stopped` with a shell loop on `ps --all`, which is the
harness waiting and not a decision of the agent's. The first run of the part failed in the harness
(it required a command in every fix, which E0710 lacks); the second run is the finding above.

### Cuts and known limits of this part

- The agent never drives a restore over a name made again (`E0708`), a missing volume for
  `export` (`E0707`) or a terminal (`E0714`); the goldens and slice 2's and 3's VM parts do.
- The expired trash is made by renaming the entry on the host, not by waiting a week.
- A disk full during a run or an export is not made in the VM (a full guest disk would break the
  rest of the demo) and has no `ENOSPC` test of its own in the simulator for the state code: the
  claims in the failure table below come from reading the code (`state_commands.zig`: a write
  failure unlinks the part file and is `E0715`). That is a gap.
- The agent's readiness wait and its wait for `stopped` are shell loops (finding 1).

### Failure modes

| What | How it shows | Recovery |
| --- | --- | --- |
| A volume in use | `run`: `E0706`, exit 125; `state rm`, `export`: `E0706`, exit 1. The context has `volume` and `holder`; the first fix is `zbx stop <holder>` | stop the holder, or mount the volume `:ro` |
| A disk full during a run | the container's own write fails with `ENOSPC` inside it (the volume is a plain directory); a failure of zbx's own record or lock write is the run's error naming the path. Not tested (see the cuts) | free space, run again; the volume keeps what was written |
| A disk full during an export | `E0715` (the archive could not be written); the archive is written as `FILE.zbx-part`, removed on a failed write and renamed when whole, so no half archive is left. Not tested with a full disk | free space; export again |
| A restore after the trash expired | `E0710`, exit 1, `context.trash` the entry; `state ls` shows `expired: true`; no command fix | the files are still on disk under `state/.trash/<name>@<seconds>` until the next `state rm` empties them: copy them out by hand |
| A restore with no trash, or over a new volume | `E0709`; `E0708` naming both | `zbx state ls`; `state rm` the new one first |
| Postgres killed mid-write | the lock is free at once (kernel closes it); the same command starts postgres, which replays its WAL; the row written before the kill is there (SPEC 3 and AGENT 3 in the VM) | none needed |
| A secret path that does not exist | `E0210` (the source does not exist), exit 125, nothing created; the same for `--bind` (MOUNTS 3 in the VM) | fix the path |
| Anything else | each `07xx` code, `zbx explain <code>` | see "Failure modes" in slices 2 and 3 |

Postgres killed mid-write was not made worse on purpose: the demo kills it right after an insert
(SPEC 3), which is the case the spec names. A kill during heavy writes is the database's own
recovery, and this is not tested beyond that.
