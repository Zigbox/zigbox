## Slice 1: the probe

[run 43626834366](https://github.com/Zigbox/zigbox/actions/runs/43626834366), commit 4956039.
After the slice's review fixes it passed again in 39 s: [run 43636460487](https://github.com/Zigbox/zigbox/actions/runs/43636460487),
commit 94fd4f0. The table gives the second run's figures.
It runs on a `vm/s2-*` branch only, and no CI demo runs it. Findings are in
[2026-11-14-s2-probe-findings.md](../decisions/2026-11-14-s2-probe-findings.md).

| Fact | Ubuntu 24.04 guest, as `demo` (uid 1000) |

| Kernel | 6.8.0-147-generic; it offers FUSE 7.39 and `max_readahead` 131072 |
| `/dev/fuse` | `666 root:root` |
| `apparmor_restrict_unprivileged_userns` | 0, set by the harness's provisioning (Ubuntu ships 1, which was not tested) |

| Overlay | `userxattr`, with the FUSE mount as its lower layer |
| First 1 MiB `read(2)` through the overlay | 2171 us uncached (mean 1851 us over 16 MiB); 948 us cached (mean 458 us) |
| READ size the server sees | buffered `read(2)`: 128 KiB (128 requests for 16 MiB); `O_DIRECT`: 1 MiB. Not a rule: the size is the reader's (see the findings) |
| Reads as uid 0 and as uid 1000 | ok, through the overlay; uid 1000 also directly on the FUSE mount |
| Copy-up | ok: the appended file is in the upper, the lower is unchanged, and the lower gives `EROFS` |
| `EIO` reply | `cat: ...: Input/output error` |
| Server killed (`kill -9`) | `cat` through the overlay, and `ls` on the FUSE mount: `Transport endpoint is not connected` |
| After the kill, cached `big.bin` | a new open: `Transport endpoint is not connected`; a descriptor opened before: 16 MiB read from the cache, then its close fails the same way |

The latency figures are for a server that answers from memory, so they measure the kernel path and
not a registry. The first run's figures (2685 us uncached, mean 2039 us; 1069 us cached, mean
538 us) included the server writing one log line to stderr per READ inside the timed reads; the
review fixes keep that log in memory and write it on STATFS, outside the timed reads, and the
second run's figures above are without it.

After the server's death the page cache does not help: a new open of a fully cached file fails
with `ENOTCONN`, so slice 4 must not assume cached files stay readable (findings, point 3).

## Slice 4 (the lazy FUSE server)

The VM check is `zig build demo-s2-lazy` (`src/testing/vm/main_s2_lazy.zig`). Slice 6's `demo-s2`
replaces it.

### Scope cuts

- **`zbx run --lazy -d` is refused with E1208.** A detached run would need the server to outlive
  the `zbx` process that started it, which slice 4 does not build. The refusal says "not yet
  supported", and the VM check asserts the code and the exit status 125.
- **Passing a descriptor of the mount out of the container is not scripted.** See
  `docs/decisions/2026-11-14-s2-lazy-teardown.md` for what an outside holder sees. The VM check
  covers the two exits that are scripted: the container killed in the middle of a read (`zbx`
  returns) and `zbx` killed with SIGKILL (nothing is left in `/proc/mounts` or in fusectl). The
  unit test of `Server` over a socket pair covers the stop flag, which bounds teardown no matter
  who holds the mount.

### What the eager-vs-lazy comparison leaves out, and why

The guest lists every entry of `/` (`find / -xdev`, without the mount points) in an eager run and
in a lazy run of the same image, and requires the two listings to be identical. For each entry
the listing has the type and mode, uid, gid, and for a file its size and checksum, for a link its
target, and for a directory its link count. It leaves out:

- **A file's link count.** An eager tree is made of hard links into the store, so a file's
  `st_nlink` there counts the store's links too. The lazy run checks the count on its own instead:
  the image's hard-link pair (`/big`, `/big.link`) shares one inode and counts 2.
- **A directory's size.** It is whatever the file system reports (4096 on ext4, something else
  over FUSE). It carries none of the image's data.
- **Times.** A store tree keeps none: both the server and the materialized tree report one fixed
  time (`store_mtime_seconds`), so the listing gains nothing from them.

**Device nodes, FIFOs, sockets and whiteouts cannot occur in a store tree.** A tree entry is a
file, a directory or a symlink (`store/tree.zig`, `Kind`). Import refuses or leaves out devices,
FIFOs and sockets, and it turns a whiteout into the removal it stands for (`store/import.zig`). So
the server never has one to serve, and the listing needs no case for them.

### Image additions

Before the import, the guest adds the following to the Alpine minirootfs:

- `/big`: 3 MiB of random data, so reads cross the 1 MiB store chunks. The guest reads 3000
  bytes at offset 1048000, which straddles the first boundary, and then the whole file.
- `/big.link`: a hard link to `/big`.
- `/cold`: a 64 KiB file with the user xattr `user.zbx.demo=lazy`. The guest checks the value,
  checks that the file lists exactly that one name, and checks that no `overlay` xattr shows on
  `/`.
- `/s2-list.sh`: the listing script.

### The server against the guest's kernel

`demo-s2-lazy` also runs the FUSE kernel test (`src/fuse/kernel_tests.zig`) in the guest, as
`demo`: the harness embeds it as an x86_64 test binary (`src/fuse_kernel_test_root.zig`, built
by `build.zig`) and serves it, and the step requires the runner to print `OK` for it, not `SKIP`.
The test mounts `/dev/fuse` in its own user and mount namespace, serves the mount from its own
threads, and checks, through the kernel: reads (buffered at an odd offset, a 1 MiB direct read
across chunks, a sequential read, a symlink), `ENOENT`, `statx` (type, mode, size, link count,
owner), the root's listing (exactly `.`, `..`, `a`, `b`, `c`, `l`), `getxattr` and `listxattr`
(the user xattr shows, the `user.overlay.*` one does not), and `EIO` from a file whose chunk
cannot be read.

### The serving fuzzer

`zig build fuzz -- fuse_serve` (`src/fuzz_fuse_serve.zig`) drives `Serving` over a fake device
with every serving thread and the shared chunk cache: `INIT`, then reads (across chunk
boundaries, past the end, of a file whose chunk fails), `GETATTR` and `READDIRPLUS`, each reply
checked against the fixture. A quarter of the seeds use the real bounds (the 1 MiB store chunk,
a first file between 1 MiB and 2.8 MiB); the rest use chunks of 8, 64 or 4096 bytes. Whether two
threads read the same chunk at once depends on the scheduler, so the fuzzer counts it but its
test does not require it.

## Slice 5 (run integration), split into 5a and 5b

The brief's slice 5 did not fit one implementer's context, so the supervisor split it
(2026-11-15):

- **5a:** the resolver behind the FUSE server (a catalog from the node table and a verified
  index, every chunk through `Resolver.read`), the resolver's events rendered as coded lines
  capped at `lazy_errors_shown_max` plus a summary, the registry Range client, `zbx run --lazy
  <registry ref>` fetching and verifying the index (trees stored with `put_checked`) when the
  image is not local, the `W1201` fallback to a whole pull, and the progress and summary lines.
- **5b:** image record v4 `partial`, run record `lazy`, `ps`/`inspect` JSON, `gc` and `verify` of
  partial images, holders, the `zbx doctor` line, `StartOptions.lazy_sources` and its surface
  test.

Background fill stays off (`fill = false`) and `-d` stays refused with E1208 through both.

The first 5a implementer stopped at its context ceiling with the resolver wired into the server
(not yet reachable from the CLI) and E1201 and E1202 registered; see
`docs/decisions/2026-11-15-s2-resolver-wiring.md` for what is left.

### 5a: what a remote lazy run does, and the cuts

`zbx run --lazy <registry ref>` in the foreground, when the store has no record of the image,
fetches and verifies the lazy index (`lazy_start.zig`), attaches it and the registry to the FUSE
server (`cli.attach_remote`), prints the progress line when the resolver starts, logs the
resolver's events, and prints the summary line after the run. An image the store has runs as in
slice 4, from the store's own objects.

- **The composed run reads the image from memory.** `run_image.compose` works on the `Image`
  that `lazy_start.start` filled in memory (manifest, config, tree, settings); no image record is
  read or needed, so nothing was cut there.
- **A named `User` of a remote image is cut.** `choose_user` reads `/etc/passwd` and `/etc/group`
  from the store's objects, and before the run those of a remote image are not local (the server
  that would fetch them starts with the container). A numeric `User` (or `--user 1000:1000`)
  works; a name gives `E0521`, as for an image whose files lack it. Fetching the two files
  through the resolver before the start is left for 5b or later. The fixture image of `demo-s2`
  sets no `User`.
- **Registry fetches are serialized.** One registry client holds one token and one wire state,
  so `lazy/registry_range.zig` lets one fetch at a time use it; a fetch waits its turn within its
  `timeout_ms`. `lazy_fetches_max` concurrent requests to the registry come later (one client
  per slot).
- **No `zbx.lock` and no image record** are written by a remote lazy run (records of partial
  images are 5b). A second `--lazy` run of the same tag resolves it again.
- **W1202, E1203 and E1206 name the object's id and the chunk, not the file's path**: the
  resolver's catalog has no paths (objects are shared by hard links and by equal files). The
  brief asks for the file; mapping an object back to a path through the node table is left
  for later.
- **The progress line is printed once**, when the resolver starts, on a terminal too; the brief's
  line that rewrites in place while starting has nothing to rewrite before the container runs.
- **The summary's per-source bytes** count chunk bytes the registry sent (compressed), not the
  index, the manifest or the config: `demo-s2` step 2 must add the index (the progress line's
  size, also exact in `Workspace.index_fetched`) and the manifest and config to compare with the
  registry's counter.
- **A remote lazy run is not yet in a VM demo.** The pull fixture serves no layer-writer-2 image
  and the push fixture serves no pulls; the disk-backed registry of slice 6 (`demo-s2`) is where
  a remote lazy start is first run live. The fixture already answers closed ranges
  (`bytes=a-b`, 206 even from offset 0). `demo-s2-lazy` (slice 4's check, the store as the only
  source) was run on the 5a commit to show the CLI changes keep it green.

### 5b: records, reports and the library interface, and the cuts

- **A remote lazy run writes the image's record**, version 4 with `partial = true`, before the
  container starts: tags carried over plus the tag the run used, platform, config, tree, layers,
  settings. It roots the tree for gc and shows in `zbx store ls` as `partial N%` (JSON:
  `"partial":true,"local_percent":N`). No root record under `roots/` is written, so `zbx store
  verify` never walks a partial tree; it counts partial images in one line of its own
  (`partial_images` in JSON). Whole images stay version 3, which older releases read.
- **A second `--lazy` run of a partial image starts lazily again**, by digest. **A run without
  `--lazy`** of a partial image pulls it whole first (quietly, by digest), as for an absent image.
- **`zbx images` is `zbx store ls`.** The brief's `zbx images` is the image table of
  `zbx store ls`; there is no separate command.
- **There is no `zbx inspect` of a run.** `zbx inspect` reads build results only, so the run's
  `lazy: {local_percent, fetched_bytes, errors}` is in `zbx ps --output json` only. The text table
  of `ps` is unchanged.
- **The run record's `.lazy` keeps a count of sources, not their names** (version 11, written
  only for lazy runs; listen/devices runs stay version 10 and others 9).
- **gc roots a partial tree as any tree.** An image record roots its tree; the walk does not need
  file objects to exist, so a partial tree's present objects are kept and missing ones are not
  counted. A running lazy container is a live tree from its run record, as any run is. The
  chunks of an object fetched in part (`partial/<id>/`) stay while a root holds the object; once
  none does, gc counts them with the cut downloads and an apply removes them, after the same age
  as a cut download. They are a cache: removed, never trashed, and `zbx store restore` does not
  bring them back. When the same gc trashes a partial image's record, a restore puts the record
  back and a lazy run of it fetches the missing chunks again.
- **The lazy index is fetched within `net_request_timeout_ms` (120 s) in all**, its tokens and
  401 retries included, each request within `lazy_read_deadline_ms` of what is left: an index
  at the 64 MiB maximum needs a registry that serves about 0.5 MB/s. Past it, E0503 says the
  request ran past its 120 seconds limit, while fetching the lazy index.
- **`zbx doctor` gains a `fuse` line**: the probe opens `/dev/fuse` and mounts FUSE from a
  scratch user and mount namespace, and says which of the two failed. Only `--lazy` needs it, so
  the line only warns (W1203, as the net line's W0102) and the exit status is unchanged;
  `zbx run --lazy` itself refuses with E1201 (docs/decisions/2026-11-15-doctor-fuse-warns.md).
- **`StartOptions.lazy_sources`** goes to the server through `run.Lazy.peers` before `prepare`,
  and the resolver asks them after the store and before the registry. A library caller still
  builds the FUSE server itself (`fuse/lazy_server.zig` is not exported from `zigbox`); exporting
  a ready-made server is left for Zigcube's C2.

## Slice 6

### Product changes

- **The 0.5.2 dormancy is undone.** Push and export write layer writer 2 with its lazy index
  again, the `lazy_start` build option and the E0004 refusal of `--lazy` are gone, and
  `demo-s2-lazy` builds without an option. `--lazy` stays opt-in.
- **`zbx run -d --lazy` works.** The supervisor attaches the registry, starts the FUSE server,
  its threads and the range client's I/O after the fork, and tears them down (and wipes the
  registry token) after the container ends. The resolver's lines (W1202, E1203, E1206) and the
  summary go to the run's log as stderr lines, so `zbx logs` shows them; the progress line, and
  any line before the start is reported, also reaches the caller's stderr as a warning frame.
  `zbx exec` reads through the same mount, and `zbx stop` ends the container, after which the
  supervisor joins the server. `--lazy --rootfs` stays E1208, whose cause and explanation no
  longer mention `-d`.
- **Background fill is on** for remote lazy runs, foreground and detached, after 2 s with no
  read and in ranges of at most 2 MiB (docs/decisions/2026-11-18-s2-fill-idle.md). The run
  record is written again each second while what was fetched changes, so `zbx ps --output json`
  shows `lazy.local_percent` rising to 100; the image's record is rewritten whole once every
  object is local. `zbx store gc` during the fill needed no change.
- **E1203 is retitled** "a chunk could not be fetched: the read got EIO" (it said "in time",
  which was wrong when every source sent wrong bytes); E1203 is new in S2 and unreleased.
- **Cut: W1202 and E1203 still name the object, not the file's path.** Naming the path needs a
  reverse walk of the node table from the object, for each event, on a resolver thread; it was
  left out of this slice.

### demo-s2

`zig build demo-s2` (`src/testing/vm/main_s2.zig`) runs the brief's nine steps in the M0 VM as
the ordinary user `demo`, against a registry on the runner.

- **The registry** (`registry_disk_s2.zig`, HTTP in `http_s2.zig`) keeps blobs on the runner's
  disk, answers a closed `Range` with 206, and throttles every response body through one global
  40 MiB/s bucket. It counts the bytes it serves (`served`, and `chunks`, which is every range
  request except the two images' registered index ranges) and has two faults the guest drives
  through `/control/...`: `flip-on`/`flip-off` (one byte flipped in the middle of the chosen
  chunk's compressed range) and `down`/`up` (every request refused while down).
- **The fixture** (`fixture_s2.zig`, written in the guest by `tool_s2.zig gen`) is deterministic:
  Alpine's rootfs plus `/app/start`, `/app/config`, `/data/*.bin` and `/models/weights.bin`, 3 GiB
  in all; `-v2` changes `/app/start`'s output and nothing else that step 5 reads. The runner
  computes every hash the steps compare against from the same generator, and finds chunk 3 of
  `/data/c.bin` in the pushed index (`index_s2.zig`) to arm the flip.
- **The guest reaches the registry through a loopback relay** (`tool_s2.zig forward`, on
  `localhost:5000`), because zbx speaks plain HTTP only to a loopback registry.
- Each step is one guest command (`sh /tmp/s2.sh <step>`), which prints one `ok` or `FAIL (...)`
  line per check and one `s2: recorded <key> <value>` line per number. The harness checks every
  number's bound again (`checks_s2.zig`) and prints them all as `demo-s2: RECORDED` lines. A step
  that fails does not stop the later ones.

The checks, per step:

1. `zbx doctor`'s line "FUSE mounts inside a user namespace" says ok.
2. `zbx run --lazy lazy:3g -- /app/start` prints the expected `ready <hash>` line in under 10 s
   (`lazy_ms`), with under 64 MiB served by then (`lazy_bytes_at_ready`), and exits 0; the sum of
   the summary line's `sent N bytes` equals the registry's `chunks` (`lazy_sent_bytes`,
   `registry_chunk_bytes`).
3. `zbx pull lazy:3g` exits 0 and takes over 75 s (`pull_ms`); step 2's time is under a quarter of
   it.
4. `zbx run -d --lazy`: `ps --output json` shows `local_percent` below 100; `store gc --output
   json` plans no objects and no partials; `local_percent` reaches 100 within 300 s (`fill_ms`);
   after `stop`, `store verify` exits 0; a run without `--lazy` has no `fuse` line in its
   mountinfo.
5. In step 3's store (which holds `lazy:3g` whole), `run --lazy lazy:3g-v2` prints v2's ready line
   with under 20 MiB from the registry (`source_bytes`).
6. With the flip on, `sha256sum /data/c.bin` fails with EIO; W1202 comes before E1203, names the
   object and "chunk N's hash"; no partial chunk is left in the store; with the flip off, a second
   run prints the expected hash.
7. With a detached lazy run up, the registry goes down: `/app/config` (already read) still reads;
   `sha256sum /data/e.bin` fails with EIO in under 35 s (`cut_first_ms`) and `zbx logs` shows
   E1203; a second missing read fails in under 7 s (`cut_second_ms`); `exec true` still works.
   Once up, the hash comes back right in under 10 s (`cut_recover_ms`).
8. `run --lazy alpine:3.20` (no index) prints W1201 and runs; `run --lazy --rootfs` exits 125
   with E1208; a second user who cannot open `/dev/fuse` gets E1201.
9. In one store: the release before S2 (`old_release.zon`, `s2_tag`) runs `-d`; this `zbx`
   lists and stops it. This `zbx`'s detached lazy run writes a version 11 record, which the old
   release does not know: its `zbx ps --all` leaves it out without a word, and its `zbx stop`
   refuses it with E0402 ("from a newer zbx"). The brief asked for the old `zbx ps` to refuse it;
   v0.5.1's `ps` skips newer records silently and warns W0203 only when a run prunes more than 32
   records, so the refusal checked is the old `stop`'s.

### Cuts and deviations

- **The fixture is generated in the guest**, not on the runner, and pushed with the guest's own
  `zbx push`: copying 6 GiB into the guest through the harness's HTTP server would take longer
  than generating it, and the push is itself under test. The runner still holds the registry and
  computes every expected hash on its own (docs/decisions/2026-11-18-s2-demo-fixture-in-guest.md).
- **The throttle covers response bodies only**, uploads included; heads and the control routes
  are not counted against it.
- **EIO's text:** Alpine's `sha256sum` is busybox on musl and prints `I/O error`; the script
  accepts that and glibc's `Input/output error`.
- **W1202 names the object and the chunk's ordinal**, not the file: the warning's context has
  the object and the source, so the check looks for the object's hash and "chunk N's hash".
- **E1201 for a second user** is made by moving `/dev/fuse` to group `demo` with mode 660 for that
  one command and back, rather than removing the module, which would break `demo`'s own steps.
- **Step 5 reuses step 3's store** instead of pulling again.

### Known risks

- Step 2's 64 MiB bound shares the 40 MiB/s link with the background fill, which starts at once;
  the bound holds only if the fill yields to demand reads.
- Step 7 races the fill: if the fill reaches `/data/e.bin` before the registry goes down, the
  read succeeds from the store and the step fails. The registry goes down a second or two after
  the start, when the fill has had at most about 80 MiB of the 40 MiB/s link; the order in which
  the fill takes files is zbx's, not the fixture's, and was not checked against a live run.
- The summary-against-counter check assumes zbx reads the index with exactly the range the
  manifest's annotation names; any other range is counted as chunks.
- The runner needs about 6 GiB for the registry and the guest's overlay grows to about 15 GiB;
  both jobs free disk first.
