# M7 demo: the build

This document grows slice by slice. Until the `demo-m7` job is green in CI, M7 is built, not
demonstrated.

## Slice 2: keys, one step, the cache

`zbx build` builds the steps of `zbx.build.zon` one at a time, in graph order, each from its
base in `zbx.lock`; a row per step says `hit` or `built`. `src/testing/vm/main_m7.zig` builds
the `compile` step twice (miss, then hit).

### Known limits (accepted)

- **No cache pruning.** Entries in `build/cache` stay until a later slice prunes them.
- **`store verify` and `store usage` do not know the cache**: they neither check nor count its
  entries.
- **/out size is unbounded until import's limits (E0415).** A step may write as much as the disk
  holds; the import then refuses what is over the store's file, path or depth limits.
- (Ended in slice 3b-ii.) A base that `zbx.lock` names but the store lacks was refused (E0804);
  it is now pulled by the locked digest.
- A SIGKILLed `zbx` leaves its work directory and run record until the next build's sweep and
  the run layer's reconciliation; the sim tests plant such leftovers, the real kill is the VM
  demo's.
- Farm directories made before slice 2 keep old mtimes: see DECISIONS, "Farm format marker".

## Slice 3b-i (review fixes)

Done: the scheduler review's nits. A worker's pipe bytes now start with a tag byte (output or
failure), so a diagnostic can never pass for an answer or be dropped for its length; the unused
file count is gone from the answer; a failed row is told before a step failure (`zbx build |
head -1` is unchanged: see below); the row buffer is derived from the row's parts; the unused pull and import workspaces
are no longer passed to `zbx build`. The fixed parallel bound (4, not the online CPUs) is the
cut listed under "Slice 3 (partial)".

Known limit (accepted, N8): an imported step output is not rooted before the parent records its
cache entry, so a `store gc` between the worker's import and the entry could collect it.
`cache.lookup` reads a missing tree as a miss (`tree_incomplete`), so the next build rebuilds
the step; the real exposure is a dependent step in the same build, which would mount the
collected tree.

## Slice 3b-ii: the result

Built: image assembly (`build/assemble.zig`: canonical, wrap, merge, with an explicit frame stack
and the bounds in `constants.zig`) and its cache; `image.config` resolved from the base's
settings (`build/result.zig`); `E0807` for a clash between the base and an add, a path or tree
past the bounds, and a config field that does not fit; the build record and the result digest;
`zbx run <result digest>` and `zbx inspect <result digest>`; `--output json` for `zbx build` with
`zbx schema build` and `zbx schema inspect`; pull of a locked base by digest; the N8 root. The
text report is now `  compile   miss   0.42 s` (hit or miss, time), then the image row, then
`built b3:<digest>  (H hits, M misses, S.d s)`.

### Cuts and deviations

- The image cache entry holds a tree under an image key, not the result digest (DECISIONS).
- E0807's conflict line names the path, the kinds and both sources: the base, or the earlier
  `.image.add` (its `from` and `to`), and the add that clashes. The fix text says which.
- **Cut: the `build` root.** The brief asks for a root labelled with the build file path for the
  result. It is not added: the image tree is kept by the image cache entry (DECISIONS #17), which
  gc follows. The consequence: if that entry is removed by hand, `store gc` can collect the
  result's tree, and `zbx run <digest>` then fails with the missing-tree diagnostic. A build
  rebuilds it. The same holds for a cache that gc refuses to follow (past 8192 entries).
- A locked base's pull prints one line, `pulling <ref>@<digest>`, on stdout, or on stderr under
  `--output json`. A registry that returns another manifest than the lock names is E0804 with
  both digests, not an assertion.
- A damaged result record is E0422 and one written by a newer zbx is E0423 with "upgrade zbx".
- `zbx run <result digest>` does not take `--user`; `zbx inspect` takes the full digest only.
- The pasta VM check stays cut (see "Slice 3b split").

### Known limits (accepted)

- N8: the step worker never overwrites a root that already exists for the tree (a user's root
  survives), and the parent removes only a `build:` root written at or after the build began. A
  crash between the cache entry and the removal leaves the root until it is removed by hand.
- The pull of a locked base by digest is covered twice: a compose simulation test with a fake
  registry (a pull, and a lock holding an index digest), and `RESULT7` in the VM, which removes
  the base from the store first and asserts one `pulling <registry>/library/alpine@sha256:` line.
- The conflict check reads trees through the store, one directory at a time; a merge of more than
  `build_merge_common_max` (256) directories in common is E0807.
- Result records are not checked or counted by `store verify` and `store usage`, as for the cache.

### Tests and the VM part

`fuzz_result.zig` (`zig build fuzz -- result`, in the CI matrix): a random record round-trips
through `encode` and `parse` to the same bytes and digest, and damaged bytes (flips, a cut,
a garbage tail) never crash `parse` and are accepted only if they re-encode to themselves.

The VM part `RESULT7` (`spec_m7_result.zig`) builds a project of two sleeping steps and an
image with a config, so the full alpine-only project stands in for the Go project of the brief
(the Go project, the golden digest and the second VM are slice 4). It checks: all three rows
`miss` in `--output json`, the `compile` and `notice` intervals overlapping, `zbx run <digest>`
printing `hello from zigbox`, `zbx inspect --output json`, and a second build with
`(3 hits, 0 misses`; before the build it drops the pulled base (`store rm`) and asserts the
build pulls it by digest. Its assertions are one pure function with unit tests. The old BUILD7 part
now reads the digest from the footer line.

## Slice 3b-iii: network, streaming, library

Built: `network = true` shows as `net` at the end of the step's text row, and `W0801` ("the build has steps that use the network", naming them) is printed once on stderr before the first step; `--verbose` streams each step's output to stderr behind `<step> | `, whole lines only (decision `2026-11-03-m7-slice-3b-iii-streaming`); `zigbox.build` is exported from the library (file, graph, key, step, schedule). Tests: the scheduler recovers from a step whose worker dies (`schedule_tests.zig`: nothing new starts, none outlives the build, a rebuild treats what finished as hits); and the crash proof proper, `compose_tests.zig`, "a step that dies at any write point": a step (import of `/out`, its root, the cache entry) runs on the simulated store, the machine dies at each of its write points in turn (before and inside the import, between the root and the entry, inside the entry), the process starts again on what the disk kept, the step runs again, and the entry must name the clean build's tree with `store verify` finding no damage. `build_library_tests.zig` runs `build.step.run_step` as a second caller, on two threads each with its own simulated store.

### Cuts and deviations

- **Cut: the pasta VM check** (owner, 2026-11-03). `demo-m5` checks pasta and `demo-m7` step 6 runs `wget` through it.
- Streaming is stderr-only, and a step's stdout and stderr are not told apart in it.
- The second-caller test uses the simulated host and store through `zigbox.zig`'s exports (`host_sim`, `store.fs_sim`, `store.import`), and the test-only fixtures `runtime/sim_run.zig` and `store/test_support.zig`, as `pull_library_tests.zig` does; the fixtures are not part of the library.

### Known limits (accepted)

- W0801 is not shown when the build has no steps with `network = true`, and a step that reaches the network without the flag fails (E0805, step 6 of the demo).
- Streamed lines are not coloured, and a terminal that is not wide wraps them.

## Slice 4: the VM demo, CI and the agent test

`zig build demo-m7` runs two VMs. The first starts from a store the 0.2.0 binary (`m7_commit` in `old_release.zon`) seeded, and runs, in order: UPGRADE (`upgrade_m7.zig`), the M6b SPEC part, HELLO steps 1 to 4 (`hello_m7.zig`), ACCEPT (`accept_m7.zig`), AGENT (`agent_m7.zig`), and last BUILD and RESULT (slices 2 and 3), which `store rm` the base. The second is a clean VM: HELLO steps 5 and 6. Every assertion is a pure function in `checks_m7.zig` with unit tests; the parts only run commands and call them. The project is `src/testing/vm/m7_project/` (embedded, written into the guest with `put_file`); the golden digest is `src/testing/vm/m7_expected.zon`, copied from a recorded green run and never written by hand.

### By hand

1. `cd` into a directory with `zbx.build.zon`, `zbx.lock`, `go.mod`, `main.go`, `VERSION`, `LICENSE`, `README.md` (copy `src/testing/vm/m7_project/`). `zbx build --output json`: three `miss` rows, `compile` and `notice` overlapping; `zbx run <digest>` prints `hello from zigbox`; `zbx inspect <digest> --output json`.
2. `zbx build` again: three hits, the same digest, under a second, footer `(3 hits, 0 misses`.
3. Append a line to `README.md` and build: three hits, same digest (README is no step's input).
4. Change the greeting in `main.go` to `hello again from zigbox`: `compile` miss, `notice` hit, `image` miss, `(1 hit, 2 misses`, a new digest that prints the new greeting. Restore: the first digest, three hits.
5. In a clean VM (or with `ZBX_*` pointed at an empty store): the same build gives the golden digest.
6. Add a `fetch` step (base `alpine:3.20`, `wget -q -O /out/page https://example.com`, no `.network`): exit 1, `error[ZBX-E0805]: build step "fetch" failed: exit`, `the step has no network`, `add .network = true to step "fetch" in zbx.build.zon`; the other steps report hit.

### Cuts and deviations

- **Cut: the blob-cache disk.** The golang image is about 70 MB and is pulled twice (two VMs) through `mirror.gcr.io`. No cached disk is attached; CI time is the cost.
- **Cut: the pasta check** stays cut (slice 3b-iii). Step 6 relies on the step having no network, not on pasta.
- Step 6 runs in the second VM, after step 5, so the other steps are hits there. In the first VM the same refusal is covered by AGENT (E0805 as JSON).
- The `0:0` ownership inside the built tree is asserted by BUILD7 (`tree_owner`). ACCEPT asserts the other half: every file the builds put in the store is the user's (uid 1000). `find ! -uid 1000` finds nothing because the golang and alpine images' files are root-owned (0:0 in the store's namespace, uid 1000 on the host); an image with files of another owner would show up there.
- The lock's `tree` values are informational (the build does not compare them with the pulled tree); they were taken from the recorded run.
- `hello_m7.zig` is the brief's HELLO; `spec_m7.zig` (BUILD7) is slice 2's check, kept.
- The AGENT FINDINGs: the fix of E0805 that names `.network = true` is a sentence with `command: null`, so the agent infers the edit.

### Failure modes

- **Base not locked**: E0804, fix `zbx pull busybox:1.36`, as the user spelled the base (ACCEPT asserts it).
- **Cycle**: E0802 names it (`a -> b -> a`); **outside input**: E0803 names the path (ACCEPT).
- **Step out of memory / step timeout**: the step fails as E0805 with the cgroup's or timer's cause in the message; nothing is cached for it. Not run in the VM demo (the cloud container has no cgroup v2); covered by the unit tests of the step runner.
- **Disk full during output import**: the import fails as ZBX-E0416 (no space; any other write failure is E0417, `store/diagnose.zig` `write_failed`), and no cache entry is written. The objects already written are whole and kept until `store gc`. Covered by `compose_tests.zig`, "a full disk during a step's output import is E0416, with no cache entry written" (a simulated disk of a few bytes); not in the VM. The crash-at-every-write-point test in the same file is a different claim (a crash leaves the store valid).
- **A network step's output changing**: the step is a miss only when its key changes; a rerun is not forced. A `net` step is cached under its key, and W0801 says its output depends on what the network returns, not only on the inputs.
- **A crash mid-build**: `build/work/` keeps the step's work directory; the next `zbx build` removes every leftover work directory before it starts, then runs. The ACCEPT part asserts none is left after the builds above; BUILD7 kills a build mid-step and asserts the sweep.
