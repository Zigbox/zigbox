# M8 demo: trust

This document grows slice by slice. Until the `demo-m8` job is green in CI, M8 is built, not
demonstrated. There is no `demo-m8` yet: it comes with slice 2.

## Slice 1: keys, with passphrase encryption

`zbx key new <name>`, `key list` and `key show <name>` make and describe Ed25519 signing keys
in `$XDG_CONFIG_HOME/zbx/keys` (default `~/.config/zbx/keys`, mode 0700; a key file is 0600).
A new key's secret is sealed under a passphrase with argon2id and XChaCha20-Poly1305, or kept in
the clear with `--no-passphrase`. `list` and `show` read only the `.pub` files and never need a
passphrase. What ran so far: unit and simulation tests (`zig build test`), the `key` fuzzer, and a
smoke run of the real binary on a Linux host that is not the test VM. The VM has not run it.

### argon2id measurement

`zbx key new` with a passphrase file, t=3, m=64 MiB, p=1, a `ReleaseSafe` build, five runs in
the Claude Code cloud container (4 vCPUs, Xeon at 2.3 GHz; not the test VM):
107, 108, 105, 121 and 121 ms. The whole command, not only the hash. The defaults stay at the
brief's. The VM measurement is **not yet run**; it is recorded here by the demo in slice 2.

### Known limits (accepted)

- **A forgotten passphrase is a lost key.** There is no recovery and no reset.
- **The `.pub` file's second line (the encryption word) is advisory.** `list` and `show` believe
  it; `.key` is the truth, and a later slice that opens the key reads the `.key` file.
- **argon2id's memory is taken from the OS** (`page_allocator`) for one call, because the
  command line has no allocator. The only allocation of the program, bounded by the parameter
  limits that `parse` enforces (at most 128 MiB).
- **No key deletion, rotation or export** yet: slice 1 only makes and shows keys.

## Slice 2: `zbx sign`

`zbx sign <operand> [--key <name>] [--passphrase-file <path>]` signs a tree and adds the
signature to the tree's record, `trust/signatures/<tree hex>` in the store (JSON Lines, one DSSE
envelope per line, at most eight lines). The operand is a build result or tree digest
(`b3:<hex>`) or an image `name@sha256:<manifest>`. It first checks the tree is whole and every
object hashes to its id (`E0910` if not; a missing file object says it is missing), then opens
the key (`E0911` without a passphrase; the key is opened first, and the tree is checked again under
the store lock, which avoids a check-then-sign race) and signs a `sign/v1` statement. `--key` defaults to the only key; with several it is required
(`E0006`). Signing the same subjects with the same key again changes nothing, whatever the time: the
comparison ignores `signedAt`, the old line is kept and `zbx sign` exits 0 and says it was already
signed (`docs/decisions/2026-11-08-sign-idempotence.md`). A manifest subject's name is the
canonical, tagless `registry/repository@sha256:<digest>`, so two spellings of one reference are
one line. A record that is full (eight lines for a tree, 4096 records in the store) is refused
with `E0910`; until `zbx trust prune` (slice 5) exists, the fix says to remove a record file. A record that is damaged or written by a newer release is refused with
`E0903` and never rewritten. `--output json` prints `zbx.sign/1`.

What ran: unit and simulation tests (record tests with crash simulation, `sign_commands_tests`),
and the `trust` fuzzer, which now also checks that `record.parse` accepts only what the writer
writes. The VM has not run it; `demo-m8` comes with a later part of slice 2.

### Cut: provenance statements move to slice 4

The brief has `sign` sign a build result's provenance record when there is one. No provenance
record is written yet (that is slice 4), so slice 2 always signs the `sign/v1` statement. When
slice 4 lands, `sign` on a result with a provenance record signs that record's exact bytes, and
`zbx inspect --provenance` shows it. Until then the first line of the brief's demo
("`inspect --provenance` shows its inputs and builder") is not reachable.

## Slice 6: packages

`zig build packages` writes the `zigbox` deb and rpm for x86_64 and aarch64 and the apt and dnf
trees around them; `zig build packages-check` reads the tree back. The owner signs in two rounds
([docs/releases/packaging.md](../releases/packaging.md)); `-Dtest-key` signs with a fixed test
key instead, for CI. The writers in `src/package/` know nothing about `zbx`; `src/package_release.zig`
(pure) and `src/package_main.zig` (I/O) do.

Checked in the build container (no VM): `dpkg-deb -I` of the deb; `apt-get update` against the
test-key tree with `signed-by=zigbox-test-key.gpg` (InRelease verified, candidate `zigbox 0.3.1`);
the whole two-round flow with a scratch gpg key (header signatures, InRelease, Release.gpg,
repomd signatures), `packages-check` passing on the signed tree and failing on one appended byte.
`rpm`, `createrepo_c` and `dnf` are not in the build container; the earlier slice-6 check (see the
handoff note) ran `rpm -K/-V`, install under `--root` and a `createrepo_c` comparison.

### Known limits (accepted)

- **`primary.xml` differs from `createrepo_c` in one attribute**, `<time file>`, which is a fixed
  epoch here so the output is reproducible. `filelists` and `other` are byte-equal.
- **No `PAYLOADDIGESTALT`** in the rpm header; the file digests are SHA-256 and the payload is
  covered by the header signature.
- **Fedora's rpm 6 needs the key imported** (`rpmkeys --import`) before it accepts a signature,
  the test key included.
- **`packages-check` does not verify OpenPGP signatures** of an owner-signed tree with the public
  key. It checks each round-2 signature file records the digest bits of the file it sits beside
  (so a swapped or stale file is refused, here and when the signing run places it) and that the
  four are by one key. With `-Dtest-key` it also recomputes them and compares bytes. The runbook's
  `gpg --verify` and `rpm -Kv` are the verification. The round-1 rpm header signatures are
  checked for form only.
- **No replay or freeze protection:** `Release` has a fixed `Date` and no `Valid-Until`.
- **The maintainer string** is a supervisor assumption (`docs/decisions/2026-11-08-package-bounds.md`).
- **VM check:** `.github/workflows/vm.yml` runs the demos m0 to m7 only; see the slice report for
  the status of the `vm/m8-slice6` run.

## Slice 7: the rpm and Debian guests

`zig build demo-m8-packages` installs the signed `zigbox` package on Ubuntu 24.04, Debian 12,
Fedora 45 and Rocky 9 in the test VM, with the Ed25519 test key and no unsigned fallback, then
runs `zbx --version` and `zbx doctor`. All four accepted the key on metadata and package: see
[the decision](../decisions/2026-11-08-archive-key-type.md). Run on CI:
https://github.com/Zigbox/zigbox/actions/runs/42504288000 (PASSED in 157 s).

Not part of this slice: the full demo-m8 (slice 8). `zbx doctor` exits 2 on Debian 12 (no systemd
user session for the `su` login) and Rocky 9 (kernel 5.14, cgroup `cpu` not delegated); the check
records this and does not fail on it.

## Slice 10: pack and export (lane U)

Built: `zbx store export --oci <source> <dir>` (an OCI image layout, `zbx.export/1` with
`--output json`), `zbx push --dry-run <source>` (packs and prints the manifest digest; the upload
is slice 11), the `zigbox.push` library surface, gc of pack records, the pack fuzzer, and a
`src/push/` rule in `.github/ci-changes.sh`.

Run: `zig build test`, `zig build tidy`, `zig build fuzz -- pack`, `zig build fuzz -- gc`,
`zig build check` (see the report). VM check `demo-m8` (`vm/m8-export` on CI): one tree imported
and exported as two users in the guest; layouts byte-identical, every blob hashes to its file
name, the layer reads back with the guest's `tar` and `gzip`. It is the slice's check, not the M8
demo.

Not run: no OCI tool (skopeo, crane, umoci) exists in the build container. `tar -tvzf` of the
golden layer was read here (GNU tar 1.35): the entries, modes, symlink and empty directory match
the golden.

Cuts and deviations (accepted for now): depth-first per-directory sorted entry order;
`source.resolve` accepts a bare tree digest, which packs with no image settings; E0417 reused for export write failures; mode and
uid fields clamped, the real value in pax; gc deletes pack records instead of trashing them and
does not print their count; `zbx push --dry-run --output json` prints the same line as text;
`ci-changes.sh` has no table test.

Known caveat (slice 10 review): files of the same content are written as hard links in the layer,
and size-0 files of one tree share an object, so on a snapshotter that does not keep inodes apart
two empty files can end up linked. The layer form is unchanged, since dropping those links would
change layer digests; see `docs/decisions/2026-11-08-m8-slice10-review-fixes.md`.

## Slice 11: upload and `zbx push` without credentials (lane U)

Built: `net.zig` HEAD, POST, PATCH and PUT with streamed bodies and the Location, Range and
Content-Range headers; `src/push/upload.zig` (HEAD each blob, cross-repo mount when asked, a POST
session, PATCH pieces checked against the returned Range, a closing PUT with `?digest=`, then the
manifest PUT whose `Docker-Content-Digest` must equal ours; the manifest goes up only after every
blob is confirmed); `zbx push <source> <registry/repository:tag>` (a digest-only or tagless
destination is refused, E0551); `zbx.push/1` JSON (per blob `exists`, `mounted` or `uploaded`, then
the manifest digest); E0551, E0555 (blob upload refused), E0556 (manifest refused); the push
fixture (`src/testing/vm/push_fixture.zig`), served by the simulator and by `registry_server.zig`;
the `registry` fuzzer's upload mode; the second-caller library test.

Run here: `zig build test`, `zig build tidy`, `zig build fuzz -- registry <seed> 20000`,
`zig build check` (see the report). A real TCP upload test in `host_real_net.zig` pushes through
`registry_server.zig` over loopback.

VM check (`vm/m8-slice11` on CI): in the guest, install a real registry at `localhost:5000`,
push the tree image as one user, push again (every blob `exists`, same manifest digest), compare
with the registry's `Docker-Content-Digest`, pull as a second user. It is the slice's check, not
the M8 demo. Not run here: there is no `/dev/kvm` in the build container.

Deviation: the brief's `zbx run registry:2` needs an image runtime the guest does not have at this
point, so the check installs the Ubuntu `docker-registry` package instead and serves it on
`localhost:5000`. It is the same distribution API, so the push path under test is unchanged.

Cuts: no credentials and no token flow (slice 12); a cross-repo mount is exercised by the
simulator only, since the guest holds one repository.
