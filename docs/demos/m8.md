# M8 demo: trust

This document grows slice by slice. Until the `demo-m8` job is green in CI, M8 is built, not
demonstrated. Slice 8 (below) is the demo itself: `zig build demo-m8` and `demo-m8-packages`.

## Slice 1: keys, with passphrase encryption

`zbx key new <name>`, `key list` and `key show <name>` make and describe Ed25519 signing keys
in `$XDG_CONFIG_HOME/zbx/keys` (default `~/.config/zbx/keys`, mode 0700; a key file is 0600).
A new key's secret is sealed under a passphrase with argon2id and XChaCha20-Poly1305, or kept in
the clear with `--no-passphrase`. `list` and `show` read only the `.pub` files and never need a
passphrase. What ran so far: unit and simulation tests (`zig build test`), the `key` fuzzer, and a
smoke run of the real binary on a Linux host that is not the test VM. The VM has not run it.

### argon2id measurement

`zbx key new` with a passphrase file, t=3, m=64 MiB, p=1, a `ReleaseSafe` build, five runs in
the Claude Code cloud container (4 vCPUs, Xeon at 2.3 GHz; not the test VM):
107, 108, 105, 121 and 121 ms. The whole command, not only the hash. The defaults stay at the
brief's. The VM measurement is **not yet run**; it is recorded here by the demo in slice 2.

### Known limits (accepted)

- **A forgotten passphrase is a lost key.** There is no recovery and no reset.
- **The `.pub` file's second line (the encryption word) is advisory.** `list` and `show` believe
  it; `.key` is the truth, and a later slice that opens the key reads the `.key` file.
- **argon2id's memory is taken from the OS** (`page_allocator`) for one call, because the
  command line has no allocator. The only allocation of the program, bounded by the parameter
  limits that `parse` enforces (at most 128 MiB).
- **No key deletion, rotation or export** yet: slice 1 only makes and shows keys.

## Slice 2: `zbx sign`

`zbx sign <operand> [--key <name>] [--passphrase-file <path>]` signs a tree and adds the
signature to the tree's record, `trust/signatures/<tree hex>` in the store (JSON Lines, one DSSE
envelope per line, at most eight lines). The operand is a build result or tree digest
(`b3:<hex>`) or an image `name@sha256:<manifest>`. It first checks the tree is whole and every
object hashes to its id (`E0910` if not; a missing file object says it is missing), then opens
the key (`E0911` without a passphrase; the key is opened first, and the tree is checked again under
the store lock, which avoids a check-then-sign race) and signs a `sign/v1` statement. `--key` defaults to the only key; with several it is required
(`E0006`). Signing the same subjects with the same key again changes nothing, whatever the time: the
comparison ignores `signedAt`, the old line is kept and `zbx sign` exits 0 and says it was already
signed (`docs/decisions/2026-11-08-sign-idempotence.md`). A manifest subject's name is the
canonical, tagless `registry/repository@sha256:<digest>`, so two spellings of one reference are
one line. A record that is full (eight lines for a tree, 4096 records in the store) is refused
with `E0910`; until `zbx trust prune` (slice 5) exists, the fix says to remove a record file. A record that is damaged or written by a newer release is refused with
`E0903` and never rewritten. `--output json` prints `zbx.sign/1`.

What ran: unit and simulation tests (record tests with crash simulation, `sign_commands_tests`),
and the `trust` fuzzer, which now also checks that `record.parse` accepts only what the writer
writes. The VM has not run it; `demo-m8` comes with a later part of slice 2.

### Cut: provenance statements move to slice 4 (done in slice 4, below)

The brief has `sign` sign a build result's provenance record when there is one. No provenance
record is written yet (that is slice 4), so slice 2 always signs the `sign/v1` statement. When
slice 4 lands, `sign` on a result with a provenance record signs that record's exact bytes, and
`zbx inspect --provenance` shows it. Until then the first line of the brief's demo
("`inspect --provenance` shows its inputs and builder") is not reachable.

## Slice 3, part 1: the policy file and the run gate (lane T)

Cuts and deviations (accepted for now):

  a signature, but a rule that cannot be met must not be taken for one that is.
- A `--rootfs` directory has no tree, so `require_signature` refuses it (E0905).
- The default simulated host's file system is now empty instead of down, so a run finds no policy
  file; the gate treats any read error other than "absent" as E0904.
- E0903 can now end a run (the gate reads the record), so its `explain` text and page changed.
- `policy_bytes_max` (16 KiB) is a new derived bound.

Not built in this part: `zbx policy check` (`zbx.policy/1`), the gate in `exec` and in build
steps, the tamper check (`trust/verified`, E0907, `verify = "always"`, gc), and the VM part of

## Slice 3, part 2: the tamper check (lane T)

Built: `src/trust/tamper.zig`, the tamper check E0907. Before a `run` (foreground or detached)
starts, the store child walks the tree and hashes each file object against its name, then checks
the object's mode and owner. The record `trust/verified/<tree hex>` keeps (object id, inode, size,
ctime) for each object found intact; the next run believes an object only when all four agree, and
hashes it again otherwise (a changed `ctime` always does). `verify = "always"` believes no record.
`zbx store gc` removes the records of trees it removes. E0907 names the file's path in the image and
what differs (bytes, mode, owner, missing). Simulation tests: `src/trust/tamper_tests.zig`
(changed bytes, mode, owner and a missing object are found with and without the record; a touched
`ctime` is hashed again; a garbage record is ignored) and `src/trust/gate_sim_tests.zig` (over
random policies, a refused run makes no scope and leaves the files as they were). The
`policy_keys_max` and one-past test is in `policy_tests.zig` (part 1). The VM part of `demo-m8`
(`main_m8.zig`, SIGN): a key sealed by a passphrase file signs a pulled `alpine`; under
`require_signature` the signed tree runs, an unsigned one is E0905, and a changed object of the
signed tree is E0907 until it is put back.

Cuts and deviations:
- The check runs when any policy file is loaded, even one with no rules; with no policy file, none.
- `exec` and build steps are not tamper-checked; only `run`.
- A hand change that keeps inode, size and ctime equal is not found (the record's stated limit).
- The check also compares the materialized farm `cache/<tree>` with the tree (inode per file,
  mode/owner/target per directory and link, entry counts); it refuses with E0907 and never repairs.
  Extended attributes and times of directories and links are not compared. See
  `docs/decisions/2026-11-09-tamper-farm-check.md`, which corrects the brief's "one inode covers both".
- `zbx policy check` says file integrity is not part of its preview.
- New internal constants: `trust_verified_entries_max` (65536 file objects per tree), its entry and
  file sizes. A tree with more objects is checked in full each time and gets no record.
- Still not built: the full demo steps 3 and 4 (the JSON-listing object find, offline `verify`).

## Slice 6: packages

`zig build packages` writes the `zigbox` deb and rpm for x86_64 and aarch64 and the apt and dnf
trees around them; `zig build packages-check` reads the tree back. The owner signs in two rounds
([docs/releases/packaging.md](../releases/packaging.md)); `-Dtest-key` signs with a fixed test
key instead, for CI. The writers in `src/package/` know nothing about `zbx`; `src/package_release.zig`
(pure) and `src/package_main.zig` (I/O) do.

Checked in the build container (no VM): `dpkg-deb -I` of the deb; `apt-get update` against the
test-key tree with `signed-by=zigbox-test-key.gpg` (InRelease verified, candidate `zigbox 0.3.1`);
the whole two-round flow with a scratch gpg key (header signatures, InRelease, Release.gpg,
repomd signatures), `packages-check` passing on the signed tree and failing on one appended byte.
`rpm`, `createrepo_c` and `dnf` are not in the build container; the earlier slice-6 check (see the
handoff note) ran `rpm -K/-V`, install under `--root` and a `createrepo_c` comparison.

### Known limits (accepted)

- **`primary.xml` differs from `createrepo_c` in one attribute**, `<time file>`, which is a fixed
  epoch here so the output is reproducible. `filelists` and `other` are byte-equal.
- **No `PAYLOADDIGESTALT`** in the rpm header; the file digests are SHA-256 and the payload is
  covered by the header signature.
- **Fedora's rpm 6 needs the key imported** (`rpmkeys --import`) before it accepts a signature,
  the test key included.
- **`packages-check` does not verify OpenPGP signatures** of an owner-signed tree with the public
  key. It checks each round-2 signature file records the digest bits of the file it sits beside
  (so a swapped or stale file is refused, here and when the signing run places it) and that the
  four are by one key. With `-Dtest-key` it also recomputes them and compares bytes. The runbook's
  `gpg --verify` and `rpm -Kv` are the verification. The round-1 rpm header signatures are
  checked for form only.
- **No replay or freeze protection:** `Release` has a fixed `Date` and no `Valid-Until`.
- **The maintainer string** is a supervisor assumption (`docs/decisions/2026-11-08-package-bounds.md`).
- **VM check:** `.github/workflows/vm.yml` runs the demos m0 to m7 only; see the slice report for
  the status of the `vm/m8-slice6` run.

## Slice 12: credentials and write-scoped tokens (lane U)

Built: `--username`, `--password-file` and `--password-stdin` on `zbx push` (there is no
`--password`: it is refused with E0003 and the value is never echoed; no environment variable,
no `config.json`, no credential helper). The password file must be a regular file, mode `0600` or
tighter, one line of at most 4096 bytes together with the user (`push_credential_bytes_max`); stdin
is refused when it is a terminal. The `Basic` challenge; the Bearer exchange (`Basic` sent to the
realm with the push scope `repository:<name>:pull,push`, plus `repository:<from>:pull` for a
mount; the challenge's own scope is ignored); one re-exchange when a token expires mid-push.
The realm rule: the realm host is the registry's, is the known pair (`registry-1.docker.io` with
`auth.docker.io`), or is loopback when the registry is; https, or http only on loopback;
anything else is E0554 before a password is sent. `Basic` goes only to the registry's origin or
the realm; a bearer token only to the registry's origin; a `Location` or redirect on another
origin carries no `Authorization`. The password and the token are wiped with
`std.crypto.secureZero` after use. Codes: E0552 (no credentials), E0553 (refused, or a token
without the `push` scope, naming `push`), E0554 (realm refused, blame external, exit 3), E0558
(unsafe or unreadable password source).

Tests: `src/push/auth_tests.zig` (Basic, Bearer, expiry, pull-only, far realm, wrong password,
far `Location`, and a marker-password test over 200 seeds that scans the workspace, diagnostics
and files for the secret, its base64 and the token), `src/push/credentials_tests.zig` (realm
rule, wipe, encoding, Docker Hub and GHCR fixtures), `store_commands_tests.zig` (the CLI paths and
a marker test over 60 seeds that scans stdout, stderr, files and the log), the `registry` fuzzer
(half the pushes log in, in a random mode; it asserts no credentialed request reached another
host and that the diagnostic holds no secret).

Fixtures: the Docker Hub and GHCR 401 challenges and token responses were **built from the
published documentation, not captured**: this build container has no route to either registry
with a token, and a capture would need an account. They carry placeholder tokens (`PLACEHOLDER`),
no secret. Re-capture them when someone with an account can.

VM check: `vm/m8-push-ghcr` (`vm.yml` has `packages: write` for it) builds `zbx` on the runner
and pushes a one-file tree to `ghcr.io/zigbox/zigbox-demo:<run id>` with the run's `GITHUB_TOKEN`
through `--password-stdin` only. It is not a guest demo.

Docker Hub by hand (needs an account; not run in CI):

1. Make a Docker Hub access token with read and write scope (Account settings, Personal access
   tokens). Treat it as a password.
2. Put it in a file only you can read: `umask 077; cat > ~/.zbx-hub` and paste it, then end the
   line. Or keep it in a password manager and pipe it.
3. `d=$(zbx store import ./tree)`, then
   `zbx push --username <your hub user> --password-file ~/.zbx-hub "$d" docker.io/<you>/demo:1`
   (or `... --password-stdin ...` with `pass show hub |` in front).
4. Expect the manifest digest on stdout. `docker pull <you>/demo:1` (or `zbx pull`) and compare.
5. A wrong token must end in ZBX-E0553, a world-readable file in ZBX-E0558.

Deviations: E0558 also covers stdin that cannot be read, a missing, linked or unreadable file and a
`:` in the user (the brief names the mode and size cases only); a 403 `DENIED` answered to a
credentialed request is reported as E0553; I did the mechanical parts (goldens, error pages,
help) myself, not with a Haiku subagent.

Cuts and known limits: the `429` retry stays cut; no inspection of a JWT's scope (the push asks
for what it needs and a refusal is E0553). Wiped: the password and username (`Credentials.wipe`),
the Basic text, the token, the token service's answer and its parse memory (`wipe_secrets`), and,
after every network call that carried a credential and on every way out of it, the request head
and the socket's and TLS's plaintext read and write buffers of the network memory (`wipe_buffers`).
Not wiped, because they are not ours: the key and cipher state inside std's TLS client, kernel
socket buffers, and copies the kernel or a core dump took before the wipe. The child exits
straight after the push.

Slice 12 VM check, recorded: `vm/m8-push-ghcr` run 42573408656 pushed `ghcr.io/zigbox/zigbox-demo:<run id>`
with the run's `GITHUB_TOKEN` through `--password-stdin` and passed. Two earlier runs failed and
found real problems the simulator hid: a directory is not a push source (the check now imports the
tree into the store first), and `HostReal.read` asserted an open file on standard input, so the first
real `--password-stdin` push panicked (fixed: handle 0 is exempt).

## Slice 14: the derived binding

A pulled image's run now meets a result-bound statement, so `require_provenance` holds for pushed
images (a pushed image carries its result's digest in its config, and the pull derives it again).

- The image record is version 3: pull keeps the config's labels (`.label_key`/`.label_value`
  lines in key order, or `.labels_unknown = true`). Version 1 and 2 still read, with the labels
  unknown; a record with unknown labels derives no result, so a result-bound statement does not
  count for it. The run says so (`not_derived`: pull the image again, which rewrites the record
  as version 3), not that the statement is for another result.
- The verdict derives the zbxResult digest from the tree, the recorded settings and the labels
  with `build/result.zig`'s own encoder (`encode_parts`), so it is M7's digest by construction.
  `zbx policy check` and `zbx run` and `zbx exec` ask the same question.
- Pull checks the manifest's `org.zigbox.tree` annotation against the tree the layers made and
  warns `ZBX-W0551` on a mismatch; nothing relies on the annotation.
- Tests: random configs round-trip (pushed, then pulled, derives the original digest), every
  changed field changes the digest, a version 2 record derives none, the verdict counts a derived
  match and not a mismatch.

Cuts and limits:

- Labels kept in the record are bounded by `image_labels_bytes_max` (2 KiB) and
  `image_labels_count_max` (32). An image with more is recorded with unknown labels (it derives
  nothing, is never refused). 8 KiB would not fit the record buffer.
- An image built by a build step from a base does not derive: the base's labels are not in its
  record. It still meets a manifest-bound statement.
- Labels never refuse a pull: they are read by their own bounded scan of the config, so a repeated
  key or a huge value leaves them unknown, as main (which skipped them) accepted both. The
  manifest annotation is read the same way. A label over 1 KiB used to trip an assertion when the
  record was written; fixed (`roots.put_string_up_to`).
- Not run here: the upgrade VM demos (`vm/all-slice14` on CI).
- Upgrade: a store pulled into by this release holds version 3 records, which an older zbx does
  not read (it says the record is from a newer zbx, as for any version it does not know).
  Upgrade every zbx that shares a store together. Records an older release wrote still read.

## Slice 4: provenance (lane T)

`zbx build` writes a provenance record for each result it builds, hit or miss, unsigned, at
`trust/provenance/<result hex>` (atomic rename, under the store lock; a later build of the same
result replaces it). `zbx inspect --provenance <result digest>` shows it as labelled text or as
`zbx.provenance/1` (`--output json`; `zbx schema inspect-provenance`) with the keys that signed
a provenance statement of the tree, each marked "this record" (the envelope's payload is the
stored bytes) or "an earlier build" (a later build replaced the record). `zbx sign <result>`
wraps the stored record's exact bytes in the DSSE envelope; a result with no record (built
before this slice) falls back to the `sign/v1` statement, so a 0.3.0-written cache still signs.
`require_provenance = true` in the policy needs a signature by a listed key over a provenance
statement of the run's tree, bound to the result that is to run; otherwise the run is refused
as E0906, with one of five causes: nothing stored or signed (`missing`), a record or a
provenance line with no listed key's valid signature (`unsigned`), a signed record of another
result (`other_binding`), a manifest-bound run whose image record cannot derive a result
(`not_derived`: it predates the labels, or they did not fit; "pull the image again"), or a
subject that is no build result (`not_a_result`: a build step's base, a bare tree digest). A
directory run has no tree, so it is E0905's no-tree form.
**Since slice 14, a pulled or pushed image can meet `require_provenance`:** its record derives
the result M7 would compute from its tree, settings and labels, and a signed provenance
statement of that result counts (`verdict.derived_fits`). E0906 then judges the image against
the derived result, with the same `missing`, `unsigned` and `other_binding` causes as for a
build result. A build step's base still never derives (slice 14's cut), so `require_provenance`
refuses every registry base in a `zbx build`, as `not_a_result`.

When the store already holds `trust_records_max` provenance records, a build still succeeds but
writes no record for a result that has none, and prints ZBX-W0901 on stderr (exit 0); a policy
with `require_provenance` then refuses that result as E0906 `missing` until room is made.

### The statement, and the SLSA field map

The record is an in-toto Statement v1 in canonical JSON (`json.zig`: schema order, no
whitespace, integers only; `parse` reads the members in the writer's order, renders what it read
and refuses any payload that is not those bytes). Its predicate is SLSA provenance v1.

| SLSA field | Zigbox value |
| --- | --- |
| `subject[0]` | `{"name":"tree","digest":{"zbxTree":<hex>}}`, the image tree |
| `subject[1]` | `{"name":"result","digest":{"zbxResult":<hex>}}`, the build result record |
| `predicateType` | `https://slsa.dev/provenance/v1` |
| `buildDefinition.buildType` | `https://zigbox.org/build/v1` |
| `externalParameters.buildFile` | `{"name":<path>,"digest":{"blake3":<hex>}}` |
| `internalParameters.steps[]` | per step: `name`, `key`, `base` (index into `resolvedDependencies` bases), `input`, `needs` (name to output tree), `output`, `network` |
| `internalParameters.image` | `{"key":<image key>,"base":<index or null>}` |
| `resolvedDependencies[]` | `zbx.lock` as `{"name":"zbx.lock","digest":{"blake3":..}}` when there is a lock, then each base: `name` the reference as written, `digest` `{"sha256":<manifest>}`, `annotations` `{"zbxTree":<tree>}` |
| `runDetails.builder.id` | `https://zigbox.org/zbx` |
| `runDetails.builder.version` | `{"zbx":<release>,"platform":"linux/amd64" or "linux/arm64"}` |
| `runDetails.builder.builderDependencies[]` | the running binary, `{"name":"zbx","digest":{"blake3":..}}` |
| `runDetails.metadata` | `startedOn`, `finishedOn`, RFC 3339 UTC, whole seconds |

Digest-set keys: `zbxTree` and `zbxResult` are Zigbox's own (a BLAKE3 tree digest and a
BLAKE3 result-record digest, 64 lower-case hex digits, no `b3:` prefix); `blake3` is the
registered-by-convention name for BLAKE3 files; `sha256` is a base image's manifest digest.
`build_file`'s path that is not UTF-8 is recorded as `(path is not UTF-8)`.

A record is a function of the build's inputs and its two times: an all-hit rebuild of an
unchanged project writes the same record but for the times (a test in `compose_tests.zig`
builds, builds again, deletes the record and builds once more, and compares). The lock digest is
read from `zbx.lock`; the binary's digest is streamed from `/proc/self/exe` (zero if it cannot
be read).

### Schema check

`src/testdata/provenance_golden.json` is the rendered sample record of
`trust/provenance_tests.zig`. Its `predicate` was checked once against SLSA's published schema:
the `slsa.v1.Provenance` message of https://slsa.dev/spec/v1.0/schema/provenance.proto,
compiled with protoc, and the predicate parsed with python protobuf 7.36.2's
`json_format.Parse` (strict: an unknown field or a wrong type fails). It parsed. SLSA publishes
no JSON Schema file, so the proto is the schema. The check is not part of CI; the test pins
the bytes.

### Cut: the git source read

The brief's optional read of the git source (commit and remote for the build file's repository)
is cut: nothing in the demo needs it, and it would be the first thing `zbx build` reads outside
the store and project. The record has no `git` field; adding it later is a new record shape.

### Deviations

- `statement_bytes_max` is now derived from the longest provenance record, rounded up to 64 KiB:
  256 KiB, up from 128 KiB (docs/decisions/2026-11-09-m8-statement-bytes-from-provenance.md).
  `inspect_provenance_bytes_max` is twice that. `sim_fs_pool_bytes_max` rises from 2 to 3 MiB so
  the simulated store holds a worst-case signature record; 4 MiB pushes the test binary's static
  data past the linker's 2 GiB limit.
- A store too full to take the record (`trust_records_max`, 4096) skips it with one line on
  stderr that names the bound; the build still succeeds, and a result without a record signs
  `sign/v1`. The line has no warning code of its own: a W-code is the owner's call. Under
  `require_provenance` that result is then refused as E0906 `missing`, and nothing in this
  release removes records (prune is slice 5).
- `zbx sign` of a result whose provenance record was rewritten by a rebuild (new times only)
  adds no line when the same key already signed that tree's provenance for that result, so a CI
  job that signs after every build cannot fill the tree's eight lines.
- Not fixed: the record's lock digest is taken from `zbx.lock` as it is on disk at the end of the
  build (review NIT); the lock's loaded bytes are not kept.
- E0906 is the only code added; a result with no record under `inspect --provenance` is E0005.

## Slice 5: verify and the trust bundle (lane T)

`zbx verify <result|tree|name@sha256:...>` checks six links offline (no network, no registry
call; a simulation test counts requests) and prints one line per link, or `zbx.verify/1` with
`--output json`: 1 signatures, 2 signer, 3 tree, 4 provenance, 5 inputs, 6 build_file. A link
after a broken one reads `not reached`. A broken link prints the report on stdout, then
`ZBX-E0908` on stderr, exit 1. The signer link needs `--key`, `--public` or a policy file;
with none it is E0908 "no signer is trusted". `--strict` fails on an absent input (`ZBX-W0903`
otherwise), `--require-provenance` fails when no signed provenance fits. A signature record
that is damaged is `E0903` (exit 2: the store, not the artifact, is at fault).

`zbx trust export <tree>` prints the tree's signatures as a bundle on stdout; `zbx trust import
<file>` adds the new ones, each verified before it is stored; a bundle with any damage is
refused whole as `E0909` and changes nothing. `zbx trust prune` lists the signature and
provenance records whose tree is gone (a dry run) and `--apply` removes them; a damaged record
of a tree that is present is kept and warned as `W0902` (a damaged record of an absent tree is an orphan and is removed). `zbx store gc` now counts such records (`trust_orphans` in
`zbx.store.gc/1`; a text line naming `zbx trust prune` when above zero).

Tests: `trust/peer_tests.zig` (library), `trust/verify_trust_tests.zig` (commands, offline,
every broken link, the orphan life cycle), the `peer` fuzzer (a bundle with a bit flipped is
refused whole, or stored exactly), and the guest check in `testing/vm/main_m8.zig`.

### Cuts

- **Derived-result binding** (slice 14) is not part of verify: a derived result is not
  re-derived, only its signatures, tree and provenance are checked.
- **`store_full` on import** (4096 records) mirrors sign's check but is not exercised: the
  simulated filesystem holds 640 nodes. The scan bound is tested by lowering the limit
  (`scan_limited`).
- **Bundle unreadable** (a file that cannot be read, or is missing) is `E0909` with its own
  wording; no further code was registered.
- **A truncated prune scan** reads the first `trust_records_max` names of each directory in
  directory order, so orphans past the bound are not reached while earlier names are all kept;
  this is acceptable under the bound and the report says `truncated`.
- **`--key` and `--public`** add no trust when a policy file is present: see
  `docs/decisions/2026-11-09-verify-policy-decides.md`.
- **Sim hosts report owner 0**, so only the VM proves the tree check's object ids.
- **W0903**, not the brief's `W0901`: see `docs/decisions/2026-11-09-verify-absent-input-w0903.md`.

## Slice 9: the Mac

On the Mac, `zbx key`, `sign`, `verify`, `trust` and `policy` are forwarded whole to the Linux
zbx in the machine (owner decision 4: forwarded, not demonstrated). `build` and `inspect` are not
forwarded. Nothing here is new on disk: the forwarding protocol drops `XDG_*`, so keys and the
user's policy land under `~/.config/zbx/` with the home mounted at the same path, and they live
on the shared Mac home.

- **No terminal.** `key` and `sign` are forwarded with no terminal (`Command.terminal` is false),
  so a command that would ask for a passphrase is refused by the Linux zbx's existing one-line
  `ZBX-E0911`; no code was added. `sign` needs this too: only the key file says whether it is
  sealed. On the Mac a key therefore uses `--passphrase-file` (a file under the shared home) or
  `--no-passphrase`. The terminal passphrase read is not forwarded (the brief's cut).
- **Not run.** No Mac was available and the macOS CI runner was down: the forwarding table and
  the no-terminal rule are unit tests that compile only on macOS; they were type-checked with
  `zig test -target aarch64-macos` as far as the missing embedded `vm_image_version` allows.
- **The Mac's E0911.** The Linux zbx cannot tell a Mac's missing terminal from a script's, so
  `zbx guest serve` sets `ZBX_FORWARDED=mac` for every forwarded command (the guest ignores any the
  Mac sends), and `trust/diagnose.zig` then says "zbx on a Mac does not ask for one on the
  terminal; give it with --passphrase-file". The fix now names the command that was run: for
  `sign` it is `zbx sign <what> --key <name> --passphrase-file <file>`, not a new key (this
  also corrects the Linux fix). No code was added, and the Linux text is unchanged, so the
  checked-in E0911 goldens still hold; the three variants are a unit test in `diagnose.zig`, and
  E0911's `explain` text has a Mac paragraph.
- **Cut: a `--passphrase-file` (or `trust import <file>`) outside the home.** The Mac does not
  check path arguments, so a file under `$TMPDIR` (`/var/folders/...`) is refused with E0911
  "there is no file ...", though it exists: the machine shares only the home. A true diagnostic
  needs a message that is not E1013's `cd ~` fix, which is a new wording to register; it waits
  for the owner. The Mac help says the file goes under the home.
- **Tests.** The tables and the walk of the command line moved to `src/forward_commands.zig`, with
  one `first_operand` shared by `forwarded`, `runs_container` and `has_terminal`; they run in
  `zig build test` on Linux. `forward_commands_tests.zig` checks each forwarded name against
  `cli.command_named`, and that every forwarded command whose source calls `passphrase.acquire`
  is in `no_terminal_commands` (it reads source text, so a new command's file is added to its
  list). `Command.terminal` has no default.

## Checks to run on a real Mac (not run: none was available)

virtiofs may differ from a Linux disk in three ways that make `key` and `sign` refuse falsely or
hide a weakness. Run these on a Mac with the machine up, in a shell in your home:

1. `zbx key new t --no-passphrase`, then `ls -led ~/.config/zbx/keys ~/.config/zbx/keys/*`.
   Expect mode 700 on the directory, 600 on the key and two files. If the directory is 755 the
   share ignores `chmod` and every `key` and `sign` is refused (E0901 `dir_too_open`, whose
   `chmod 700` fix does nothing). If `key new` is refused with "could not be read" and an errno,
   the share lacks `link()`, which `key_store.write_new` uses.
2. `chmod 644 ~/.config/zbx/keys/t.key; zbx sign <digest> --key t`. Expect E0901.
3. A passphrase file at mode 644 with `zbx key new u --passphrase-file <file>`: expect E0911
   `file_too_open`; at 600 it works.
4. ACLs are invisible to both mode checks: `chmod +a "group:staff allow read" <file>` leaves 600
   and the file is accepted. The check cannot see this; it is a known gap, not a fix for this
   slice.

If 1 fails, the fix is to keep the keys directory on the machine's disk (a cut of "keys on the
Mac home"), which is an owner decision.

## Slice 8: the demo

`zig build demo-m8` runs in one VM, as the ordinary user, in this order: **UPGRADE8**

reuses its volume), **SPEC** (the M6b spec part), **HELLO** (M7's steps on the Go hello-world),

`zig build demo-m8-packages` is slice 7's, unchanged; CI runs it only when `.github/ci-changes.sh`

### By hand

1. `zbx key new demo --passphrase-file ~/pass` (mode 600; the file's contents are never on a command
   line), then `zbx build`, `zbx sign <result> --passphrase-file ~/pass`, and
   `zbx inspect --provenance <result>`: the bases, steps and builder, signed.
2. A policy at `~/.config/zbx/policy.zon` with `.require_signature = true` and the key's public
   part (`zbx key show demo`): the signed result runs; `zbx run alpine:3.20 true` is E0905, exit
   125, and makes no container, run record or scope.
3. Append one byte to the hello binary's object (`chmod u+w`, `printf x >>`): `zbx run` is E0907
   naming `/usr/local/bin/hello`; `zbx store verify` names the object. Remove the byte and set the
   mode back: the run works.
4. `unshare -n zbx verify <result>`: six links ok with no network at all.
5. `zbx policy check <result>` agrees with `run`; `sign` with no passphrase file and no terminal,
   or a wrong one, is E0911 at once and writes no record; `zbx trust export <result>` is one

### Failure modes

- **A lost key or a forgotten passphrase** is a lost key: no recovery. Signatures already made stay
  valid; make a new key, add it to the policy, and sign again.
- **A key file too open** (mode other than 0600, or a passphrase file readable by others) is
  refused with E0911 before anything is read. `chmod 600` it.
- **No passphrase and no terminal** is E0911 at once; give `--passphrase-file`.
- **A policy that refuses everything** (`require_signature` with no trusted key) makes every run
  E0905. `zbx policy check <result>` says why without running; remove or edit the file.
- **A tampered object** is E0907 naming the path; `zbx store verify` names the object. Recover by
  putting the bytes back, or `zbx store rm` the tree and pull or build it again.
- **A provenance record replaced after signing** no longer matches the signed digest: `verify` link
  4 fails (E0908). Sign the new record, or restore the old one from a `trust export` bundle.
- **A missing input in `verify`** (a base or source gone from the store) fails the inputs link
  (E0908); pull it again, or `trust import` the bundle.
- **The disk full during a signature write:** the record is written whole or not at all (a
  temporary file renamed), so the old record stays; free space and sign again.
- **Orphan records** (a tree gone but its record kept) are listed by `zbx trust prune` and removed
  by `--apply`. Pruning gives up the ability to verify that tree's old signatures again unless
  they were exported first.
- **A package upgrade with a container running:** the package replaces `/usr/bin/zbx`; the running
  container keeps its mapped binary and is not restarted. New `zbx` commands read the old run
  record (version 8 reads as 9). Stop and start the container to use the new binary.
