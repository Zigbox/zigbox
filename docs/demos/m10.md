# M10 demo notes

## Scope cuts

- **Slice 1: `--device` refuses `:`, so by-path names are out.** `/dev/dri/by-path/pci-0000:03:00.0-render`
  and `/dev/char/226:128` are refused with E0225, which rules out the stable names a multi-GPU
  host would use. Give the node they point to (`/dev/dri/renderD128`). See
  `docs/decisions/2026-11-12-device-path-limit.md`: paths are at most 48 bytes, and by-id and
  by-path names are not supported.

## Not run in the VM

- **`--user` with `--device` on a real kernel.** The review asked for a `--user 1000:1000 --device`
  case in the M1 guest. CI (run 43284204313, step `EXTRA: --device`) shows the command line
  refuses it: `error[ZBX-E0015]: not a valid --user value ... a directory has no image to look
  the user up in`. Only an image with a `USER` reaches the `set_user` step, and the M1 guest has
  no image. The `keep_groups` branch of `HostReal.set_user` is therefore covered by the
  simulator tests only (`devices_tests.zig`, which count `setgroups` through `run.start`, the
  library path) until a guest that runs an image gets a device step (slice 2 or later).

## Slice 2 (CDI)

- **The guest has no GPU and no vendor driver.** The M1 step `EXTRA: --device vendor.example/gpu=0`
  writes a fake vendor spec in `/etc/cdi` (one node, the `render` node of slice 1, one variable and
  the `nvidia-cdi-hook update-ldcache` hook) and checks that the run opens the node, sees the
  variable, and that `gpu=9` is E0230 listing
  `vendor.example/gpu=0`. A real NVIDIA spec and driver libraries are not exercised anywhere.
- **Libraries.** The mounts (a directory and a file bind) and the `LD_LIBRARY_PATH` fallback
  (set, and put before a value the user gave) are covered by simulator tests
  (`cdi_run_tests.zig`); the M1 fake vendor spec binds a directory too, so the VM runs the mount
  path (the command reads a file in it and finds it read-only). No glibc image runs in the guest,
  so a real `ldconfig` writing a cache is not run. Alpine (musl) cannot load glibc driver
  libraries. W0208 must not appear in the guest (the VM check fails on it): the Alpine rootfs's `ldconfig` is a stub that exits
  0. W0208's text is checked by its golden, and the simulator test sees it once when `ldconfig`
  is absent.
- **`ldconfig` runs last and is bounded.** It runs after the descriptors are sealed, the
  capabilities dropped and seccomp installed (just before `exec`), with an alarm of
  `cdi_ldconfig_seconds_max` (10) seconds. A timeout is a failed `ldconfig`: W0208 and the
  `LD_LIBRARY_PATH` fallback. It runs as the container's user, so with a read-only `/etc` it may
  fail to write the cache and the fallback is taken. The deadline is in the waiter (SIGKILL of the helper's process group at expiry); one deadline covers the reads and the reap (a helper that closes or redirects its own output, or writes past the read bound, is killed too), and a killed run is W0208 even when the helper had exited 0. Real-host unit tests run each hang shape and check the status is SIGKILL and `timed_out` is set. The helper's stdin is `/dev/null`. A helper process that escapes the kill (for instance by `setsid`) keeps running as a child of the user's command; zbx does not hunt it down. The simulator has no hanging program: a knob makes an installed `ldconfig` report a timeout, and a test checks W0208 and the fallback; a hang itself is run only on the real host.
- **`--read-only` with a device that has mounts is refused up front** (E0227, one line, "mounts,
  which a read-only root (--read-only) cannot take"); the mount targets cannot be made in a
  read-only root. Devices with nodes only work with `--read-only`. Both are simulator tests.
- **Spec directories**: `$XDG_CONFIG_HOME/cdi` (else `$HOME/.config/cdi`), then `/var/run/cdi`,
  then `/etc/cdi`, the first winning. At most 64 spec files in all, read in name order; more is
  E0226. See `docs/decisions/2026-11-13-cdi-discovery-and-late-steps.md`.
- **A resolved set given to the library (`Spec.cdi`)** gets the same host check as discovery;
  a node the host lacks is E0225 (not E0230: the name is already resolved).
- **Cut: a spec over 64 KiB is refused** (`cdi_spec_bytes_max` is 65535; was planned at 256 KiB,
  the host read limit makes it 64 KiB). E0226 says it is too big.
- **Cut: YAML specs** are refused with E0226 and the `nvidia-ctk cdi generate --format=json` fix.
- **Cut: hooks other than `nvidia-cdi-hook update-ldcache`, `intelRdt`, `additionalGids`, mounts
  that are not binds** are E0227, only for a device that has them.
- **Still not run: `--user` with `--device`** (see slice 1 above): the guest still has no image.

- **VM step `EXTRA: doctor's GPU section, --gpu all and --gpu dri`** (demo-m1): writes the spec
  `zigbox.test/gpu` with a `render` node and checks doctor lists the spec and the node as
  openable. Then, by what the guest has: with no `/dev/dri/renderD*`, `--gpu all` is E0228 and
  `--gpu dri` is printed as NOT RUN; with one, `--gpu dri` must show it in `ls /dev/dri` and the
  E0228 half is not exercised there (it is by simulator tests and the E0228 golden). CI run 43399633096 (vm/m1-m10-slice3, demo-m1 PASSED in 45 s): the guest has no render
  node, so doctor listed `zigbox.test/gpu=0` with its node openable, `--gpu all` was E0228, and
  **`--gpu dri` was NOT RUN** (cut: no render node in the runner's QEMU guest).
- **Deviation: `zbx inspect` shows what was asked only** (`"asked":"gpu=all"`), not asked and
  resolved. The record keeps what was asked, as the brief says; the resolved set depends on the
  host at start, and nothing stores it, so inspect cannot show it without re-resolving on a
  different host state. Doing it means adding the resolved paths to the record (a format change).
  Cut; the owner decides.
- **`schemas.zig`'s inspect `devices` item** still lists `path` as required, though CDI names and
  `gpu=` keywords have none (slice 2 already did this). Not changed here.
- **Mac**: `--gpu` and `--device` are E0229 (Apple's virtualization gives a Linux guest no GPU
  compute); golden in `vm_golden.zig`. Not run on a Mac.
- **Help text is 16383 of the 16384-byte `output_bytes_max`.** Slice 4 adds flags only by trimming
  help or raising the bound (a user-visible limit: ask the supervisor).

## Slice 4 (`zig build demo-m10`, CI, by-hand steps)

`demo-m10` (`src/testing/vm/main_m10.zig`, checks in `checks_m10.zig`, each with a unit test)
runs a fake vendor, `zigbox.test/gpu`, in the Ubuntu 24.04 guest. The node is `/dev/zbx-gpu`
(the character device 1:3, mode 0660, group `render`), the spec is `/etc/cdi/zbx-gpu.json`, and
the container is the pinned Alpine minirootfs. The seven steps:

1. `zbx doctor` lists the spec, its device and the node, and no GPU line is a gap.
2. `--device zigbox.test/gpu=0`: the node opens, `ZBXGPU=on` is set, the library is mounted.
3. `--gpu all` is E0228 when the guest has no render node, or `--gpu dri` lists it when it has one.
4. After `gpasswd -d demo render`, the same run is E0225 naming the node and the group.
5. A YAML spec beside the JSON one: doctor shows the refusal and the `--format=json` fix, the JSON
   device still runs, and a name only the YAML could hold is E0226 naming the file.
6. A copy of the rootfs without `ldconfig` runs with W0208, and the library directory is on
   `LD_LIBRARY_PATH`.
7. A run with no devices has no demo node, no note and exit 0.

**Not run here:** `--gpu dri` when the guest has no render node (the usual case on the CI
runners' QEMU). The output prints `NOT RUN: --gpu dri`; step 3 then checks the E0228 refusal.
No real NVIDIA, AMD or Intel hardware was available, so those paths are by hand (below).

### By hand: NVIDIA

1. Install the driver and `nvidia-container-toolkit` (it gives `nvidia-ctk`).
2. `sudo nvidia-ctk cdi generate --format=json --output=/etc/cdi/nvidia.json`. zbx does not read
   YAML; `zbx doctor` says so if `nvidia.yaml` is the only spec.
3. `zbx doctor`: every `gpu` line should be `ok`. A closed node names its group, for example
   `sudo usermod -aG render $USER` (log in again afterwards).
4. `zbx run --gpu all --rootfs ./debian -- nvidia-smi` (a glibc image; see "Alpine" below).

### By hand: AMD

1. Install the ROCm stack. The nodes are `/dev/kfd` and `/dev/dri/renderD*`; both must be openable
   by you (groups `render`, and `video` on some distributions).
2. `zbx doctor` should list the render nodes. `zbx run --gpu dri --rootfs ./ubuntu -- rocminfo`
   passes the render nodes only; `kfd` needs a CDI spec naming it, or `--device /dev/kfd`.

### By hand: Intel

1. The i915 or xe driver gives `/dev/dri/renderD*`. `zbx run --gpu dri --rootfs ./ubuntu -- vainfo`
   (with `intel-media-va-driver` in the image).

### Failure modes

- **A driver upgraded under a stopped container.** A container that was stopped before an upgrade
  keeps the library paths it was started with; the new driver's files are at other paths. Start
  it again with a fresh `zbx run`, which reads the spec again. `zbx doctor` says a spec is stale
  when a mount source in it is gone: regenerate it with `nvidia-ctk cdi generate`.
- **A user not in `render`.** E0225 names the node and its group; `zbx doctor` prints the
  `usermod -aG <group> $USER` fix.
- **A YAML spec.** Refused with E0226 when a device only it could hold is asked for (and doctor
  says so). Generate JSON instead.
- **An Alpine image with NVIDIA.** The NVIDIA libraries are glibc builds. On musl they do not
  load; the run starts, the program does not find `libcuda`. Use a glibc image.

### Cuts and deviations (slice 4)

- `handle_bytes_max` went from 480 KiB to 768 KiB (`src/constants.zig`): the run's `Handle` now
  holds the CDI scratch, so `gpu.zig` no longer takes ~269 KB of stack.
- `inspect` shows the devices asked for, not the resolved set (accepted by the owner).
- `--device gpu=all` is not an alias for `--gpu all`: E0225.
- The help text was tightened to stay under its 16384-byte bound; the bound is unchanged.
